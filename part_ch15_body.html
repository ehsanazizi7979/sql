Chapter 15

Automating Plan Capture

Everything so far assumed you were sitting in front of SSMS. This chapter is about the 2 a.m. problem: the plan you need was captured by nothing, cached for four seconds, and is gone. The answer is an Extended Events session — three showplan events, a couple of filters, and a file on disk.

1 Why you'd automate at all

The plan cache and the Query Store both give you aggregated metrics. Aggregation is exactly what hides the five minutes last Tuesday when everything went wrong.

Everything in Chapter 9's DMVs is a counter. Each execution adds to total_elapsed_time, and the row you read is the total since the plan entered cache. If a query is erratic, or the instance only misbehaves at specific times, that average smears the interesting part into nothing. You need per-execution plans plus their runtime metrics, for a period.

Three specific situations defeat the casual approaches:

  • The plans aren't there any more. High volumes of ad hoc, unparameterized queries flood the cache with single-use plans, and older plans age out (Chapter 9). The same workload probably has the Query Store filtering out most of that noise, so the plan is in neither place.
  • It happened hours ago. By the time you're looking, the offending execution is history. You need something that was already recording.
  • You can't change the code. Adding SET STATISTICS XML ON to a batch is fine on your dev box; on production it means a deployment.
The two tools Extended Events — the modern one, and what you should be using on SQL Server 2012+ and Azure SQL DB. SQL Trace / Profiler — the one it replaced, deprecated, and only relevant if you're on SQL Server 2005–2008R2 (2008/2008R2 Extended Events exist but can't capture plans and have no GUI).

2 Why Extended Events, in one table

The difference isn't cosmetic. It's collect-everything-then-discard versus collect-almost-nothing-on-purpose.

Extended EventsSQL Trace
Design principleCollect as little as possible; you define precisely when to collect.Collect everything that might be needed, then discard what a trace doesn't want.
Where it runsAt a lower level inside SQL Server.Higher up, with a heavier payload per event.
FilteringPredicate evaluated before the event fires fully — cheap.The event fires fully for every database and every SQL text; the filter is applied only when the trace consumer reads it.
Extra fieldsNone by default. You add actions (e.g. sql_text) explicitly.Several global fields collected on every event whether you want them or not.
FutureWhere all new SQL Server monitoring functionality is built.On the deprecation path.
The caveat that applies to both Capturing a plan happens in-process, on the same thread that executes the query, and plans are big. That means real memory and I/O overhead added to the server you're diagnosing. On production: add very granular filters, run for minutes not days, and test first.

3 The three showplan events

They capture the plan at three different moments in the optimization process. Only one of them carries runtime metrics — and that's the expensive one.

EventFiresRuntime metrics?Use it when
query_post_compilation_showplan Only on plan compilation. First call of a proc/batch/ad hoc query; also fires for an estimated-plan request when nothing is cached. Won't fire on plan reuse. No You want to see what was compiled — e.g. plan before a recompile.
query_pre_execution_showplan Right before execution. The plan compiled or retrieved from cache. No Recompile investigations: capture before and after.
query_post_execution_showplan After execution. Yes — row counts, executions, estimated vs actual. Almost always. This is the one the author reaches for.
Because the first two fire before execution… …neither can contain runtime statistics. That's not a bug in your session; there's simply nothing to report yet. And because the third one carries both the plan and the metrics, it's the most expensive of the three.

The author usually adds two non-plan events for context: sql_batch_completed (useful performance metrics for the finished batch) and sql_statement_recompile (which reveals the cause of a statement-level recompile plus the database and object it happened on).

4 Building a session in the GUI

Worth doing once so you can see what every option means — then script it out and never open the dialog again.

Sessions live per-server under Management → Extended Events → Sessions. The green arrow / red square tells you running vs stopped; AlwaysOn_health, system_health and telemetry_xevents are built in.

Note the description under query_post_compilation_showplan: "Using this event can have a significant performance overhead so it should only be used when troubleshooting or monitoring specific problems for brief periods of time." That is the product team saying the same thing as the caution box.

Reading those predicates The name in the GUI is equal_i_sql_unicode_string; when scripted it collapses to plain =. The like_i_sql_unicode_string comparator collapses to LIKE. Same predicate, two spellings — that's why the T-SQL in Listing 15-1 looks simpler than the dialog.

The remaining two tabs are the payload: Event Fields (base columns, always captured) and Global Fields (Actions) — where nothing is collected by default, and where you'd add sql_text if an event didn't already carry it. Actions cost extra, so add sparingly.

The last page, Advanced, sets the memory buffer, dispatch frequency and retention; the book doesn't cover it. Click OK and, because "watch live data" was ticked, a Live Data window opens immediately.

Skip the New Session Wizard It can only create sessions, never alter them, and it has limitations. Use the dialog above, or skip straight to T-SQL.

5 The same session, as T-SQL

Right-click the session → Script Session As…. You get something you can read in a code review, diff, and move between servers.

Listing 15-1 · event session with all three showplan events
CREATE EVENT SESSION ExecutionPlansOnAdventureWorks2014
ON SERVER
    ADD EVENT sqlserver.query_post_compilation_showplan
    (WHERE (   sqlserver.database_name = N'AdventureWorks2014'
               AND sqlserver.like_i_sql_unicode_string(sqlserver.sql_text,
                       N'%Person.Person%'))),
    ADD EVENT sqlserver.query_post_execution_showplan
    (WHERE (   sqlserver.database_name = N'AdventureWorks2014'
               AND sqlserver.like_i_sql_unicode_string(sqlserver.sql_text,
                       N'%Person.Person%'))),
    ADD EVENT sqlserver.query_pre_execution_showplan
    (WHERE (   sqlserver.database_name = N'AdventureWorks2014'
               AND sqlserver.like_i_sql_unicode_string(sqlserver.sql_text,
                       N'%Person.Person%'))),
    ADD EVENT sqlserver.sql_batch_completed
    (WHERE (   sqlserver.database_name = N'AdventureWorks2014'
               AND sqlserver.like_i_sql_unicode_string(sqlserver.sql_text,
                       N'%Person.Person%')))
    ADD TARGET package0.event_file
    (SET filename = N'C:\PerfData\ExecutionPlansOnAdventureWorks2014.xel')
WITH (MAX_MEMORY = 4096KB,
      EVENT_RETENTION_MODE = ALLOW_SINGLE_EVENT_LOSS,
      MAX_DISPATCH_LATENCY = 30 SECONDS,
      MAX_EVENT_SIZE = 0KB,
      MEMORY_PARTITION_MODE = NONE,
      TRACK_CAUSALITY = ON,
      STARTUP_STATE = OFF)
GO

Every choice from the five dialog pages is here. And the WITH block is worth reading once:

OptionWhat it does
MAX_MEMORYBuffer size before events are dispatched to targets.
EVENT_RETENTION_MODEWhat to lose when the buffer fills. Here: a single event.
MAX_DISPATCH_LATENCYHow long events can sit in the buffer before being flushed — trades latency for overhead.
TRACK_CAUSALITYAdds the attach_* fields so related events can be grouped and ordered.
STARTUP_STATEON would restart the session when SQL Server starts. Deliberately off here.

Triggering it with a plan you know isn't cached

Listing 15-2 · evict the plan, then run the query
USE AdventureWorks2014;
GO
DECLARE @PlanHandle VARBINARY(64);

SELECT  @PlanHandle = deqs.plan_handle
FROM    sys.dm_exec_query_stats AS deqs
        CROSS APPLY sys.dm_exec_sql_text(deqs.sql_handle) AS dest
WHERE   dest.text LIKE '%Person.Person%';

IF @PlanHandle IS NOT NULL
    BEGIN
        DBCC FREEPROCCACHE(@PlanHandle);
    END;
GO

SELECT  p.LastName + ', ' + p.FirstName ,
        p.Title ,
        pp.PhoneNumber
FROM    Person.Person AS p
        JOIN Person.PersonPhone AS pp
        ON pp.BusinessEntityID = p.BusinessEntityID
        JOIN Person.PhoneNumberType AS pnt
        ON pnt.PhoneNumberTypeID = pp.PhoneNumberTypeID
WHERE   pnt.Name = 'Cell'
        AND p.LastName = 'Dempsey';
GO

Why the setup batch? To guarantee all three showplan events fire — no cached plan means a genuine compile. Both batches run in AdventureWorks and both mention Person.Person, so all four events fire twice. Run the query batch alone afterwards and you get only three events: nothing recompiles, so no post_compilation.

The clue that a plan came from Extended Events

Recognise this shape If you open a plan and the top of the tree looks wrong — no SELECT, missing properties — you're not looking at a broken plan. You're looking at a plan captured out-of-band, and the metadata lives in the XML rather than the picture.

6 Reading the event details

The grid tells you an event fired. The Details tab tells you when, how much it cost, and what other events belong to the same story.

Three things in that pane earn their keep:

  • The attach_ fields only exist because TRACK_CAUSALITY = ON. attach_activity_id.guid groups related events; attach_activity_id.seq orders them. On a busy server where several event sets interleave, that's how you tell which events belong together. Here, seq says this is the first.
  • plan_handle and sql_handle let you go and fetch the plan and text back out of cache if you need to.
  • object_name = Dynamic SQL, object_type — what the query is. For a stored procedure you'd see its name instead, which is how you reconstruct which proc was slow.

7 The session you'd actually deploy

Listing 15-1 was a teaching session: three showplan events, deliberately overdone to prove a point. Here's the real thing.

Rules for a lightweight session: run for a limited time, capture exactly what you need, and pick one showplan event — almost always query_post_execution_showplan. Then filter hard so the event rarely fires fully.

Listing 15-3 · plans plus waits for one procedure
CREATE EVENT SESSION ExecPlansAndWaits
ON SERVER
    ADD EVENT sqlos.wait_completed
    (WHERE (   (sqlserver.database_name = N'AdventureWorks2014')
               AND (sqlserver.like_i_sql_unicode_string(sqlserver.sql_text,
                      N'%ProductTransferByReference%')))),
    ADD EVENT sqlserver.query_post_execution_showplan
    (WHERE (   (sqlserver.database_name = N'AdventureWorks2014')
               AND (sqlserver.like_i_sql_unicode_string(sqlserver.sql_text,
                      N'%ProductTransferByReference%')))),
    ADD EVENT sqlserver.rpc_completed
    (WHERE (   (sqlserver.database_name = N'AdventureWorks2014')
               AND (sqlserver.like_i_sql_unicode_string(sqlserver.sql_text,
                      N'%ProductTransferByReference%')))),
    ADD EVENT sqlserver.rpc_starting
    (WHERE (   (sqlserver.database_name = N'AdventureWorks2014')
               AND (sqlserver.like_i_sql_unicode_string(sqlserver.sql_text,
                      N'%ProductTransferByReference%'))))
    ADD TARGET package0.event_file
    (SET filename = N'C:\PerfData\ExecPlansAndWaits.xel')
WITH (TRACK_CAUSALITY = ON)
GO

Four events, one story, all filtered to one procedure:

rpc_startingThe procedure starts — including parameter values.
wait_completedEach wait as it finishes, so you can see where the time went.
rpc_completedThe procedure finishes, with its metrics.
post_execution_showplanThe plan, with runtime counters.

With causality tracking on, you can order all of it: procedure started with these parameters, waited on this, then that, in this order, and here's the plan. That's essentially everything needed to troubleshoot one specific query — start it on production, capture a few minutes, stop it.

Waits are the part people forget A plan tells you how the work was done. wait_completed tells you what it was waiting on — the thing a plan can never show you. Pairing the two is the whole reason to automate.

8 SQL Trace, for when you have no choice

Deprecated, expensive, and inefficient at filtering. Included because you may still meet it — and because knowing why it's bad clarifies why Extended Events is designed the way it is.

Never capture event data with the Profiler GUI Use Profiler to define the trace and script it out, then run it as a server-side trace writing to a file. The GUI's caching mechanism can have a profoundly negative effect on the server you're trying to diagnose.
Trace eventEquivalent / behaviourVerdict
Showplan XMLFires on each execution; compile-time plan. Like query_pre_execution_showplan.The preferable one if you must minimise impact.
Showplan XML for Query CompileOnly on compilation. Like query_post_compilation_showplan.Useful, narrower.
Performance StatisticsTraces when plans are added to or removed from cache.Different job; not a plan.
Showplan XML Statistics ProfileActual plan, after execution.The one you'd most want — and the most expensive to capture.

And the reason filtering doesn't save you: even filtered on database and SQL text, the event still fires fully for every database and every text, and the filter is only applied when the trace consumer reads it. Add the global fields collected by default, whether you want them or not, and short runs become mandatory rather than advisable.

9 Cheat sheet

The decisions, in the order you'd make them.

DecisionAnswer
Which tool?Extended Events on 2012+ / Azure SQL DB. SQL Trace only on 2005–2008R2.
Which plan event?query_post_execution_showplan — the only one with runtime metrics. query_post_compilation_showplan if you specifically want compiles. query_pre_execution_showplan when studying recompiles.
How many plan events?One. Listing 15-1's three-event session is a demo, not a pattern.
How to limit the data?Predicates on sqlserver.database_name and sqlserver.sql_text (like_i_sql_unicode_string). The event doesn't fire fully unless they match.
What else to add?rpc_starting/rpc_completed for parameters and duration; sqlos.wait_completed for where the time went; sql_statement_recompile for recompile causes.
Where to write it?package0.event_file — flat file, best performing, most common target.
Causality tracking?On, if you're collecting several event types and need to group and order them.
How long?Minutes. Then stop it. Test it off-production first.
  • The problem the chapter solves is aggregation: cache and Query Store hide a bad five minutes inside a lifetime average.
  • Capturing plans is in-process and expensive — same thread as the query, big payloads. Filter hard, run briefly.
  • Pre-execution events have no runtime stats. Nothing to report yet — not a bug.
  • Extended Events filters before firing; Trace filters after. That single sentence explains the whole performance gap.
  • A captured plan has no SELECT operator and may be missing first-operator properties. Read the XML, not the picture.
  • Causality gives you a story: attach_activity_id.guid groups, .seq orders.
  • Network capture > GUI capture. Both tools: define it, script it, run it server-side.
The chapter's summary, condensed Automating capture reaches plans that cache queries and Query Store settings can't give you — and it lets you correlate the plan with the events around it (waits, recompiles, parameters). Use Extended Events rather than Trace. But "low overhead" is not "no overhead": filter precisely, capture briefly, and test before pointing it at production.
