Chapter 12

Batch Mode Processing

Chapter 11's plans pass rows one at a time. Batch mode passes them roughly 900 at a time — and the difference in overhead is the whole story. How to tell the two apart in a plan, when batch mode simply isn't available, and why a query can quietly fix its own memory grant.

1 What batch mode actually saves

Not CPU per row. Negotiation — the back-and-forth by which one operator asks another for the next row.

In row mode — how everything else in the book works — an operator asks the one below it for a row, does its work, passes that one row on, and asks again. A blocking operator asks for every input row one at a time, then hands out its results one at a time. That constant request negotiation is a costly operation, and it gets worse the more rows you move.

Row mode9,000 rows between two operators = 9,000 negotiations. Each one is cheap; there are just a lot of them.
Batch mode9,000 rows in 900-row batches = 10 negotiations. Same data, three orders of magnitude less chatter.
900 is guidance, not a constant Batch size depends largely on the number and size of the columns being passed through the query, so you'll see batches smaller than 900. The book has never observed one larger than 900, but there's no evidence 900 is a hard ceiling either — and behaviour varies by version.

Two preconditions matter, and both are moving targets. Batch mode currently requires a table with a columnstore index somewhere in the query, and — since SQL Server 2016 — it works in serial plans as well as parallel ones (before that, it required parallelism; more below). Microsoft has announced batch mode for rowstore tables too, so expect the rules to keep loosening.

2 Setting up, and spotting batch mode in a plan

Two properties answer the whole question — and they're the same two you'll use to catch a plan that fell back from batch to row mid-flight.

Listing 12-1 · a columnstore index on a genuinely large table
CREATE NONCLUSTERED COLUMNSTORE INDEX TransactionHistoryCS
ON dbo.bigTransactionHistory
(
    ProductID,
    TransactionDate,
    Quantity,
    ActualCost,
    TransactionID
);
dbo.bigTransactionHistory comes from a script by Adam Machanic that builds large test tables inside AdventureWorks — the book links to it, and you'll need something on that scale to see batch mode behave realistically.
Listing 12-2 · the analysis query
SELECT th.ProductID,
       AVG(th.ActualCost),
       MAX(th.ActualCost),
       MIN(th.ActualCost)
FROM dbo.bigTransactionHistory AS th
GROUP BY th.ProductID;

That last number is aggregate pushdown from Chapter 8 doing its work across 31+ million rows: the scan compresses away some of the aggregation and injects the results directly into the Hash Match's output rather than passing them through the arrow.

The single most useful check Compare Actual Execution Mode with Estimated Execution Mode on the columnstore scan. Batch/Batch is what you want. Batch estimated with Row actual means the plan was built for batch mode and fell back at runtime — which, per Chapter 8, is a SQL Server 2012 problem when a batch-mode hash operation spills to tempdb, and is catastrophic for performance.

3 Batch mode before SQL Server 2016

The rule that used to make batch mode hard to reach: it required a parallel plan. Drop the compatibility level and watch the plan change shape.

Listing 12-3 · back to SQL Server 2014 behaviour
ALTER DATABASE AdventureWorks2014
SET COMPATIBILITY_LEVEL = 120;

Why? Because before 2016 batch mode required a parallel plan, so the serial plan couldn't use batch mode at all. Without batch mode the serial version cost too much — enough to cross the cost threshold — so the optimizer went parallel to get at the faster processing model.

Prove it with a hint Add OPTION (MAXDOP 1) to Listing 12-2 and capture the actual plan: the serial plan's cost comes out around 150, and the optimizer stops choosing the columnstore index entirely, because using it in a serial plan is estimated even higher (about 200). Force it back with an INDEX() hint (Chapter 10) to see that for yourself. Same query, same data — a completely different decision, because a processing mode wasn't available.
Listing 12-4 · the undocumented escape hatch
SELECT th.ProductID,
       AVG(th.ActualCost),
       MAX(th.ActualCost),
       MIN(th.ActualCost)
FROM dbo.bigTransactionHistory AS th
GROUP BY th.ProductID
OPTION(QUERYTRACEON 8649);
Trace flag 8649 artificially lowers the cost threshold for parallelism to zero, so everything runs parallel — and therefore gets batch mode on 2012/2014. Undocumented. The supported alternative is to lower the cost threshold; the sensible alternative is to be on a newer version.
Listing 12-5 · back to 140
ALTER DATABASE AdventureWorks2014
SET COMPATIBILITY_LEVEL = 140;
Remember that changing compatibility level can change costs as well as features — both the optimizer's available options and the cardinality estimation engine differ between levels.

4 Mixing columnstore and rowstore

One row-mode operator and four batch-mode ones, in a single plan — and the tell-tale pair of aggregations that means "local, then global".

The rule in one sentence Batch mode isn't about the index you're reading from — it's about whether at least one table in the query has a columnstore index, even an unhelpful one. Meet that, and individual operators run in batch mode wherever they support it, in a plan that mixes both modes freely.
Listing 12-6 · join a columnstore table to a rowstore table
SELECT bp.Name,
       AVG(th.ActualCost),
       MAX(th.ActualCost),
       MIN(th.ActualCost)
FROM dbo.bigTransactionHistory AS th
    JOIN dbo.bigProduct AS bp
        ON bp.ProductID = th.ProductID
GROUP BY bp.Name;

The plan looks over-engineered for one GROUP BY, and the reason is aggregation being split in two. The scan does some of the work itself (aggregate pushdown, cutting about 1.5 million rows), and the Hash Match does the rest — but only locally, on ProductID.

That choice is deliberate. Aggregating on ProductID first cuts roughly 30 million rows down to 25,200 — the number of distinct ProductIDs — before the join even happens. Only then does the plan join to bigProduct to pick up Name, sort by it, and let a Stream Aggregate produce the final global values.

Batch mode hereColumnstore Index Scan · Hash Match (Aggregate) · Adaptive Join · Sort. These operators understand batches.
Row mode hereClustered Index Scan on bigProduct · Stream Aggregate. Row mode isn't a downgrade — it's the only option for these operators.

The Adaptive Join (Chapter 4) is worth a second look: its actual join type was Hash Match, with the Clustered Index Scan as the lower input, because the row count exceeded the Adaptive Threshold Rows property. It made that decision during execution, not during compilation — which is the whole point of an adaptive operator.

5 Adaptive memory grants

A query that over-estimates by 25×, asks for 80 MB, uses 3 MB — and then fixes itself on the next execution without recompiling.

Listing 12-7 · the procedure
CREATE OR ALTER PROCEDURE dbo.CostCheck (@Cost MONEY)
AS
SELECT p.Name,
       AVG(th.Quantity)
FROM dbo.bigTransactionHistory AS th
    JOIN dbo.bigProduct AS p
        ON p.ProductID = th.ProductID
WHERE th.ActualCost = @Cost
GROUP BY p.Name;
Listing 12-8 · first execution
EXEC dbo.CostCheck @Cost = 0;

The chain of over-estimation is worth following, because each step feeds the next:

  • The columnstore scan estimated 12.3 million rows; the actual was 10.8 million.
  • The Hash Match estimated its output at 25,200 rows from the sampled statistics; it produced about 10,000.
  • The Hash Match (Aggregate) uses a hash table optimised for aggregation — it holds GROUP BY values and intermediate results, not the input rows — so its grant is based on rows produced, not read.
  • And because the Adaptive Join's build phase overlaps with the Hash Match, its grant is added on top, along with the Sort's.

Net result: 80,840 KB requested, 3,192 KB used. The book is honest that these particular over-estimates don't fully explain a grant quite that large — SQL Server deliberately allows a generous margin to avoid spills.

Listing 12-9 · second execution, different value
EXEC dbo.CostCheck @Cost = 15.035;

This is adaptive memory grants, available from SQL Server 2017 and in Azure SQL Database: the engine adjusts the grant up or down on subsequent executions, based on what previous executions actually needed. Since 2016's columnstore plans can be serial, this is another case where the chapter's two topics — batch mode and parallelism — keep overlapping.

It switches itself off A query with wildly varied allocations could thrash — so at some point adaptive memory is disabled per plan, automatically. It stays on for other plans, and is re-enabled whenever that plan is recompiled. You can't see the disabled state in a single plan; you need Extended Events. A practical test: compare memory allocation values across consecutive executions — if they never change even while the query spills or over-allocates badly, adaptive memory is off.

6 Losing batch mode

The list of constructs that used to break it — and the reason SQL Server 2017 rarely lets it go.

SQL Server 2017 has "a very heavy bias" towards batch mode for any query touching a columnstore index, for all or at least part of the plan. On SQL Server 2014 or 2016, these operations would not run in batch mode:

ConstructEffect on 2014 / 2016Chapter
UNION ALLThat part of the plan drops to row modeCh. 5 / 10
OUTER JOINRow mode for the joinCh. 4
IN / EXISTS, including NOT versionsRow mode for the semi/anti joinCh. 4
OR in a WHERERow modeCh. 3
Aggregation without GROUP BYRow modeCh. 5
OVER()Row mode for the window aggregateCh. 5

On 2017 the book tested each of these and found the plan went to batch mode in whole or in part every time. But the method doesn't change: read the actual plan and check each operator's execution mode. That's the only reliable answer, on any version.

  • Batch mode saves negotiation, not arithmetic. 9,000 rows in 10 batches instead of 9,000 requests.
  • The requirement is "a columnstore somewhere", not "read from the columnstore". One qualifying table enables batch mode across the plan.
  • Before 2016, batch mode needed a parallel plan — which is why the same query changed shape at compatibility level 120.
  • Two aggregation operators are usually local-then-global. Look for partialagg and the local hash key.
  • An excessive grant is a symptom, not a cause. Follow the estimate chain — scan estimate → aggregate output estimate → join and sort grants.
  • Adaptive memory can hide a bad estimate by correcting it on the second execution. Don't mistake "no warning now" for "the estimate was fine".
The chapter's summary, condensed Batch mode moves large groups of rows at once instead of one at a time, and unlocks optimisations that exist only in that mode. Today it needs a columnstore index and, on older versions, a parallel plan and only a handful of capable operators. For large data sets the benefits are huge — but point lookups and narrow range scans are still better served by row mode.
