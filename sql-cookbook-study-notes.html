The short version

Chapter 1 in plain English

Every recipe in this chapter is a variation of one question: “give me some of the data in a table.” You pick which table, which rows, which columns, and what to call the answers. That’s it. Everything else in the chapter is a small tool for doing one of those four things more precisely.

🎯

Pick the rows you care about

WHERE acts as a filter. A row survives only if the condition is true for it. Use AND, OR and brackets to combine conditions.

🧱

Pick the columns you need

Name columns instead of using * when you write real code: less data over the network, and the query still makes sense to whoever reads it next.

🏷️

Label the output

An AS alias turns SAL into SALARY. Readable results are part of the job, not decoration.

🔀

Reshape what comes back

Glue columns together, choose a value with CASE, and swap NULL for something real with COALESCE.

✂️

Take just a few rows

Need a sample? Cap the result with LIMIT, TOP, FETCH FIRST or ROWNUM — and shuffle first with a random sort.

🔍

Match text loosely

LIKE '%ER' means “ends with ER”. % stands for any run of characters; _ stands for exactly one.

The one thing to remember SQL is written in one order and evaluated in another. You type SELECT … FROM … WHERE, but the database starts with FROM, then filters with WHERE, and only then works out the SELECT list. That single fact explains recipe 1.6 — why you can’t use a column alias inside WHERE.

Mental model

The shape of every query in this chapter

Ingredients first, then the filter, then the output list. Keep this picture in your head and the fourteen recipes stop looking like fourteen separate things.

SQL · the skeleton 
select <columns you want>      -- 1. what to show
  from <table>                  -- 2. where the data lives
 where <condition on rows>      -- 3. which rows survive
 order by <sort key>;           -- 4. in what order (chapter 2)

But the database runs it in this order

FROMgrab the table
→
WHEREthrow rows away
→
SELECTbuild the output columns
(aliases are born here)
→
ORDER BYsort the survivors
Because of that order A WHERE clause can’t see a SELECT alias — the alias doesn’t exist yet when the filter runs. Recipe 1.6 shows the standard workaround: wrap the query in an inline view so the alias exists before the outer filter.

1.1

Retrieving all rows and all columns

In plain English You want to dump the whole table. The star * means “every column”, and because there’s no WHERE, every row comes back too.

SQL · all rows, all columns 
select *
  from emp

The honest alternative — spell out the columns:

SQL · explicit column list 
select empno,ename,job,sal,mgr,hiredate,comm,deptno
  from emp
The book’s advice SELECT * is fine for quick, one-off exploring. Inside application code, list the columns. Performance is identical, but a named list is self-documenting, and if a column disappears you get a clear error instead of a program quietly receiving a different shape of data.

1.3

Finding rows that satisfy multiple conditions

In plain English Stack conditions with OR (any of them) and AND (all of them). Brackets decide the grouping — and moving them changes which rows come back, as this recipe demonstrates.

The book’s query: department 10, or anyone earning commission, or someone in department 20 on $2,000 or less.

SQL · OR / AND 
select *
  from emp
 where deptno = 10
    or comm is not null
    or sal <= 2000 and deptno=20

Now move the brackets

Wrapping the first three conditions in brackets, then demanding deptno = 20, changes the meaning to “anyone in department 20 who is also (in dept 10 — impossible — or on commission, or paid $2,000 or less)”.

SQL · the same conditions, regrouped 
select *
  from emp
 where (     deptno = 10
         or comm is not null
         or sal <= 2000
       )
   and deptno=20

1.6

Referencing an aliased column in the WHERE clause

In plain English You gave a column a nice alias, then tried to filter on it — and it failed. Not a typo: the alias doesn’t exist yet when WHERE runs. The fix is to wrap the query in an inline view (a subquery in the FROM clause) so the alias is created first.

This fails — salary isn’t defined at filter time:

SQL · invalid 
select sal as salary, comm as commission
  from emp
 where salary < 5000

This works — the outer query filters on a column the inner query already named:

SQL · inline view 
select *
  from (
select sal as salary, comm as commission
  from emp
       ) x
 where salary < 5000
Why this recipe matters more than it looks The same trick is what lets you filter on aggregates (e.g. sum(sal)), scalar subqueries and window functions. The alias is just the simplest case. The inline view is aliased x — not every database insists on a name there, but every one accepts it.

1.9

Limiting the number of rows returned

In plain English “Just give me the first five rows — I don’t care which.” Here the databases really do disagree, so the book lists all four spellings.

SQL · FETCH FIRST 
select *
  from emp fetch first 5 rows only
SQL · LIMIT 
select *
  from emp limit 5
SQL · ROWNUM 
select *
  from emp
 where rownum <= 5
SQL · TOP 
select top 5 *
  from emp

Why ROWNUM = 5 never returns a row

Oracle numbers a row as it is fetched, starting at 1. Asking for rownum = 5 means: “hand me a row only if it is the fifth one” — but the first row offered is numbered 1, so it is discarded, the next is also numbered 1 (because nothing has been returned yet), and so on. The filter can never be satisfied. Use <=, never =.

The one exception rownum = 1 does work — Oracle has to fetch at least one row to find out whether the table is empty, so row 1 is available to satisfy the test.
1.10

Returning n random records

In plain English Two moves combined: sort by a random value (so the order is different every time), then take the first n. That’s recipe 1.9 plus a random sort.

  from emp

SQL · rand() + limit 
select ename,job
  from emp

SQL · random() + limit 
select ename,job
  from emp
 order by random() limit 5

Book’s warning Don’t confuse a function in ORDER BY with a number. order by 2 means “sort by the second column in the select list”; order by random() means “sort by this value, computed fresh for each row”.
1.11

Finding NULL values

In plain English NULL means “unknown / no value”. It isn’t equal to anything — not even to another NULL — so = null and != null both quietly fail. You must use IS NULL.

SQL · IS NULL 
select *
  from emp
 where comm is null

And the opposite, for rows that do have a commission:

SQL · IS NOT NULL 
select *
  from emp
 where comm is not null
1.12

Transforming NULLs into real values

In plain English Blanks are ugly in reports and dangerous in arithmetic (1 + NULL is NULL). COALESCE returns the first non-null value it is given — so coalesce(comm,0) means “commission, or 0 if there isn’t one”.

SQL · COALESCE 
select coalesce(comm,0)
  from emp

The same idea written the long way with CASE — works everywhere too, just noisier:

SQL · CASE alternative 
select case
       when comm is not null then comm
       else 0
       end
  from emp
Portability note COALESCE is part of standard SQL and works in every database the book covers, so it’s the safe default. Some databases also offer NVL, IFNULL or ISNULL — same job, less portable.
1.13

Searching for patterns

In plain English LIKE is “contains / starts with / ends with”. % stands for any number of characters (including none) and _ stands for exactly one. So '%I%' = contains an “I” anywhere, and '%ER' = ends in “ER”.

1.14

Summing up

In plain English The book closes the chapter with this thought: these recipes look simple, but they are fundamental. Getting records out of a table is the core of querying — every harder recipe later in the book is built on top of SELECT, WHERE and a handful of expressions.

Which is why it is worth being deliberate about the small decisions now: naming columns instead of starring them, bracketing conditions, using IS NULL instead of = null, and reaching for CASE and COALESCE when a value needs interpreting.

Chapter 2 · book pages 15–28

Sorting Query Results

Chapter 1 got the right rows out of the table. Chapter 2 decides what order they come back in — which is, for anyone reading the result, half the meaning. All of it runs through one clause: ORDER BY.

The short version

Chapter 2 in plain English

ORDER BY takes the rows your WHERE clause left behind and puts them in sequence. You can sort on a column, on several columns, on a piece of a column, on a CASE expression, or on nothing more elaborate than a flag that tells the database where the NULLs belong. Six recipes, one clause.

⬆️

ASC / DESC sets direction

Ascending is the default, so asc is optional. Add desc to flip a column — per column, not per query.

🪜

More columns = tie-breakers

order by deptno, sal desc sorts by department first, and only within a department does salary matter.

🧩

You can sort on an expression

ORDER BY accepts any value: a substring, a function call, a CASE. Whatever it returns is the sort key.

🕳️

NULLs need a decision

Every database has a default for where NULL goes — and they disagree. If the position matters, say so explicitly.

🔢

Position beats typing

order by 3 means “the third column in the select list”. Short, but silently wrong the moment you edit that list.

🪄

Sort keys can be conditional

Sort salespeople by commission and everyone else by salary — one CASE in the ORDER BY does both at once.

The mirror image of recipe 1.6 In Chapter 1 an alias couldn’t be used in WHERE, because the filter runs before the select list is built. ORDER BY runs after it — so here the alias is fair game. Same rule, opposite consequence: clauses can only see what has already been computed.

Returning query results in a specified order

2.3

Sorting by substrings

In plain English Sort by part of a value rather than the whole thing. The book wants the last two characters of JOB: find the string’s length, subtract two, and take everything from there to the end — substr(job, length(job)-1).

SQL · SUBSTR 
select ename,job
  from emp
 order by substr(job,length(job)-1)
SQL · SUBSTRING 
select ename,job
  from emp
 order by substring(job,len(job)-1,2)

2.4

Sorting mixed alphanumeric data

In plain English One column holds letters and numbers glued together, like SMITH 20. Sort it as-is and you sort by the letters. To sort by the number you have to strip the letters out first — and to sort by the letters, strip the digits. TRANSLATE plus REPLACE is how the book does it.

The book builds a view that deliberately mixes the two:

SQL · the mixed column 
create view V
as
select ename||' '||deptno as data
  from emp

select * from V

How the two expressions work

ExpressionWhat it doesResult for SMITH 20

Sort by the number (DEPTNO):

SQL · ORDER BY DEPTNO 
/* ORDER BY DEPTNO */
select data
  from V

SQL · ORDER BY ENAME 
/* ORDER BY ENAME */
select data

2.5

Dealing with NULLs when sorting

In plain English COMM is empty for most employees. Where should those blanks land — first or last? Every database has a default and they don’t agree, so if the position matters you have to say it. The portable trick: compute a little flag (0 = is null, 1 = isn’t), sort by the flag, then by the real value.

SQL · the flag, then the value 
select ename,sal,comm
  from (
select ename,sal,comm,
       case when comm is null then 0 else 1 end as is_null
  from emp
       ) x
 order by is_null desc,comm

2.7

Summing up

In plain English Sorting is a core skill, and ORDER BY is more capable than it looks — but it needs care: collation, ties, NULL placement and positional references all have sharp edges. The book closes by noting that many later recipes depend on getting this right.

Working with Multiple Tables

Real data lives in several tables at once. This chapter is the hinge of the whole book: joins put tables side by side, set operations stack them on top of each other — and most of the difficulty is in the rows that don’t match.

The short version

Chapter 3 in plain English

Two ways to combine tables, and twelve recipes that use them. Joins go sideways — you get more columns. Set operations go downwards — you get more rows. Once you can picture a join as “a Cartesian product with a filter”, the whole chapter stops being a list of syntaxes.

🧱

Stacking rows: UNION ALL

Put one result on top of another. Columns must match in number and type. UNION also removes duplicates — and usually pays for it with a sort.

🔗

Joining rows: the equi-join

Match rows where a column in one table equals a column in the other. That’s the everyday join, and it’s just a WHERE condition.

🧲

Keep the unmatched: outer join

A LEFT JOIN keeps every row on the left even when there’s no match. That’s how departments with no employees survive.

🕵️

Find the missing: anti-join

LEFT JOIN … WHERE right.key IS NULL is the standard way to ask “which rows have no partner?”

⚠️

Joins duplicate rows

Two bonuses for one employee means that employee’s salary counts twice in a SUM. Aggregate with care.

🕳️

NULLs break NOT IN

One NULL in the subquery and NOT IN returns nothing at all. NOT EXISTS doesn’t have that problem.

In plain English You need rows that exist in both sources. Two ways: join on every column that identifies a row, or use the set operation INTERSECT — which keeps only the rows that appear on both sides.

3.4

Values in one table that don’t exist in another

In plain English Set difference: which department numbers are in DEPT but never appear in EMP? Answer: 40. Most databases have an operator for this (EXCEPT, or MINUS in Oracle); MySQL needs a subquery — and that subquery hides a NULL trap.

select deptno from dept

select deptno
  from dept
 where deptno not in (select deptno from emp)

The NULL trap in NOT IN

Add one NULL to the inner list and NOT IN silently returns nothing. The book proves it with truth tables: NOT IN is really a chain of ORs, and in SQL TRUE OR NULL is TRUE, but FALSE OR NULL is NULL. Rows that fail every comparison end up NULL — not TRUE — so they’re filtered out.

The safe answer, immune to NULLs and usually faster — a correlated NOT EXISTS:

SQL · NOT EXISTS 
select d.deptno
  from dept d
 where not exists (
   select 1
     from emp e
    where d.deptno = e.deptno
)
Why select 1? With EXISTS / NOT EXISTS the select list is irrelevant — only “are there any rows?” matters. The book selects NULL on purpose, to stop you looking at the wrong thing.
3.5

SQL · anti-join 
select d.*
  from dept d left outer join emp e
    on (d.deptno = e.deptno)
 where e.deptno is null

3.6

Adding joins without interfering with other joins

In plain English Your query works. You want one more column from another table — but a plain join to it drops rows, because not every employee has a bonus. Fix: make the new join an outer join, or fetch the value with a scalar subquery and leave the existing joins untouched.

EMP_BONUS holds three rows — so an inner join returns three employees instead of fourteen:

SQL · left join 
select e.ename, d.loc, eb.received
  from emp e join dept d
    on (e.deptno=d.deptno)
  left join emp_bonus eb
    on (e.empno=eb.empno)
 order by 2

select e.ename, d.loc,
       (select eb.received from emp_bonus eb
         where eb.empno=e.empno) as received
  from emp e, dept d
 where e.deptno=d.deptno
 order by 2
The scalar subquery’s condition A subquery in the SELECT list must return exactly one value per row. If it can return two rows (e.g. an employee with several bonuses), the query errors. That’s the price of the convenience.
3.7

3.8

Identifying and avoiding Cartesian products

In plain English Forgot the join condition? Then every row pairs with every row — three employees × four departments = twelve rows, three of them fiction. The fix is one more line in the WHERE clause.

SQL · wrong 
select e.ename, d.loc
  from emp e, dept d
 where e.deptno = 10

select e.ename, d.loc
  from emp e, dept d
 where e.deptno = 10
   and d.deptno = e.deptno
Cartesian products aren’t always evil The book notes they’re the standard tool for pivoting/unpivoting a result set, generating a sequence of numbers, and mimicking a loop. Accidental ones are the problem.

3.11

Returning missing data from multiple tables

In plain English Department 40 has no employees; employee YODA has no department. A LEFT JOIN keeps one of them, a RIGHT JOIN keeps the other. Only a full outer join keeps both — all the unmatched rows from each side.

SQL · FULL OUTER JOIN 
select d.deptno,d.dname,e.ename
  from dept d full outer join emp e
    on (d.deptno=e.deptno)

select d.deptno,d.dname,e.ename
  from dept d right outer join emp e
    on (d.deptno=e.deptno)

  from dept d left outer join emp e
    on (d.deptno=e.deptno)

Chapter 4 · book pages 67–89

Inserting, Updating, and Deleting

The first three chapters only ever read. This one changes the data: INSERT adds rows, UPDATE rewrites them, DELETE removes them — and every one of those statements is one careless WHERE away from touching the whole table.

The short version

Chapter 4 in plain English

Three statements, one question between them: which rows? For INSERT the question is “which columns am I filling, and with what”. For UPDATE and DELETE it is literally “which rows does my WHERE clause select” — no WHERE means every row. MERGE combines all three into one statement for syncing tables.

➕

INSERT … VALUES

Add one row — or several at once, on most engines, by listing multiple VALUES tuples.

📋

INSERT … SELECT

Copy rows from one table into another. Any query works, so you can copy a filtered subset — or the whole table.

🎚️

Default ≠ NULL

Leave a column out and it takes its default. To actually get NULL, you must say NULL.

✏️

UPDATE … SET … WHERE

The SET clause says what the new value is; the WHERE clause says who gets it. Test the WHERE with a SELECT first.

🗑️

DELETE FROM … WHERE

Same logic, opposite verb. DELETE without WHERE empties the table; TRUNCATE is faster but differs on rollback.

🔀

MERGE = upsert

Update when the row exists, insert when it doesn’t, delete when a condition fails — all in one pass. Built for syncing an external feed.

The habit that saves you Before running an UPDATE or DELETE, run the same WHERE clause as a SELECT and look at the rows. A typo in deptno = 10 is a one-character edit away from deptno = 20, and the statement you just ran is the one with no undo button.

4.1

Inserting a new record

In plain English INSERT INTO table (columns) VALUES (values). Name the columns and the values line up one-for-one. Most databases also let you insert several rows in a single statement.

4.2

Inserting default values

In plain English A column can be declared with a default. You can ask for that default explicitly with the DEFAULT keyword — useful when you don’t know (or don’t want to repeat) what the default actually is.

4.3

Overriding a default value with NULL

In plain English Counter-intuitive but true: omitting a column does not give you NULL — it gives you the default. If the default is 0, leaving ID out stores 0. To store a real NULL, write NULL.

SQL · explicit NULL beats the default 
insert into d (id, foo) values (null, 'Brighten')

Unless a constraint says otherwise A NOT NULL constraint on the column will reject the explicit NULL — which is the point of the constraint.
4.4

Copying rows from one table into another

In plain English INSERT INTO … SELECT … — the source of the new rows is a query, so you can copy everything or just the rows you want. Here: copy the departments in New York and Boston.

  from dept
 where loc in ( 'NEW YORK','BOSTON' )

Drop the WHERE to copy every row. The same rules about column lists apply: name them, or supply all of them in the right order.

4.5

Copying a table definition

In plain English You want the shape of a table without its rows. The trick everywhere except DB2: create the table from a query, with a condition that is always false — where 1 = 0 — so the columns get built and no data comes along.

  from dept

create table dept_2 like dept

  into dept_2
  from dept
 where 1 = 0

Shape, not everything else These copy columns and types. Indexes, constraints, defaults and identity properties are — depending on the engine — usually not copied. Check the result before you rely on it.
4.6

Inserting into multiple tables at once

In plain English One query, several destinations: send each row wherever it belongs. Oracle does this natively with INSERT ALL; DB2 fakes it by inserting into a view that unions the target tables. MySQL, PostgreSQL and SQL Server have no such statement.

SQL · INSERT ALL 
insert all
  when loc in ('NEW YORK','BOSTON') then
  into dept_east (deptno,dname,loc) values (deptno,dname,loc)
  when loc = 'CHICAGO' then
    into dept_mid (deptno,dname,loc) values (deptno,dname,loc)
  else
    into dept_west (deptno,dname,loc) values (deptno,dname,loc)
  select deptno,dname,loc
    from dept
ALL vs FIRST INSERT FIRST stops at the first true condition — one destination per row. INSERT ALL evaluates every condition, so a single row can be written to several tables.
SQL · insert into a union view 
insert into (
  select * from dept_west union all
  select * from dept_east union all
  select * from dept_mid
) select * from dept

Each target table needs a check constraint matching its own region, so the engine can tell which table a row belongs in. If two tables accept the same rows, the statement fails — the book calls this “a bit of a hack”, and it is.

Not available At the time of writing, MySQL, PostgreSQL and SQL Server have no multitable insert. The portable equivalent is one INSERT … SELECT per target table, each with its own WHERE.
4.7

In plain English You want an application to add employees, but only to three columns. The answer is permissions, not SQL: expose a narrow view, grant insert rights on the view, and don’t grant them on the table.

SQL · a view as a write-only window 
create view new_emps as
select empno, ename, job
  from emp

Inserting into the view is translated into an insert on EMP behind the scenes — but only for the columns the view exposes:

SQL · insert through the view 
insert into new_emps
   (empno, ename, job)
   values (1, 'Jonathan', 'Editor')
Read your vendor’s rules Inserting through a view only works cleanly for simple views; joins, aggregates and expressions make it complicated fast. Oracle also allows inserting into an inline view (insert into (select …) values …), which other engines don’t.

   set sal=sal*1.20
 where empno in ( select empno from emp_bonus )

The EXISTS variant says the same thing — and on some engines it is the one that runs well:

SQL · WHERE EXISTS 
update emp
   set sal = sal*1.20
 where exists ( select null
                  from emp_bonus
                 where emp.empno=emp_bonus.empno )
Why NULL in the select list? With EXISTS only the presence of a row matters, never its values. Writing null makes that unmistakable — nothing here is used as a value, the WHERE inside the subquery decides everything.
4.10

Updating with values from another table

In plain English Take the values from a second table: NEW_SAL holds a new salary for department 10. Set EMP.SAL to it and EMP.COMM to half of it. Every engine has a different syntax — and one shared pitfall.

SQL · correlated subquery 
update emp e set (e.sal,e.comm) = (select ns.sal, ns.sal/2
                                     from new_sal ns
                                    where ns.deptno=e.deptno)
 where exists ( select *
                  from new_sal ns
                 where ns.deptno = e.deptno )
SQL · multi-table UPDATE 
update emp e, new_sal ns
set e.sal=ns.sal,
e.comm=ns.sal/2
where e.deptno=ns.deptno

Both tables in the UPDATE clause, the join in the WHERE. MySQL’s own syntax; not portable.

SQL · update an inline view 
update (
 select e.sal as emp_sal, e.comm as emp_comm,
        ns.sal as ns_sal, ns.sal/2 as ns_comm
   from emp e, new_sal ns
  where e.deptno = ns.deptno
) set emp_sal = ns_sal, emp_comm = ns_comm

Works only because NEW_SAL.DEPTNO is a primary key — the view is “key-preserved”, so Oracle knows which single row each update targets.

SQL · UPDATE … FROM 
update emp
   set sal = ns.sal,
       comm = ns.sal/2
  from new_sal ns
 where ns.deptno = emp.deptno
SQL · UPDATE alias … FROM 
update e
   set e.sal  = ns.sal,
       e.comm = ns.sal/2
   from emp e,
        new_sal ns
  where ns.deptno = e.deptno
The pitfall nobody expects A join written only in the SET clause is not a filter. The DB2-style correlated update matches department 10 — and sets SAL and COMM to NULL for departments 20 and 30, because their subquery found nothing. The EXISTS in the WHERE clause is what restricts the update to matching rows. Only a WHERE limits which rows an UPDATE touches.
4.11

Merging records

In plain English MERGE is insert-or-update in one statement — the standard “upsert”. The book’s example goes further: update a matched row, delete it if the update pushes it over a limit, and insert anything that wasn’t there.

SQL · MERGE 
merge into emp_commission ec
using (select * from emp) emp
   on (ec.empno=emp.empno)
 when matched then
      update set ec.comm = 1000
      delete where (sal < 2000)
 when not matched then
      insert (ec.empno,ec.ename,ec.deptno,ec.comm)
      values (emp.empno,emp.ename,emp.deptno,emp.comm)

Deleting all records from a table

In plain English DELETE FROM table with no WHERE removes every row but leaves the table itself in place.

4.13

Deleting specific records

In plain English Add a WHERE clause and the DELETE only touches the rows it selects. Everything hinges on that condition being right.

SQL · delete one department

A typo away deptno = 20 instead of 10 deletes the wrong department, and the command looks perfectly reasonable when you read it back. Run the WHERE clause as a SELECT first — every time.
4.14

Deleting a single record

In plain English Just 4.13 with a condition narrow enough to hit one row. Delete by primary key and you can be certain: the database won’t allow two rows with the same key.

SQL · delete by primary key

Any other criterion — a name, a date, a status — may match more than one row. If you’re not filtering on a unique key, check what you’re about to delete before you delete it.

4.15

Deleting referential integrity violations

In plain English Some employees point at departments that don’t exist — orphaned rows. Delete them by asking, for each employee, “does a matching department exist?” (NOT EXISTS) or “is this department number in the valid list?” (NOT IN).

SQL · NOT EXISTS 
delete from emp

   select * from dept
    where dept.deptno = emp.deptno

where deptno not in (select deptno from dept)

The short version

Chapter 5 in plain English

“What tables do I have? which columns are indexed? does this foreign key have an index?” — questions about your schema, not your data. Every engine answers them, but each names its catalogue differently, so this chapter is mostly a matter of knowing which system view to query.

5.5

Listing foreign keys without corresponding indexes

In plain English A foreign key makes the database enforce a relationship — but it doesn’t always create an index on the child column. This recipe finds foreign keys whose column has no index, which is a classic cause of slow joins and heavy locking.

The shape is identical in every dialect — and it’s the anti-join from recipe 3.5, wearing a catalogue hat:

SQL · the pattern (illustrative) 
select fkeys.table_name,
       fkeys.constraint_name,
       fkeys.column_name,
       ind_cols.index_name
  from ( /* the foreign-key columns, from the catalogue */ ) fkeys
       left join
       ( /* the indexed columns, from the catalogue */ ) ind_cols
    on ( fkeys.table_name  = ind_cols.table_name
     and fkeys.column_name = ind_cols.column_name )
 where ind_cols.index_name is null   -- <- keep only the unindexed ones
SQL · Oracle, with (+) outer joins 
select a.table_name,
       a.constraint_name,
       a.column_name,
       c.index_name
  from all_cons_columns a,
       all_constraints b,
       all_ind_columns c
 where a.table_name      = 'EMP'
   and a.owner           = 'SMEAGOL'
   and b.constraint_type = 'R'
   and a.owner           = b.owner
   and a.table_name      = b.table_name
   and a.constraint_name = b.constraint_name
   and a.owner           = c.table_owner (+)
   and a.table_name      = c.table_name (+)
   and a.column_name     = c.column_name (+)
   and c.index_name      is null
SQL · DB2, explicit LEFT JOIN 
select fkeys.tabname,
       fkeys.constname,
       fkeys.colname,
       ind_cols.indname
  from (
select a.tabschema, a.tabname, a.constname, b.colname
  from syscat.tabconst a,
       syscat.keycoluse b
 where a.tabname   = 'EMP'
   and a.tabschema = 'SMEAGOL'
   and a.type      = 'F'
   and a.tabname   = b.tabname
   and a.tabschema = b.tabschema
       ) fkeys
       left join
       (
select a.tabschema, a.tabname, a.indname, b.colname
  from syscat.indexes a,
       syscat.indexcoluse b
 where a.indschema = b.indschema
   and a.indname   = b.indname
       ) ind_cols
    on (fkeys.tabschema = ind_cols.tabschema
         and fkeys.tabname   = ind_cols.tabname
         and fkeys.colname   = ind_cols.colname )
 where ind_cols.indname is null

PostgreSQL follows the DB2 shape exactly: foreign keys come from key_column_usage + referential_constraints, indexed columns from pg_indexes + information_schema.columns, then left join … where ind_cols.indexname is null.

SQL Server does the same with sys.foreign_keys and sys.index_columns, joining on object_id and column_id rather than on names.

MySQL: compare by hand MySQL is the odd one out. It has no single query for this: run show index from emp and compare the result against information_schema.key_column_usage for the same table. A column listed in the latter but absent from the former is a foreign key with no index.
Why the book cares Parent-child relationships are enforced on the child column, and the child column is also what you join on. Without an index there, lookups scan — and, depending on the engine, updates to the parent take heavier locks than they need to.

Working with Strings

The longest chapter in the book, and the most practical: text arrives dirty, and SQL has to take it apart. Nearly every recipe here is built from five functions — SUBSTR, INSTR, REPLACE, TRANSLATE and LENGTH — plus the odd regular expression.

The short version

Chapter 6 in plain English

Two moves cover almost everything. Walk the string — join it to a numbers table so you get one row per character, then pick characters or slices out. Or swap characters out — TRANSLATE maps every letter to a marker, REPLACE deletes the markers, and what’s left is the part you wanted. The rest of the chapter is those two ideas wearing different hats.

🚶

Walking a string

Cartesian-join the value to a numbers table, filter pos <= length(str), and you have one row per character.

🔁

TRANSLATE + REPLACE

Map a class of characters to a single marker, delete the marker, and only the other class survives. This is the chapter’s workhorse.

✂️

SUBSTR + INSTR

Find a delimiter’s position, then slice between two positions. That’s how you take a string apart.

📋

Rows ⇄ delimited text

Aggregate rows into a,b,c; or split a,b,c back into rows. Both directions are recipes here.

🔤

Quotes are doubled

Inside a string literal, a quote is written twice: 'g''day'. Four quotes in a row is one quote character.

🧩

Positions are 1-based

Character 1 is the first character — everywhere in this chapter, and in SUBSTR, INSTR and STRING_SPLIT alike.

Two conventions to know before you read the code T10 and T100 are the book’s one-column helper tables holding the numbers 1–10 and 1–100. They are how you “loop” in SQL: join to them and you get N rows to walk N characters with. And TRANSLATE takes three arguments — the string, the characters to find, and the characters to put in their place; the last two must be the same length, which is why you see rpad('z',26,'z') everywhere.

6.1

Walking a string

In plain English You want to look at a string one character at a time. Join the string to a list of numbers, keep the numbers up to its length, and take the character at each position. That’s the whole trick — and the foundation for half the chapter.

SQL · one row per character 
select substr(e.ename,iter.pos,1) as C
  from (select ename from emp where ename = 'KING') e,
       (select id as pos from t10) iter
 where iter.pos <= length(e.ename)

Remove the WHERE and the join produces 10 rows for a 4-letter name — which is exactly why the filter is there:

The two-argument form substr(str, pos) returns everything from that position to the end — so as pos grows the string shrinks, and you can walk from either end by also using length(str) - pos + 1. That’s what the figure shows: KING → G, ING → NG, NG → ING, G → KING.
T10 caps you at ten Walking with T10 silently truncates anything longer than ten characters. Use T100 (or a recursive CTE) when the values can be longer.

In plain English Delete the character and see how much shorter the string got. The difference in length, divided by the length of the thing you removed, is the count.

6.6

Determining whether a string is alphanumeric

In plain English A row is “alphanumeric” if it contains only letters and digits — no commas, no $, no dots. The test: translate every letter and digit into a, then compare the result with a string of as of the same length. Equal means nothing unexpected survived.

SQL · Oracle / PostgreSQL (same idea in DB2, SQL Server) 
select data
  from V
 where translate(lower(data),
                 '0123456789abcdefghijklmnopqrstuvwxyz',
                  rpad('a',36,'a')) = rpad('a',length(data),'a')
SQL · MySQL, with a regular expression 
select data
  from V
 where data regexp '[^0-9a-zA-Z]' = 0

Worked through on the book’s view: CLARK → aaaaa (clean), SMITH, $800.00 → aaaaa, $aaa.aa (punctuation survived).

Why 36? Ten digits plus twenty-six letters. The replacement string must cover every character you’re mapping, and be at least as long as the find string on engines that pad short replacements with spaces.

Extracting initials from a name

6.8

Ordering by parts of a string

In plain English Sort by the last two characters of the name instead of the whole name. Same shape as recipe 2.3 — put a SUBSTR expression in the ORDER BY.

select ename
  from emp

6.9

Ordering by a number in a string

In plain English The data is CLARK 7782 ACCOUNTING — name, employee number and department in one string — and you want to sort by the number, not the text. Because '99' sorts after '100' as a string, you have to isolate the digits and cast them.

SQL · Oracle: three nested calls to isolate the digits 
select data
  from V
 order by
         to_number(
           replace(
         translate(data,
           replace(
         translate(data,'0123456789','##########'),
                  '#'),rpad('#',20,'#')),'#'))

Read it inside-out: digits become # → that # string is deleted from the original, leaving only letters → letters become # → delete those too → only digits remain → TO_NUMBER.

No MySQL solution At the time of writing MySQL had no TRANSLATE, so the book gives no MySQL answer for this recipe. DB2 and PostgreSQL use the same nesting with REPEAT/RPAD and a CAST.

6.11

Converting delimited data into a multivalued IN-list

In plain English Someone hands you '7654,7698,7782,7788' and you want where empno in (7654,7698,7782,7788) — four values, not one string. SQL has no built-in “split this”, so you walk the string and cut out each token.

SQL · DB2 
select empno,ename,sal,deptno
  from emp
 where empno in (
select cast(substr(c,2,locate(',',c,2)-2) as integer) empno
  from (
select substr(csv.emps,cast(iter.pos as integer)) as c
  from (select ','||'7654,7698,7782,7788'||',' emps
         from t1) csv,
       (select id as pos
          from t100 ) iter
 where iter.pos <= length(csv.emps)
       ) x
 where length(c) > 1
   and substr(c,1,1) = ','
       )

Why the leading and trailing comma? So that every token is bounded by a comma on both sides — then “the text after a comma up to the next comma” always works, including for the first and last token.

The short versions PostgreSQL: split_part(vals, ',', pos). MySQL: substring_index(substring_index(vals, ',', pos), ',', -1) — take the first n tokens, then take the last one. Oracle and SQL Server do the INSTR/CHARINDEX arithmetic by hand.
6.12

Alphabetizing a string

In plain English ADAMS → AADMS: take the string apart into characters, sort the characters, put them back together. Walking (6.1) and aggregating (6.10) combined — in that order.

SQL · MySQL 
select ename, group_concat(c order by c separator '')
  from (
select ename, substr(a.ename,iter.pos,1) c
  from emp a,
       ( select id pos from t10 ) iter
 where iter.pos <= length(a.ename)
       ) x
 group by ename

Split first (one row per character), then GROUP_CONCAT … ORDER BY c puts the letters back in alphabetical order.

SQL Server had no string_agg So the book builds the result with a PIVOT-style trick: max(case when pos=1 then c else '' end) + max(case when pos=2 ...) for each of six positions. It works because the names are at most six letters — which is exactly the kind of limit you want to know about before reusing it.
6.13

Identifying strings that can be treated as numbers

In plain English A column mixes CL10AR (letters with digits inside) and 7369 (a pure number). You want the numeric part of each, and for the pure numbers you want the whole value — not just a fragment of it.

SQL · Oracle 
select to_number (
        case
        when
           replace(translate(mixed,'0123456789','9999999999'),'9')
          is not null
        then
             replace(
           translate(mixed,
             replace(
           translate(mixed,'0123456789','9999999999'),'9'),
                    rpad('#',length(mixed),'#')),'#')
        else
             mixed
        end
        ) mixed
  from V
 where instr(translate(mixed,'0123456789','9999999999'),'9') > 0

The CASE is the interesting part: if removing the digits leaves nothing, the value is already a pure number, so return it as-is. Otherwise, strip everything that isn’t a digit.

MySQL does it differently It walks the string, keeps only characters whose ASCII code is between 48 and 57 (that is, 0–9), re-aggregates them with GROUP_CONCAT and casts to UNSIGNED. Same result, no TRANSLATE required.
6.14

Extracting the nth delimited substring

In plain English From mo,larry,curly you want the second value: larry. From a five-item list you want gina. Same position, different row — so the solution has to know where the delimiters are, not just how many there are.

SQL · MySQL, two substring_index calls 
select name
  from (
select iter.pos,
       substring_index(
       substring_index(src.name,',',iter.pos),',',-1) name
  from V src,
       (select id pos from t10) iter
 where iter.pos <=
       length(src.name)-length(replace(src.name,',',''))
       ) x
 where pos = 2

The inner call takes the first pos tokens; the outer one with -1 takes the last of those — which is the token you wanted.

PostgreSQL and SQL Server PostgreSQL is a one-liner with split_part(name, ',', 2). Modern SQL Server has STRING_SPLIT, which turns the whole column into rows. Oracle and DB2 walk the string with INSTR/LOCATE and a ROW_NUMBER() to pick the nth delimiter.
6.15

Parsing an IP address

In plain English 92.111.0.2 → four columns, split on the dots. Whether this is two lines or forty depends entirely on whether your database has a split function.

SQL · split_part 
select split_part(y.ip,'.',1) as a,
       split_part(y.ip,'.',2) as b,
       split_part(y.ip,'.',3) as c,
       split_part(y.ip,'.',4) as d
  from (select cast('92.111.0.2' as text) as ip from t1) as y
SQL · nested SUBSTRING_INDEX 
select substring_index(substring_index(y.ip,'.',1),'.',-1) a,
       substring_index(substring_index(y.ip,'.',2),'.',-1) b,
       substring_index(substring_index(y.ip,'.',3),'.',-1) c,
       substring_index(substring_index(y.ip,'.',4),'.',-1) d
  from (select '92.111.0.2' as ip from t1) y
SQL · SUBSTR + INSTR arithmetic 
select ip,
       substr(ip, 1, instr(ip,'.')-1 ) a,
       substr(ip, instr(ip,'.')+1,
                   instr(ip,'.',1,2)-instr(ip,'.')-1 ) b,
       substr(ip, instr(ip,'.',1,2)+1,
                   instr(ip,'.',1,3)-instr(ip,'.',1,2)-1 ) c,
       substr(ip, instr(ip,'.',1,3)+1 ) d
  from (select '92.111.0.2' as ip from t1)

With no split function, DB2 and SQL Server reverse the problem: prepend a dot, then for each position take RIGHT(ip, pos) — the tail of the string — and keep only the tails that start with a dot. Each such tail has one part of the IP at its front. A recursive CTE generates the positions, and a MAX(CASE WHEN rn = 1 …) pivots the four parts into columns.

The book’s version runs to about twenty lines per engine. It is a good reminder that “split a string” is a genuinely hard operation when the engine gives you only SUBSTR and INSTR.

6.17

Finding text not matching a pattern

In plain English Free-text comments contain phone numbers — but some are written 989-387-4321 and some 989-387.5359, mixing separators. You want the rows with a malformed one. So: find rows with a phone-like pattern, remove the well-formed ones, and see what’s still there.

SQL · two patterns, one trick 
select emp_id, text
from employee_comment
where regexp_like(text, '[0-9]{3}[-. ][0-9]{3}[-. ][0-9]{4}')
  and regexp_like(
         regexp_replace(text,
            '[0-9]{3}([-. ])[0-9]{3}\1[0-9]{4}','***'),
         '[0-9]{3}[-. ][0-9]{3}[-. ][0-9]{4}')

Chapter 7 · book pages 169–203

Working with Numbers

SQL is not a statistics package, but it is a very good calculator. This chapter covers the five aggregates everyone uses, the window functions that turn them into running totals and moving averages, and four recipes that do real statistics — mode, median, median absolute deviation and Benford’s law — without leaving the database.

The short version

Chapter 7 in plain English

One fact underpins half the chapter: aggregate functions ignore NULLs. AVG divides by the number of non-NULL values, so an average over a nullable column is quietly answering a narrower question than you think. The rest is about which frame you are aggregating over — the whole table (GROUP BY the lot), a group (GROUP BY a column), or a running window (OVER).

➗

The five aggregates

AVG, MIN, MAX, SUM, COUNT. Add GROUP BY and you get one answer per group.

🚫

NULLs are skipped

Every aggregate but COUNT(*) ignores NULL rows. COALESCE is how you put them back.

🪟

OVER makes it a window

The same aggregate, evaluated at each row, over the rows before it. That is a running total in one clause.

🔢

COUNT(*) ≠ COUNT(col)

Star counts rows; a column name counts non-NULL values. On the commission column that is the difference between 14 and 4.

📊

Mode and median are recipes, not functions

DENSE_RANK over a count finds the mode; PERCENTILE_CONT(0.5) finds the median. Oracle has shortcuts for both.

🧮

Division needs a decimal

Integer ÷ integer truncates in several engines. CAST(… as decimal) before you divide, or your percentage will be 0.

The trap the chapter keeps coming back to Ignored NULLs change the denominator. For DEPTNO 30 there are six employees but only four with a commission, so avg(comm) returns 550 (2200 ÷ 4) — the average of those who earn commission. To average over all six, write avg(coalesce(comm,0)) and get 2200 ÷ 6. Same query shape, different question.

7.6

Generating a running total

In plain English Add a running total in one clause: sum(sal) over (order by …) means “sum everything up to and including this row”. The only subtlety is that the ORDER BY has to be unique, or ties get summed together.

SQL · the running total 
select ename, sal,
       sum(sal) over (order by sal,empno) as running_total
  from emp
 order by 2
Why empno is in the ORDER BY WARD and MARTIN both earn 1250. Order only by SAL and the window treats them as one tie group: both rows get 2850 + 1250 + 1250 = 5350 (RUNNING_TOTAL2). Add the primary key and the totals become distinct — 4100 then 5350 (RUNNING_TOTAL1). Same thing happens to SCOTT and FORD at 3000. Any column that can tie needs a tiebreaker in the window’s ORDER BY.

7.8

Smoothing a series of values

In plain English Daily sales bounce around, and you want the trend. A moving average replaces each value with the average of it and the two days before it — which is just LAG (the previous rows) plus ordinary arithmetic.

select date1, sales,lag(sales,1) over(order by date1) as salesLagOne,

7.9

Calculating a mode

In plain English The mode is the value that appears most often. SQL has no MODE() function, so: count each value, rank the counts, keep rank 1.

SQL · DENSE_RANK over a count 
select sal
  from (
select sal,
       dense_rank()over( order by cnt desc) as rnk
  from (
select sal, count(*) as cnt
  from emp
 where deptno = 20
 group by sal
       ) x
       ) y
 where rnk = 1

The inner view counts each salary; the middle view ranks the counts with DENSE_RANK (which allows ties); the outer query keeps rank 1. Because it is a dense rank, every tied mode survives.

SQL · Oracle’s KEEP extension 
select max(sal)
       keep(dense_rank first order by cnt desc) sal
  from (
select sal, count(*) cnt
  from emp
  where deptno=20
  group by sal
       )

Read the KEEP clause right to left: order the rows by CNT descending, keep the first dense rank, then return MAX(SAL) of what is left.

KEEP picks only one mode If several salaries tie for most frequent, Oracle’s KEEP version returns just one of them — the highest, since it wraps MAX(SAL). The DENSE_RANK version returns all of them. Here it makes no difference: 3000 is both the mode and the highest salary in DEPTNO 20.
7.10

Calculating a median

In plain English The median is the 50th percentile — the middle value once the data is sorted. Recent engines have PERCENTILE_CONT(0.5) for exactly this; Oracle also has MEDIAN(). MySQL has neither, so it re-creates one out of CUME_DIST.

SQL · PERCENTILE_CONT as an aggregate 
select percentile_cont(0.5)
        within group(order by sal)
  from emp
 where deptno=20
SQL · the same, plus OVER() 
select percentile_cont(0.5)
        within group(order by sal)
        over()
  from emp
 where deptno=20

SQL Server treats PERCENTILE_CONT strictly as a window function, so it insists on the OVER().

SQL · MEDIAN 
select median(sal)
  from emp
 where deptno=20

select percentile_cont(0.5)
        within group(order by sal)
  from emp
 where deptno=20

Both work in Oracle — MEDIAN is the short one.

SQL · rebuilding the median with CUME_DIST 
with rank_tab (sal, rank_sal) as
(
select sal, cume_dist() over (order by sal)
            from emp
            where deptno=20
),
inter as
(
        select sal, rank_sal from rank_tab
        where rank_sal>=0.5
union
        select sal, rank_sal from rank_tab
        where rank_sal<=0.5
)
        select avg(sal) as MedianSal
               from inter

CUME_DIST labels every row with its percentile. It cannot be used in a WHERE clause, hence the CTE. Then take the rows at or either side of 50% and average them — which handles the even-row case where no single row sits exactly on the median.

Same function, other percentiles Because the median is just the 50th percentile, the same call with 0.05 and 0.95 gives you the 5th and 95th percentiles — another way to hunt for outliers, and the stepping stone to recipe 7.16.
7.11

Determining the percentage of a total

In plain English Part ÷ whole × 100. The part is the sum for one department; the whole is the sum for the table. Two ways to get both numbers in one query: a CASE inside two SUMs, or SUM() OVER () with no PARTITION BY.

SQL · CASE inside SUM 
select (sum(
         case when deptno = 10 then sal end)/sum(sal)
        )*100 as pct
  from emp

The CASE returns a salary only for department 10 and NULL for everything else — and since aggregates skip NULLs, the first SUM is already the department’s total. No ELSE needed.

SQL · SUM() OVER () 
select distinct (d10/total)*100 as pct
  from (
select deptno,
       sum(sal)over() total,
       sum(sal)over(partition by deptno) d10
  from emp
       ) x
 where deptno=10
Filter outside the inline view Window functions are evaluated after WHERE. Put where deptno = 10 inside inline view X and the window sees only three rows — so sum(sal)over() becomes 8750 instead of 29025, and the percentage comes out as 100%. That is why the filter sits in the outer query.
Integer division strikes If SAL is an integer, d10/total truncates to 0 in DB2, SQL Server and PostgreSQL — a percentage of zero. Cast one side to decimal first.
7.12

Aggregating nullable columns

In plain English You want the average commission across all employees in department 30, but aggregates skip NULLs — so avg(comm) silently divides by four instead of six. COALESCE(comm,0) puts the missing rows back in the denominator.

SQL 
select avg(coalesce(comm,0)) as avg_comm
  from emp
 where deptno=30
Two different questions avg(comm) asks “what does the average commissioned employee earn?” — 2200 ÷ 4 = 550. avg(coalesce(comm,0)) asks “what is the average commission across the department?” — 2200 ÷ 6 ≈ 366.67. Neither is wrong; only one is what you meant.
7.13

Computing averages without high and low values

In plain English A single huge salary drags the mean upward. Throw away the biggest and the smallest value and average the rest — statisticians call it a trimmed mean, and it is a one-WHERE-clause job.

SQL · exclude with NOT IN 
select avg(sal)
  from emp
 where sal not in (
    (select min(sal) from emp),
    (select max(sal) from emp)
 )
SQL · MIN/MAX OVER 
select avg(sal)
  from (
select sal, min(sal)over() min_sal, max(sal)over() max_sal
  from emp
       ) x
 where sal not in (min_sal,max_sal)
It removes every tie, not one row NOT IN against the min and max drops all employees earning 800 or 5000 — here that is three people, not two. If you want to remove a single instance of each, subtract instead: (sum(sal)-min(sal)-max(sal))/(count(*)-2).
A “robust statistic” The book’s margin note: a mean with the extremes removed is a safer estimate because it is less sensitive to bias. Recipe 7.16 is the other robust tool in the chapter — and both have the advantage of not assuming your data follows a normal distribution.
7.14

Converting alphanumeric strings into numbers

In plain English paul123f321 should become the number 123321. This is the string chapter’s TRANSLATE + REPLACE trick again: map every letter to #, delete the #s, cast what is left.

select cast(
       replace(
     translate( 'paul123f321',
                'abcdefghijklmnopqrstuvwxyz',

       as integer ) as num
  from t1

Fishing for digits instead of removing letters Listing all 26 letters only works if the data is strictly alphanumeric. 7.15

Changing values in a running total

In plain English A bank statement: purchases add to the balance, payments subtract. Put a CASE inside the windowed SUM so each row contributes either +amt or -amt, and the running total becomes the balance.

SQL · signed running total 
select case when trx = 'PY'
            then 'PAYMENT'
            else 'PURCHASE'
        end trx_type,
        amt,
        sum(
         case when trx = 'PY'
            then -amt else amt
         end
       ) over (order by id,amt) as balance
from V

100, 200, 150, 250, 50, 0 — every row adds its amount except the three PY payments (50, 200, 50), which subtract.

Two CASE expressions, two jobs The first CASE only produces a readable label for the output. The second is the one that does the arithmetic — it flips the sign before the window aggregates. You could drop the first and the balance would be identical.

Finding outliers using the median absolute deviation

In plain English The usual outlier test (“more than three standard deviations from the mean”) assumes bell-curve data. The robust alternative: find the median, measure how far every value sits from it, take the median of those distances — that is the MAD — then ask which values are more than a few MADs away.

Finding anomalies using Benford’s law

In plain English In real-world data, the first digit of a number is 1 about 30% of the time and 9 only about 5% — not 11% each as you would guess. That distribution is Benford’s law, and numbers invented by humans don’t follow it. So: compute the expected frequency, compute the actual one, and compare.

SQL · expected versus actual first digits 
with
FirstDigits (FirstDigit)
as
(select left(cast(SAL as CHAR),1) as FirstDigit
        from emp),
TotalCount (Total)
as
 (select count(*)
  from emp),
ExpectedBenford (Digit,Expected)
as
  (select value,(log10(value + 1) - log10(value)) as expected
   from t10
   where value < 10)
select count(FirstDigit),Digit
,coalesce(count(*)/Total,0) as ActualProportion,Expected
From FirstDigits
     Join TotalCount
     Right Join ExpectedBenford
     on FirstDigits.FirstDigit=ExpectedBenford.Digit
group by Digit
order by Digit;
The math, and the RIGHT JOIN Expected frequency for digit d is log10((d+1)/d) — which is what log10(value+1) - log10(value) computes, using T10 to generate the digits 1–9. The RIGHT JOIN onto the expected table means digits with zero occurrences still appear in the output instead of vanishing.
It needs a lot of data Benford works best with a large set of values spanning several orders of magnitude. Fourteen salaries don’t really qualify — but the book makes the point that even here, a deviation from the expected curve is reason to look more closely.

DB2 and PostgreSQL do it the long way Neither has a LAST_DAY function, so both walk the month: start at 1 February and add days while the month number stays the same (DB2 with a recursive WITH, PostgreSQL with generate_series(0,29)), then take MAX of the day numbers. Same answer, twenty more lines.

9.6

First and last occurrence of a weekday in a month

In plain English The first Monday of June and the last Monday of June. Oracle answers with two NEXT_DAY calls; everyone else walks the month and takes MIN/MAX of the Mondays.

SQL · Oracle 
select next_day(trunc(sysdate,'mm')-1,'MONDAY') first_monday,
       next_day(last_day(trunc(sysdate,'mm'))-7,'MONDAY') last_monday
  from dual
SQL · DB2 
with x (dy,mth,is_monday)
  as (
select dy,month(dy),
       case when dayname(dy)='Monday'
            then 1 else 0
       end
  from (
select (current_date-day(current_date) day +1 day) dy
  from t1
       ) tmp1
 union all

       case when dayname(dy +1 day)='Monday'
            then 1 else 0
       end
  from x
 where month(dy +1 day) = mth

  from x

The -1 and the -7 NEXT_DAY returns the next occurrence, strictly after the date you give it. So next_day(trunc(sysdate,'mm'),'MONDAY') would return the second Monday whenever the month starts on a Monday. Subtracting one day first makes the first-of-month itself eligible. The last-Monday version subtracts a week from the end of the month for exactly the same reason.
Everyone else does date arithmetic PostgreSQL and MySQL compute the offset from the first of the month with SIGN() and ABS(), then add 28 days if that still falls in the same month, otherwise 21. The book’s version is worth reading slowly — it is the exact logic NEXT_DAY hides.
9.7

Creating a calendar

In plain English The showpiece of the chapter. Generate every day of the month, tag each with a weekday number and a week number, then pivot the days into seven columns grouped by week. A wall calendar, produced by GROUP BY.

       month(current_date) mth,

       dayofweek(dy+1 day), week_iso(dy+1 day)
  from x
 where month(dy+1 day) = mth

That is why the SQL Server and MySQL versions carry a correction for Sunday — case when datepart(dw,dy) = 1 then ww-1 else ww end — so that weeks don’t break across the month boundary.

9.10

Filling in missing dates

In plain English A report needs a row for every month, including the ones where nobody was hired. Generate the months, LEFT JOIN the employees onto them, and count. The months with no matches show zero.

SQL · Oracle 
with x
  as (
select add_months(start_date,level-1) start_date
  from (
select min(trunc(hiredate,'y')) start_date,
       add_months(max(trunc(hiredate,'y')),12) end_date
  from emp
       )
 connect by level <= months_between(end_date,start_date)
)
select x.start_date MTH, count(e.hiredate) num_hired
  from x left join emp e
    on (x.start_date = trunc(e.hiredate,'mm'))
 group by x.start_date
 order by 1
count(e.hiredate), not count(*) This is the whole recipe. A LEFT JOIN gives every generated month at least one row — so count(*) would return 1 for a month with no hires, and your report would be quietly wrong. Counting a column of the outer-joined table returns 0, because that column is NULL on the unmatched rows.
Where the range comes from The recursion starts at min(trunc(hiredate,'y')) — 1 January of the first hire year — and runs for months_between(end_date, start_date) months. DB2, MySQL, PostgreSQL and SQL Server all build the same series with +1 month recursion, and all of them filter with start_date < end_date in the recursive step.

9.12

Comparing records using specific parts of a date

In plain English Which employees were hired on the same month and weekday? Flatten each hire date to something like 3DEC, self-join on it, and drop the mirror-image pairs with a.empno < b.empno.

SQL · Oracle and PostgreSQL 
select a.ename ||
       ' was hired on the same month and weekday as '||
       b.ename as msg
  from emp a, emp b
 where to_char(a.hiredate,'DMON') =
       to_char(b.hiredate,'DMON')
   and a.empno < b.empno
 order by a.ename

The format mask is doing the real work: DMON keeps the day-of-month and the month name but throws away the year — and the day-of-month implies the weekday.

Why a.empno < b.empno A self-join produces each pair twice — FORD×JAMES and JAMES×FORD — and each row also joins to itself. The inequality kills both: it removes the mirror images, and because no row is less than itself, it removes the self-matches too. One clause, three problems. (Without it you get six rows instead of three.)
9.13

Identifying overlapping date ranges

In plain English An employee worked several projects, and some of them ran at the same time. Two ranges overlap when one starts inside the other: compare each row’s start date against every other row’s start and end.

SQL · the self-join 
select a.empno,a.ename,
       'project '||b.proj_id||
       ' overlaps project '||a.proj_id as msg
  from emp_project a,
       emp_project b
 where a.empno = b.empno
   and b.proj_start >= a.proj_start
   and b.proj_start <= a.proj_end
   and a.proj_id != b.proj_id
The window-function alternative The book also solves it without a self-join, for when each person has only a handful of projects: order each person’s projects by start date and ask whether the LEADing start dates fall inside the current range — lead(proj_start,1|2|3|4) over (partition by ename order by proj_start) between proj_start and proj_end.
The hard-coded 1..4 The LEAD version only looks four rows ahead, so it silently misses an overlap five projects later. It is fast and readable for small sets; the self-join has no such ceiling. The book is explicit that this is a trade-off, not an improvement.

Working with Ranges

Five recipes, and one idea underneath all of them: a range is a set of rows where each one continues the last. This row’s end equals the next row’s start. Once you can see the neighbour row — with LEAD or LAG — finding ranges, numbering them, and filling the gaps between them all become one-liners.

The short version

Chapter 10 in plain English

The test for “these two rows form a continuous range” is almost embarrassingly simple: does this row’s end date equal the next row’s start date? Everything else in the chapter is bookkeeping around that question — picking the rows where it’s true, counting the rows where it’s false, or manufacturing the rows that don’t exist at all.

🔗

Consecutive = end meets start

One comparison against the next row. LEAD gives you that row without a self-join.

↔️

LEAD and LAG

Look forward one row, look back one row. Add PARTITION BY and the neighbours are within each group, not across the table.

🏝️

Flag, then running-sum

Mark each row 1 where a range breaks and 0 where it continues, then total the flags: every row now carries its range number.

🕳️

Gaps need invented rows

You cannot count a year that isn’t in the table. Generate the years first, then LEFT JOIN and COALESCE the count to 0.

🔢

Numbers from nothing

Recursive WITH, Oracle’s MODEL clause, generate_series, or a numbers table — pick whichever your engine has.

🧱

Ordering must be unique

“The next row” only means something if the ORDER BY gives a definite order. Ties quietly scramble the result.

Recipe by recipe

10.1 – 10.6, explained simply

Five recipes and a summary. Recipes 10.1 and 10.3 are two halves of one technique.

10.1

Locating a range of consecutive values

In plain English From a table of projects, keep the rows that are continued by the next row — those whose end date matches the following row’s start date. One window function, one WHERE clause.

SQL · all five dialects 
select proj_id, proj_start, proj_end
  from (
select proj_id, proj_start, proj_end,
       lead(proj_start)over(order by proj_id) next_proj_start
  from V
       ) alias
 where next_proj_start = proj_end

The inline view adds the neighbour, the outer query tests it. That’s the whole shape of the chapter.

The last row is always excluded LEAD returns NULL for the final row, and NULL = proj_end is never true — so the last project drops out even when it obviously starts a range. That is right for this recipe (nothing continues it) but it matters in 10.3, which must still return single-row ranges.
Adding the row before it The book shows a variant that keeps rows whose start matches the previous row’s end — or proj_start = lag(proj_end)over(order by proj_id) — which pulls the last row of each run into the result as well. Which of the two you want depends on whether you are after “rows with a successor” or “rows inside a run”.
10.2

Finding differences between rows in the same group

In plain English For each employee, compare their salary with the salary of the next person hired in the same department, and show “N/A” for whoever was hired last. That is LEAD with a PARTITION BY and a COALESCE.

SQL · the solution 
with next_sal_tab (deptno,ename,sal,hiredate,next_sal)
as
(select deptno, ename, sal, hiredate,
       lead(sal)over(partition by deptno
                         order by hiredate) as next_sal
  from emp )

   select deptno, ename, sal, hiredate
,    coalesce(cast(sal-next_sal as char), 'N/A') as diff
   from next_sal_tab
This column is text, not a number coalesce(cast(sal-next_sal as char),'N/A') forces the difference to a character type so the literal 'N/A' fits. The side effect is that the column left-aligns and can no longer be sorted or summed numerically. If you only need a NULL, skip the cast and leave the value alone. (Oracle’s version uses nvl(to_char(…),'N/A'), and lpad(…,10) to line the column up.)
The tie problem, again When several employees share a HIREDATE, plain LEAD(sal) compares them to each other instead of to the next date — so ant compares to joe’s 1500 rather than to MILLER’s 1300. The fix is the same one used in recipes 8.7 and 9.x: count(*) over (partition by deptno, hiredate) and row_number() give you the distance to skip, and lead(sal, cnt-rn+1) jumps the whole tied block.
10.3

Beginning and end of a range of consecutive values

In plain English Now collapse each run into one row: its first start and its last end. Flag where the range breaks, add the flags up as you go, and the running total is the group number.

SQL · flag, running-sum, group 
select proj_grp, min(proj_start), max(proj_end)
  from (
select proj_id,proj_start,proj_end,
       sum(flag)over(order by proj_id) proj_grp
  from (
select proj_id,proj_start,proj_end,
       case when
            lag(proj_end)over(order by proj_id) = proj_start
            then 0 else 1
       end flag
  from V
       ) alias1
       ) alias2
 group by proj_grp
This idiom has a name: gaps and islands The islands are the runs, the gaps are the breaks. The pattern — mark a break with 1, keep the run with 0, cumulative-sum the marker — works for consecutive dates, consecutive integers, consecutive anything. Once you recognise it in this recipe you will see it everywhere.
Single-row ranges survive A project with no neighbour on either side gets flag = 1 and becomes a group of one — so it appears in the output with proj_start = proj_end rather than being dropped. That is the deliberate difference from recipe 10.1, which discards it.
10.4

Filling in missing values in a range

In plain English “How many people were hired each year from 2005 to 2014?” Some of those years have no rows in EMP at all, so a GROUP BY can’t invent them. Build the ten years first, then left-join the counts onto them.

SQL · Oracle 
select x.yr, coalesce(cnt,0) cnt
  from (
select extract(year from min(hiredate)over()) -
       mod(extract(year from min(hiredate)over()),10) +
       rownum-1 yr
  from emp
 where rownum <= 10
       ) x
  left join
       (
select to_number(to_char(hiredate,'YYYY')) yr, count(*) cnt
  from emp
 group by to_number(to_char(hiredate,'YYYY'))
       ) y
    on ( x.yr = y.yr )
SQL · PostgreSQL and MySQL, using T10 
select y.yr, coalesce(x.cnt,0) as cnt
  from (
select min_year-mod(cast(min_year as int),10)+rn as yr
  from (
select (select min(extract(year from hiredate))
          from emp) as min_year,
       id-1 as rn
  from t10
       ) a
       ) y
  left join
       (
select extract(year from hiredate) as yr, count(*) as cnt
  from emp
 group by extract(year from hiredate)
       ) x
    on ( y.yr = x.yr )
Check the decade arithmetic before you reuse it The book’s formula subtracts mod(year,10) — the year’s last digit — which lands on the start of the decade, 2000, and the ten rows then run 2000–2009. But the result set the recipe is aiming at is 2005–2014: the ten years beginning with the earliest hire. To get that, drop the - mod(…,10) term and simply add rn to the minimum year. (The book’s own step-by-step figure on page 328 is inconsistent too — it prints MOD_YR as 0 for a 2005 start, and one row as 1984. Read it as an illustration of the idea, not as verified output.)
Where the ten rows come from DB2, Oracle and SQL Server take them from EMP itself with ROWNUM / ROW_NUMBER() / TOP (10) — the table is only being used as a supplier of ten rows. PostgreSQL and MySQL use T10, which is exactly what it’s for.
10.5

Generating consecutive numeric values

In plain English Produce the numbers 1 to 10 without reading them from anywhere. Recursion does it in every engine that has a recursive WITH; PostgreSQL has generate_series; and Oracle has the MODEL clause, which is the most interesting code in the book.

SQL · recursive WITH 
with x (id)
as (
select 1
 union all
select id+1
  from x
 where id+1 <= 10
)
select * from x

Seed with 1, add 1 each pass, stop at 10. SQL Server caps recursion at 100 levels by default, so long series need OPTION (MAXRECURSION n).

SQL · generate_series 
select id
  from generate_series (1, 10) x(id)

Start, stop — and an optional third argument for the step: generate_series(min(deptno), max(deptno), 5) gives 10, 15, 20, 25, 30.

SQL · the MODEL clause 
select array id
  from dual
 model
   dimension by (0 idx)
   measures(1 array)
   rules iterate (10) (
     array[iteration_number] = iteration_number+1
   )

MODEL turns a query into a spreadsheet: DIMENSION BY the row axis, MEASURES the cells, RULES ITERATE the loop. Ten iterations write the numbers 1–10 into cells 0–9.

Why this recipe matters Every earlier chapter reached for T10 or T500 — a physical numbers table. This recipe is how you make one on demand. In practice that is what the recursive WITH and generate_series versions are for, and it is why modern code rarely ships a T500 any more.
10.6

Summing up

In plain English Ranges are neighbours. Find the neighbour with LEAD/LAG, and the three questions — which rows are in a range, where does a range start and end, and which values are missing — all turn into an aggregate or a filter.

The chapter’s other lesson is about honesty in reporting: a table can only tell you about the rows it has, so any question of the form “for every year in this decade…” requires you to construct the frame first and join the data onto it. Otherwise the missing years don’t show up as missing — they just vanish.

Advanced Searching

Twelve recipes that treat searching as something more than a WHERE clause: paging through results, jumping to the “next” row, ranking, suppressing duplicates, and finding a value in one row to use in all the others. Almost all of them are window functions in disguise.

The short version

Chapter 11 in plain English

SQL has no idea what “first”, “next” or “latest” means until you impose an order. So every recipe here starts the same way: number the rows in some order, then query the numbers. Once the row has a number — from ROW_NUMBER, RANK or DENSE_RANK — “page 2”, “every other row”, “the top five” and “the latest hire” all become ordinary comparisons.

📄

Paging is numbering

ROW_NUMBER() + where rn between 6 and 10. No LIMIT, no OFFSET, works everywhere.

🏅

Three ways to rank

11.1

Paginating through a result set

In plain English Show five rows per page, then the next five. Number the rows in a definite order, then ask for a range of numbers. That’s all pagination is.

SQL · page one, then page two 
select sal
  from (
select row_number() over (order by sal) as rn,
       sal
  from emp
       ) x
 where rn between 1 and 5

select sal
  from (
select row_number() over (order by sal) as rn,
       sal
  from emp
       ) x
 where rn between 6 and 10
Oracle’s ROWNUM needs the double nesting ROWNUM is assigned as rows are produced — before ORDER BY runs — so select sal, rownum rn from emp order by sal numbers rows in whatever order they came out, not in salary order. The book’s Oracle version therefore sorts in an inner query and numbers in an outer one: select sal, rownum rn from (select sal from emp order by sal). Window functions have no such problem, because the ORDER BY lives inside the OVER().
Why not LIMIT? LIMIT/OFFSET, TOP and FETCH FIRST all exist — in different engines. The ROW_NUMBER form runs unchanged on all five, which is why the book opens the chapter with it.
11.2

Skipping n rows from a table

In plain English Return every other row, or every fifth row. Same numbering as 11.1 — then filter on the number with MOD instead of a range.

SQL · every other employee 
select ename
  from (
select row_number() over (order by ename) rn,
       ename
  from emp
       ) x
 where mod(rn,2) = 1
Change the modulus mod(rn,5) = 1 gives every fifth row; mod(rn,2) = 0 gives the other half. The range form from 11.1 (rn between 6 and 10) and this form are the same idea with a different predicate — pick whichever reads better for the question.
11.3

Incorporating OR logic when using outer joins

In plain English You want every department listed, with employees shown only for departments 10 and 20. Write the filter in the WHERE clause and departments 30 and 40 vanish — because WHERE is applied after the outer join, and their employees are NULL. Put the filter in the ON clause and they stay.

SQL · the condition goes in the ON clause 
select e.ename, d.deptno, d.dname, d.loc
  from dept d left join emp e
    on (d.deptno = e.deptno
       and (e.deptno=10 or e.deptno=20))
 order by 2
SQL · or filter first, then outer join 
select e.ename, d.deptno, d.dname, d.loc
  from dept d
  left join
       (select ename, deptno
          from emp
         where deptno in ( 10, 20 )
       ) e on ( e.deptno = d.deptno )
 order by 2
The rule, stated once A condition in the ON clause decides which rows join. A condition in the WHERE clause decides which joined rows survive. Putting e.deptno = 10 in the WHERE clause of a LEFT JOIN is the single most common way to accidentally turn an outer join back into an inner join — because NULL = 10 is unknown, and unknown rows are discarded.
11.4

Determining which rows are reciprocals

In plain English A row of (70, 90) is a reciprocal of (90, 70) — the two columns swapped. Join the table to itself on both columns, then keep only one row per pair.

SQL · self-join both ways 
select distinct v1.*
  from V v1, V v2
 where v1.test1 = v2.test2
   and v1.test2 = v2.test1
   and v1.test1 <= v1.test2
Why <= and not < Each pair matches twice — (70,90) finds (90,70) and vice versa — so one of the two must be dropped. Comparing the two columns of the same row breaks the symmetry: exactly one of any mirrored pair satisfies test1 <= test2. Using < would also work for the mirrored pairs but would throw away (20,20), which is its own reciprocal — hence <=.
11.5

Selecting the top n records

In plain English The five best-paid employees — where “five” means five salaries, not five rows. Two people earn 3000, so a strict row count would cut one of them off arbitrarily. DENSE_RANK keeps both.

SQL 
select ename,sal
  from (
select ename, sal,
       dense_rank() over (order by sal desc) dr
  from emp
       ) x
 where dr <= 5
Which ranking function, and why it matters DENSE_RANK here returns 6 rows for “top 5”, because 3000 occurs twice. Swap in ROW_NUMBER and you get exactly 5 rows but one of the tied employees is silently dropped. Swap in RANK and the 3000 pair share rank 2, but the next salary gets rank 4 — leaving a hole. The book chooses DENSE_RANK because the question is about salaries, not about row counts.
11.6

Finding records with the highest and lowest values

In plain English Who earns the most and who earns the least, in one query. Put the table-wide MIN and MAX on every row with OVER(), then keep the rows that match one of them.

SQL · DB2, Oracle, and SQL Server 
select ename
  from (
select ename, sal,
       min(sal)over() min_sal,
       max(sal)over() max_sal
  from emp
       ) x
 where sal in (min_sal,max_sal)
Empty OVER() means the whole table min(sal)over() with no PARTITION BY and no ORDER BY returns one value — the global minimum — repeated on every row. Compare that with min(sal)over(partition by deptno), which repeats the department minimum, and with min(sal)over(order by sal), which makes it a running minimum. Three very different columns from one function.
11.7

Investigating future rows

In plain English Find the employees who earn less than the person hired immediately after them. Compare each row to the next with LEAD and keep the ones that go down.

SQL 
select ename, sal, hiredate
  from (
select ename, sal, hiredate,
       lead(sal)over(order by hiredate) next_sal
  from emp
       ) alias
 where sal < next_sal
Two employees share a hire date JAMES and FORD were both hired on 03-DEC-81, so they compare with each other rather than with the next date — the same tie problem as recipes 8.7 and 10.2. The book’s second solution applies the same fix: lead(sal, cnt-rn+1), where cnt counts the tied rows and rn numbers them, jumps the whole block. The last row gets NULL and is dropped by sal < NULL.
11.8

Shifting row values

In plain English Show each salary next to the next one and the previous one — and when you fall off the end, wrap around to the other end of the list. COALESCE against the global min and max does the wrapping.

SQL · forward, rewind, and wrap 
select ename,sal,
       coalesce(lead(sal)over(order by sal),min(sal)over()) forward,
       coalesce(lag(sal)over(order by sal),max(sal)over()) rewind
  from emp
Looking further than one row LEAD and LAG take an optional offset: lead(sal,3)over(order by sal) is the salary three rows ahead, and lag(sal,5) five rows back. The book’s figure for this shows exactly the NULLs you’d expect at both ends — which is why the wrap-around version needs COALESCE.
11.9

Ranking results

In plain English Number the salaries from lowest to highest, giving tied values the same rank and leaving no gaps afterwards. That is DENSE_RANK — one function, no subquery.

SQL 
select dense_rank() over(order by sal) rnk, sal
  from emp
Before window functions This needed a correlated subquery counting how many salaries were lower, plus a DISTINCT to collapse the ties — a dozen lines and a full scan per row. The book’s point in this recipe is precisely how much the window function removed.
11.10

Suppressing duplicates

In plain English List each distinct job once. DISTINCT is the obvious answer; ROW_NUMBER is the one that scales, because it lets you keep an entire row and still dedupe on one column.

SQL · three solutions 
select job
  from (
select job,
       row_number()over(partition by job order by job) rn
  from emp
       ) x
 where rn = 1

select distinct job
  from emp

select job
  from emp
 group by job
Why bother, if DISTINCT is shorter? DISTINCT applies to the whole select list. Ask for distinct job, deptno and you get nine rows instead of five, because it is now deduplicating pairs. ROW_NUMBER … partition by job followed by rn = 1 lets you name one column to dedupe on while still selecting the others — the thing DISTINCT cannot do.
11.11

Finding knight values

In plain English Show every employee alongside the salary of the most recently hired person in their department. You have to jump to a particular row (latest HIREDATE) and then across to a different column (SAL) — up and over, like a knight.

SQL · flag the row, then broadcast it 
select deptno,
       ename,
       sal,
       hiredate,
       max(latest_sal)over(partition by deptno) latest_sal
  from (
select deptno,
       ename,
       sal,
       hiredate,
       case
         when hiredate = max(hiredate)over(partition by deptno)
         then sal else 0
       end latest_sal
  from emp
       ) x
 order by 1, 4 desc

Two passes: the inner query marks the latest hire with its salary and everyone else with 0; the outer MAX … OVER (PARTITION BY deptno) copies that one non-zero value onto every row of the department.

SQL · KEEP, in one expression 
select deptno,
        ename,
        sal,
        hiredate,
         max(sal)
           keep(dense_rank last order by hiredate)
           over(partition by deptno) latest_sal
  from emp
 order by 1, 4 desc

Read it right to left: order the department’s rows by HIREDATE, keep the last dense rank, return MAX(SAL) of what survives. Oracle states the jump in one clause.

Why the else 0 works — and when it wouldn’t The non-latest rows are set to 0, not NULL, and then MAX picks the one real salary. That depends entirely on salaries being positive: if a genuine salary could be 0 (or negative), the placeholder would be indistinguishable from real data and the answer would be wrong. Using NULL in the ELSE is the safer version, since MAX ignores NULLs — and that is exactly what KEEP does implicitly.
One caution from the book If two employees in a department share the latest hire date, the non-Oracle version needs a MAX (or an explicit tiebreak) to decide which salary to broadcast. KEEP(dense_rank last …) has the same ambiguity, and the book notes that the two versions can disagree in that case.
11.12

Generating simple forecasts

In plain English Each order has an order date and a process date; you want three future rows per order showing the processing pipeline filling in. Cross join the orders to a three-row numbers table so each order appears three times.

SQL · DB2, MySQL, and SQL Server 
with nrows(n) as (
select 1 from t1 union all
select n+1 from nrows where n+1 <= 3
)
select id,
       order_date,
       process_date,
       case when nrows.n >= 2
            then process_date+1
            else null
       end as verified,
       case when nrows.n = 3
            then process_date+2
            else null
       end as shipped
  from (
select nrows.n id,
       getdate()+nrows.n   as order_date,
       getdate()+nrows.n+2 as process_date
  from nrows
       ) orders, nrows
 order by 1
How the rows get filled in Every order produces three rows. On row 1 (n = 1) both predicted columns are NULL; on row 2 the CASE fills in VERIFIED; on row 3 it fills in both. So the result reads as a timeline — the same three orders, at three stages of the pipeline, with the future dates computed as process_date + 1 and + 2.
Oracle and PostgreSQL Oracle swaps the recursive CTE for select level n from dual connect by level <= 3; PostgreSQL uses generate_series(1,3) in both places. The logic is identical — only the row generator changes. The book gives no MySQL solution here.
11.13

Summing up

In plain English “Advanced searching” turned out to be mostly giving rows an identity — a number, a rank, or a neighbour. Once a row has one, questions that felt impossible in SQL (“page 2”, “the next one”, “the latest”) become ordinary comparisons.

And the chapter’s structural lessons are just as useful as the window functions: a filter in ON preserves an outer join that the same filter in WHERE destroys; a cross join to a numbers table multiplies rows on purpose; and DISTINCT deduplicates the whole select list, which is rarely what you meant.

Reporting and Reshaping

Twenty recipes about the gap between how data is stored and how it has to be shown. Rows become columns, columns become rows, totals appear where there were none, and plain numbers turn into stars. Almost every trick here is one pattern — CASE plus an aggregate — pushed in a different direction.

The short version

Chapter 12 in plain English

A database stores data one way — narrow, repetitive, one fact per row. A report wants it another way — wide, grouped, subtotalled. This chapter is the whole business of translating between the two. The good news: there are only about five techniques, and they compose.

🔁

Rotating a result set

case when … then 1 else 0 end inside an aggregate turns rows into columns. A UNION ALL or a cross join turns them back.

🔑

A pivot needs a key

To get many output rows, first make each row unique with row_number() over (partition by …), then group on that number.

➕

Three ways to total

ROLLUP gives prefixes, CUBE gives every combination, GROUPING SETS gives exactly the ones you list.

🚩

GROUPING() breaks the tie

A NULL from a subtotal and a NULL in the data look identical. GROUPING returns 0 or 1 so you can tell which is which.

🪣

Buckets, two flavours

ceil(rn/5.0) fixes the size of each bucket; ntile(4) fixes the number of buckets.

📊

Histograms are strings

lpad('*', count(*), '*') draws horizontally; row_number plus MAX draws the same data vertically.

🪟

Windows don’t collapse rows

An aggregate with OVER repeats the total on every row — which is how you beat the “column must be in GROUP BY” rule.

⏳

Moving windows

range between 90 preceding and current row sums everything within 90 days of each row — a running total with a time limit.

🧮

Order of operations

WHERE runs before window functions, so a filter changes the totals. To filter after, wrap it in an inline view.

Recipe by recipe

12.1 – 12.21, explained simply

Twenty recipes and a summary — the longest chapter in the book.

12.1

Pivoting a result set into one row

In plain English You have fourteen employee rows and want a single row saying “dept 10 has 3, dept 20 has 5, dept 30 has 6”. Each value of DEPTNO needs to become its own column.

SQL · one row out — and the two-pass version that shows why it works 
select sum(case when deptno=10 then 1 else 0 end) as deptno_10,
       sum(case when deptno=20 then 1 else 0 end) as deptno_20,
       sum(case when deptno=30 then 1 else 0 end) as deptno_30
  from emp

/* the same flags, before they are collapsed */
select deptno,
       sum(case when deptno=10 then 1 else 0 end) as deptno_10,
       sum(case when deptno=20 then 1 else 0 end) as deptno_20,
       sum(case when deptno=30 then 1 else 0 end) as deptno_30
  from emp
 group by deptno
The whole chapter in one sentence The CASE expression is a flag that says “this row belongs to column X”. That flag is already the pivot — the SUM is only there to squash the flagged rows down to one row. Everything else in Chapter 12 is a variation on that move.
A note on the book’s second solution The book also shows an inline-view version (count(*) per department, then MAX(case …) to collapse). In the printed listing the third column reads deptno=10 instead of deptno=30 and a comma is missing after the first MAX — a typo, not a new idea. Written correctly it returns the same 3 / 5 / 6.
12.2

Pivoting a result set into multiple rows

In plain English Now you want several rows: one column per job, and beneath each job the names of the people who hold it — so the clerks column is four names tall. One row per job would only give you one name each, so something has to keep the rows apart.

SQL · number inside the job, then pivot on the number 
select max(case when job='CLERK'     then ename end) as clerks,
       max(case when job='ANALYST'   then ename end) as analysts,
       max(case when job='MANAGER'   then ename end) as mgrs,
       max(case when job='PRESIDENT' then ename end) as prez,
       max(case when job='SALESMAN'  then ename end) as sales
  from (
select job,
       ename,
       row_number()over(partition by job order by ename) rn
  from emp
       ) x
 group by rn
 order by rn
Why row_number() is not optional Drop it and group by nothing, and MAX keeps exactly one name per job — SMITH, SCOTT, JONES, KING, WARD — a single row, which is recipe 12.1 all over again. Numbering the rows within each job is what gives the outer GROUP BY rn something to line the names up against.
12.3

Reverse pivoting a result set

In plain English The opposite direction. Someone hands you a wide row — 3 | 5 | 6 across three department columns — and you need it back as three narrow rows. This is normal in warehouses, where numbers get stored pre-aggregated in columns.

SQL · a three-row table to multiply by, then a CASE to pick a column 
create view emp_cnts as
select sum(case when deptno=10 then 1 else 0 end) as deptno_10,
       sum(case when deptno=20 then 1 else 0 end) as deptno_20,
       sum(case when deptno=30 then 1 else 0 end) as deptno_30
  from emp

select dept.deptno,
       case dept.deptno
            when 10 then emp_cnts.deptno_10
            when 20 then emp_cnts.deptno_20
            when 30 then emp_cnts.deptno_30
       end as counts_by_dept
  from emp_cnts cross join
       (select deptno from dept where deptno <= 30) dept
The cross join is a photocopier A cartesian product copies the single wide row once per row of the other table. You need one copy per column you want to unwrap, so the helper table must have at least that many rows. DEPT holds four (10, 20, 30, 40) and only three columns are being unwrapped, so the deptno <= 30 filter trims it to three — otherwise you would get a fourth row of NULLs.
12.4

Reverse pivoting into one column

In plain English Go further: stuff ENAME, JOB and SAL into a single column, three lines per employee, with a blank line between employees. It is a printed list, not a table.

SQL · four copies of each row, one per output line 
with four_rows (id) as
(
 select 1
  union all
 select id+1
   from four_rows
  where id < 4
),
x_tab AS
(
 select e.ename, e.job, e.sal,
        row_number()over(partition by e.empno
                         order by e.empno) rn
   from emp e
   join four_rows on 1=1
  where e.deptno=10
)
select case rn
         when 1 then ename
         when 2 then job
         when 3 then cast(sal as char(4))
       end emps
  from x_tab
Why the row numbers run 1–4 and then start again Window functions are evaluated after FROM and WHERE. By the time ROW_NUMBER runs, each employee already exists four times, so partitioning by EMPNO numbers the four copies 1, 2, 3, 4. The fourth copy matches no branch of the CASE, comes out NULL, and NULL is your blank line. (PostgreSQL and MySQL need with recursive.)
12.5

Suppressing repeating values

In plain English Print the department number once, next to the first employee in that department, and leave it blank underneath — the way a printed report looks. As a bonus the rows have to be sorted for it to make sense.

SQL · compare each row with the one before it 
select case when lag(deptno)over(order by deptno) = deptno
            then null
            else deptno
       end deptno,
       ename
  from emp
 order by deptno, ename

/* Oracle's one-liner for the same test */
select to_number(
         decode(lag(deptno)over(order by deptno),
                deptno, null, deptno)
       ) deptno,
       ename
  from emp
 order by deptno, ename
This changes what you see, not what you have The blank cells are real NULLs. Anything downstream that counts, sums or sorts on that column will now be wrong — a NULL sorts to the bottom in Oracle and to the top in SQL Server, and count(deptno) would drop from fourteen to three. Use it as the last step before printing.
12.6

Pivoting to compare rows with each other

In plain English You want to know how much more department 20 earns than department 10, and than department 30. But those totals live on three different rows, and one row cannot see another. So: pivot the three totals onto one row, then just subtract.

SQL · pivot first, subtract second 
select d20_sal - d10_sal as d20_10_diff,
       d20_sal - d30_sal as d20_30_diff
  from (
select sum(case when deptno=10 then sal end) as d10_sal,
       sum(case when deptno=20 then sal end) as d20_sal,
       sum(case when deptno=30 then sal end) as d30_sal
  from emp
       ) totals_by_dept

/* the same thing with a CTE, which reads top to bottom */
with totals_by_dept (d10_sal, d20_sal, d30_sal) as
(
 select sum(case when deptno=10 then sal end),
        sum(case when deptno=20 then sal end),
        sum(case when deptno=30 then sal end)
   from emp
)
select d20_sal - d10_sal as d20_10_diff,
       d20_sal - d30_sal as d20_30_diff
  from totals_by_dept
Notice the missing ELSE case when deptno=10 then sal end has no else, so every row from another department contributes NULL — and SUM skips NULLs. Zero would be dangerous here: it is a real salary value, and it would quietly poison an AVG or a MIN later on. “Not this department” is what NULL is for.
12.7

Buckets of a fixed size

In plain English Put the employees into groups of exactly five — group 1 holds the first five by employee number, group 2 the next five, and the last group is allowed to be short. You don’t know in advance how many groups you’ll need.

SQL · number the rows, divide by five, round up 
select ceil(row_number()over(order by empno)/5.0) grp,
       empno,
       ename
  from emp
 order by empno

/* the working, shown one step at a time */
select row_number()over(order by empno) rn,
       row_number()over(order by empno)/5.0 division,
       ceil(row_number()over(order by empno)/5.0) grp,
       empno,
       ename
  from emp
Divide by 5.0, not 5 In Oracle, SQL Server and PostgreSQL, 6/5 is integer division and evaluates to 1; ceil(1) is still 1, so rows 5 and 6 would land in the same bucket and the grouping would silently rot. The .0 forces decimal division, so rn 6 becomes 1.2 and rounds up to bucket 2. (SQL Server spells it CEILING; the last bucket here has only four rows, since 14 isn’t a multiple of five — that’s expected.)
12.8

A predefined number of buckets

In plain English The mirror image of the previous recipe: this time you know how many groups you want (four) but not how big each one will be. Split fourteen employees four ways and you get 4, 4, 3, 3.

SQL · NTILE does the arithmetic for you 
select ntile(4)over(order by empno) grp,
       empno,
       ename
  from emp
 order by empno
Fixed size vs fixed count ceil(rn/5.0) answers “how many buckets do I need for groups of five?”. ntile(4) answers “cut this into four equal pieces”. The leftovers in NTILE go to the first buckets, one each, which is why 1 and 2 get four rows and 3 and 4 only get three. This is how quartiles and deciles are computed — and how you find the top quarter of customers by spend.
12.9

Horizontal histograms

In plain English Draw the count as asterisks: three employees in department 10 becomes ***. A string function that pads — or repeats — a character is the whole trick, and every database has one.

SQL · REPEAT 
select deptno,
       repeat('*',count(*)) cnt
  from emp
 group by deptno
SQL · LPAD — pad a single star out to length count(*) 
select deptno,
       lpad('*',count(*),'*') as cnt
  from emp
 group by deptno

/* PostgreSQL insists the length be an integer */
select deptno,
       lpad('*',count(*)::integer,'*') as cnt
  from emp
 group by deptno
SQL · REPLICATE 
select deptno,
       replicate('*',count(*)) cnt
  from emp
 group by deptno
Padding is a hack worth knowing lpad(x, n, pad) normally pads the left of a string to length n. Give it a one-character string and a pad character identical to the string and it degenerates into “repeat this character n times” — which is exactly the behaviour you want. count(*) supplies the n.
12.10

Vertical histograms

In plain English The same picture, grown upwards instead of sideways: five rows tall, one asterisk per department where that department still has an employee left. This is recipe 12.2’s pattern — number the rows, pivot them into columns, drop the NULLs.

SQL · row_number inside the department, MAX to collapse 
select max(deptno_10) d10,
       max(deptno_20) d20,
       max(deptno_30) d30
  from (
select row_number()over(partition by deptno order by empno) rn,
       case when deptno=10 then '*' else null end deptno_10,
       case when deptno=20 then '*' else null end deptno_20,
       case when deptno=30 then '*' else null end deptno_30
  from emp
       ) x
 group by rn
 order by 1 desc, 2 desc, 3 desc
The ORDER BY is doing graphics work Because each column is a stack of stars with NULLs above them, which way the rows read depends on where your database sorts NULLs. order by 1 desc, 2 desc, 3 desc hangs the stars from the bottom in Oracle and PostgreSQL; SQL Server sorts NULLs first, so the book advises leaving DESC off there. A column that grows downwards is still a valid histogram — just upside down.
12.11

Returning columns that aren’t in GROUP BY

In plain English You want “the person with the top salary in each department, and their name” — but MAX(SAL) gives you the number without the person, and adding ENAME to the select list quietly destroys the grouping. Window functions fix this: they compute the departmental maximum without collapsing the rows.

SQL · compute the bounds per row, then filter on them 
select deptno, ename, job, sal,
       case when sal = max_by_dept then 'TOP SAL IN DEPT'
            when sal = min_by_dept then 'LOW SAL IN DEPT'
       end dept_status,
       case when sal = max_by_job  then 'TOP SAL IN JOB'
            when sal = min_by_job  then 'LOW SAL IN JOB'
       end job_status
  from (
select deptno, ename, job, sal,
       max(sal)over(partition by deptno) max_by_dept,
       max(sal)over(partition by job)    max_by_job,
       min(sal)over(partition by deptno) min_by_dept,
       min(sal)over(partition by job)    min_by_job
  from emp
       ) emp_sals
 where sal in (max_by_dept, max_by_job,
               min_by_dept, min_by_job)
The query that looks right and isn’t select ename, max(sal) from emp group by ename returns all fourteen rows with everyone’s own salary, because grouping by ENAME makes each group a single employee. It reads like “find the highest paid employee” and means “find the highest salary for each name”. MAX … OVER states the group you meant.
…and it doesn’t multiply rows either The usual workaround — a self-join to a “max salary per department” inline view — has to be written carefully or it duplicates rows when two people tie. Here two analysts in dept 20 both earn 3000, and both correctly come back once each.
12.12

Simple subtotals

In plain English Salaries summed by job, plus a final line with the sum of everything. In a spreadsheet this is “add a total row”; in SQL it is ROLLUP, and the awkward part is labelling that last row, because its job column is NULL.

SQL · ROLLUP + GROUPING 
select case grouping(job)
            when 0 then job
            else 'TOTAL'
       end job,
       sum(sal) sal
  from emp
 group by rollup(job)
SQL · WITH ROLLUP + COALESCE 
select coalesce(job,'TOTAL') job,
       sum(sal) sal
  from emp
 group by job with rollup
SQL · ROLLUP(JOB) after GROUP BY 
select coalesce(job,'TOTAL') job,
       sum(sal) sal
  from emp
 group by rollup(job)
What GROUPING() actually answers “Did ROLLUP invent this NULL?” It returns 1 for rows the rollup created and 0 for rows the ordinary GROUP BY produced. That matters because a genuine NULL in the data is indistinguishable from a subtotal marker — COALESCE(job,'TOTAL') is shorter but it would also relabel a real NULL job as TOTAL.
12.13

Subtotals for every combination of expressions

In plain English Now you want the lot: salaries by dept and job, totals by dept alone, totals by job alone, and a grand total — eighteen rows of a report where every row says what it is. CUBE produces all the combinations; GROUPING() labels them.

SQL · CUBE + the two grouping bits glued together 
select deptno,
       job,
       case grouping(deptno)||grouping(job)
            when '00' then 'TOTAL BY DEPT AND JOB'
            when '10' then 'TOTAL BY JOB'
            when '01' then 'TOTAL BY DEPT'
            when '11' then 'GRAND TOTAL FOR TABLE'
       end category,
       sum(sal) sal
  from emp
 group by cube(deptno,job)
 order by grouping(job),grouping(deptno)

/* DB2 needs the cast before it can concatenate */
select deptno,
       job,
       case cast(grouping(deptno) as char(1))||
            cast(grouping(job)    as char(1))
            when '00' then 'TOTAL BY DEPT AND JOB'
            when '10' then 'TOTAL BY JOB'
            when '01' then 'TOTAL BY DEPT'
            when '11' then 'GRAND TOTAL FOR TABLE'
       end category,
       sum(sal) sal
  from emp
 group by cube(deptno,job)
SQL · CAST to CHAR(1) and use + instead of || 
select deptno,
       job,
       case cast(grouping(deptno) as char(1))+
            cast(grouping(job)    as char(1))
            when '00' then 'TOTAL BY DEPT AND JOB'
            when '10' then 'TOTAL BY JOB'
            when '01' then 'TOTAL BY DEPT'
            when '11' then 'GRAND TOTAL FOR TABLE'
       end category,
       sum(sal) sal
  from emp
 group by deptno,job with cube
 order by grouping(job),grouping(deptno)
SQL · concat() 
select deptno,
       job,
       case concat(cast(grouping(deptno) as char(1)),
                   cast(grouping(job)    as char(1)))
            when '00' then 'TOTAL BY DEPT AND JOB'
            when '10' then 'TOTAL BY JOB'
            when '01' then 'TOTAL BY DEPT'
            when '11' then 'GRAND TOTAL FOR TABLE'
       end category,
       sum(sal) sal
  from emp
 group by cube(deptno,job)
 order by grouping(job),grouping(deptno)
SQL · no CUBE, so four UNION ALLs 
select deptno, job,
       'TOTAL BY DEPT AND JOB' as category,
       sum(sal) as sal
  from emp
 group by deptno, job
 union all
select null, job, 'TOTAL BY JOB', sum(sal)
  from emp
 group by job
 union all
select deptno, null, 'TOTAL BY DEPT', sum(sal)
  from emp
 group by deptno
 union all
select null, null, 'GRAND TOTAL FOR TABLE', sum(sal)
  from emp
Two bits, four labels GROUPING(DEPTNO) and GROUPING(JOB) are a two-bit code, which is why they are glued into a string: 00 = both columns real, 10 = job was rolled up (so it is a job total), 01 = deptno was rolled up, 11 = both rolled up, i.e. the grand total. Order in the concatenation matters — grouping(deptno)||grouping(job) is not the same string as the reverse.
Or just name the groups you want CUBE always returns every combination. GROUPING SETS lets you list them, so you can drop a level without rewriting the query: 
  from emp
 group by grouping sets ((deptno),(job),(deptno,job),())

/* every level except the grand total */
 group by grouping sets ((deptno),(job),(deptno,job))

/* drop the deptno subtotal as well */
 group by grouping sets ((job),(deptno,job),())
The empty parentheses are the grand total. Remove them and the grand total disappears; remove (deptno) and the per-department subtotals go.
12.14

Identifying rows that are not subtotals

In plain English The same CUBE report, but instead of pretty labels you want two honest columns of 0 and 1 that a program — or your own WHERE clause — can filter on.

SQL · grouping() as a pair of flags 
select deptno,
       job,
       grouping(deptno) deptno_subtotals,
       grouping(job)    job_subtotals,
       sum(sal) sal
  from emp
 group by cube(deptno,job)
 order by 3, 4

/* SQL Server spells the rollup differently, nothing else changes */
select deptno,
       job,
       grouping(deptno) deptno_subtotals,
       grouping(job)    job_subtotals,
       sum(sal) sal
  from emp
 group by deptno,job with cube
Read it as a bitmap deptno_subtotals = 0 and job_subtotals = 1 means “job was rolled up, and deptno is NULL because of that” — a department subtotal. Swap the zeros and ones and you have a job subtotal. Both zero: a genuine dept/job cell. Both one: the grand total. To get a report of raw cells only, add where grouping(deptno)=0 and grouping(job)=0 around the whole thing.
12.15

Using CASE expressions to flag rows

In plain English Turn one text column into a row of tick boxes: a 1 in the IS_CLERK column for clerks, a 1 in IS_ANALYST for analysts, zeros everywhere else. Handy for eyeballing data and for feeding an analysis tool that prefers numbers to words.

SQL · one CASE per possible value 
select ename,
       case when job = 'CLERK'     then 1 else 0 end as is_clerk,
       case when job = 'SALESMAN'  then 1 else 0 end as is_sales,
       case when job = 'MANAGER'   then 1 else 0 end as is_mgr,
       case when job = 'ANALYST'   then 1 else 0 end as is_analyst,
       case when job = 'PRESIDENT' then 1 else 0 end as is_prez
  from emp
 order by 2,3,4,5,6
This is recipe 12.1 with the SUM removed A flag column and a pivot column are the same CASE. Add sum() and group by and the flags collapse into counts — which is exactly how sum(is_clerk) becomes “how many clerks”. Nothing new to learn, just the half-built version kept visible.
12.16

Creating a sparse matrix

In plain English A grid of every department against every job, with a name dropped into the cell where they meet and nothing anywhere else. Most cells are empty — hence “sparse”.

SQL · pure CASE, no aggregation at all 
select case deptno when 10 then ename end as d10,
       case deptno when 20 then ename end as d20,
       case deptno when 30 then ename end as d30,
       case job when 'CLERK'     then ename end as clerks,
       case job when 'MANAGER'   then ename end as mgrs,
       case job when 'PRESIDENT' then ename end as prez,
       case job when 'ANALYST'   then ename end as anals,
       case job when 'SALESMAN'  then ename end as sales
  from emp

/* densify: number the rows per department, then MAX them into shape */
select max(case deptno when 10 then ename end) d10,
       max(case deptno when 20 then ename end) d20,
       max(case deptno when 30 then ename end) d30,
       max(case job when 'CLERK'     then ename end) clerks,
       max(case job when 'MANAGER'   then ename end) mgrs,
       max(case job when 'PRESIDENT' then ename end) prez,
       max(case job when 'ANALYST'   then ename end) anals,
       max(case job when 'SALESMAN'  then ename end) sales
  from (
select deptno, job, ename,
       row_number()over(partition by deptno order by empno) rn
  from emp
       ) x
 group by rn
Sparse vs dense The first query is a SELECT that reshapes without aggregating, so each employee keeps its own row and the grid stays ragged. Adding row_number() per department and MAX … group by rn packs the names into the top-left corner — the same “dense” version the book shows for 12.2, with two dimensions instead of one.
12.17

Grouping rows by units of time

In plain English A transaction log with one row per second. Summarise it in five-second blocks: when the block started, when it ended, and how many transactions happened in it. There is no “five-second” column in the table — you have to manufacture the group.

SQL · bucket by id, then aggregate 
select ceil(trx_id/5.0) as grp,
       min(trx_date)    as trx_start,
       max(trx_date)    as trx_end,
       sum(trx_cnt)     as total
  from trx_log
 group by ceil(trx_id/5.0)
 order by 1
SQL · when there is no id to divide: bucket the clock instead 
select hr, grp, sum(trx_cnt) total
  from (
select trx_date, trx_cnt,
       to_number(to_char(trx_date,'hh24')) hr,
       ceil(to_number(to_char(trx_date-1/24/60/60,'miss'))/5.0) grp
  from trx_log
       ) x
 group by hr,grp
 order by hr,grp

/* Oracle/DB2 alternative: a running total and a per-group total on every row */
select trx_id, trx_date, trx_cnt,
       sum(trx_cnt)over(partition by ceil(trx_id/5.0)
                        order by trx_date
                        range between unbounded preceding
                          and current row) running_total,
       sum(trx_cnt)over(partition by ceil(trx_id/5.0)) total,
       case when mod(trx_id,5.0) = 0 then 'X' end grp_end
  from trx_log
Two ways to invent an interval If the rows carry a sequential id, ceil(trx_id/5.0) is enough — it is recipe 12.7 applied to time. If they don’t, take the seconds past the hour (to_char(…,'miss')) and bucket those, keeping the hour in the GROUP BY so a log spanning hours doesn’t merge 10:00:03 with 11:00:01. The 0.5-second subtraction in the book’s listing is there to stop a transaction sitting exactly on a boundary from starting a new bucket.
12.18

Aggregating over different partitions at once

In plain English One row per employee showing three different counts side by side: how many people are in their department, how many share their job, and how many employees exist at all. Three different groupings, one query, no self-joins.

SQL · three OVER clauses, three answers 
select ename,
       deptno,
       count(*)over(partition by deptno) deptno_cnt,
       job,
       count(*)over(partition by job)    job_cnt,
       count(*)over()                    total
  from emp
 order by deptno, ename
The famous gotcha count(*)over() counts the rows that survived WHERE, because window functions run after it. Add where deptno <> 10 and TOTAL becomes 11, not 14 — every row is recomputed against the smaller set. To filter on a window result you must wrap the query in an inline view and filter outside it.
Empty OVER () means “everything” partition by deptno = the department; partition by job = the job; () = the whole table. Add an order by inside the parentheses and the frame silently changes from the entire partition to “everything up to the current row” — a running total. That single word is the difference between a total and a running total.
12.19

Aggregating over a moving range of values

In plain English For each employee, how much salary did the company take on in the 90 days before they were hired? Not a running total from the beginning of time — a moving window that reaches back ninety days and no further.

SQL · RANGE BETWEEN … PRECEDING 
select hiredate,
       sal,
       sum(sal)over(order by hiredate
                    range between 90 preceding
                      and current row) spending_pattern
  from emp
 order by hiredate
SQL · order by a number, not a date 
/* DB2: cannot ORDER BY a date when the frame is numeric */
select hiredate,
       sal,
       sum(sal)over(order by days(hiredate)
                    range between 90 preceding
                      and current row) spending_pattern
  from emp

/* MySQL: the interval goes in the frame */
select hiredate,
       sal,
       sum(sal)over(order by hiredate
                    range interval 90 day preceding) spending_pattern
  from emp
SQL · no window frame? use a correlated subquery 
select e.hiredate,
       e.sal,
       (select sum(d.sal)
          from emp d
         where d.hiredate between e.hiredate-90
                              and e.hiredate) as spending_pattern
  from emp e
 order by 1
Follow three of the numbers 17-DEC-2010: 800 — nobody was hired before, so the window holds one row. 20-FEB-2011: 2400 — 1600 plus the 800 from 66 days earlier. 09-DEC-2012: 3000 — the window looked back 90 days and found nobody, so it restarts with just that one salary. That restart is the proof it is a moving range and not a running total.
Peers share the frame Two employees were hired on the same day (03-DEC-2011, 950 and 3000) and both get the same 11700. RANGE frames by value, so every row with the same HIREDATE sees exactly the same set of rows. ROWS BETWEEN would instead count physical rows and could split the pair.
12.20

Pivoting a result set that has subtotals

In plain English The finale: a report of managers down the side, departments across the top, salary totals in the cells, plus a per-department subtotal row and a grand total. It is ROLLUP (for the subtotals) and a pivot (for the shape) in one query — and the subtle part is not counting the same money twice.

SQL · ROLLUP inside, pivot outside 
select mgr,
       sum(case deptno when 10 then sal else 0 end) dept10,
       sum(case deptno when 20 then sal else 0 end) dept20,
       sum(case deptno when 30 then sal else 0 end) dept30,
       sum(case flag when '11' then sal else null end) total
  from (
select deptno, mgr, sum(sal) sal,
       cast(grouping(deptno) as char(1))||
       cast(grouping(mgr)    as char(1)) flag
  from emp
 where mgr is not null
 group by rollup(deptno,mgr)
       ) x
 group by mgr
 order by coalesce(mgr,9999)
SQL · WITH ROLLUP and + for concatenation 
select mgr,
       sum(case deptno when 10 then sal else 0 end) dept10,
       sum(case deptno when 20 then sal else 0 end) dept20,
       sum(case deptno when 30 then sal else 0 end) dept30,
       sum(case flag when '11' then sal else null end) total
  from (
select deptno, mgr, sum(sal) sal,
       cast(grouping(deptno) as char(1))+
       cast(grouping(mgr)    as char(1)) flag
  from emp
 where mgr is not null
 group by deptno,mgr with rollup
       ) x
 group by mgr
 order by coalesce(mgr,9999)
SQL · concat() and ROLLUP(a,b) 
select mgr,
       sum(case deptno when 10 then sal else 0 end) dept10,
       sum(case deptno when 20 then sal else 0 end) dept20,
       sum(case deptno when 30 then sal else 0 end) dept30,
       sum(case flag when '11' then sal else null end) total
  from (
select deptno, mgr, sum(sal) sal,
       concat(cast(grouping(deptno) as char(1)),
              cast(grouping(mgr)    as char(1))) flag
  from emp
 where mgr is not null
 group by rollup(deptno,mgr)
       ) x
 group by mgr
 order by coalesce(mgr,9999)
Why the columns use else 0 but TOTAL uses else null Look at what ROLLUP(deptno,mgr) produces: real cells (flag 00), a per-department subtotal (flag 01, MGR NULL) and one grand total (flag 11). Summing the department columns with else 0 adds real cells and subtotal rows, which is what you see in the bottom row. If the TOTAL column did the same it would add the real cells, the subtotals and the grand total — money counted three times. Selecting only flag 11 picks the single grand-total row and nothing else.
Order of the ROLLUP columns is load-bearing rollup(deptno,mgr) makes department the outer level, so the flag 01 means “department subtotal”. Write group by mgr,deptno with rollup and the levels swap: you would get subtotals per manager instead, and the whole report would say something different. WHERE mgr is not null is doing work too — KING has no manager, and the report is about employees who report to someone.
12.21

Summing up

In plain English A database exists to store data, but sooner or later somebody asks for it in a shape the database doesn’t have. This chapter is that translation service — and the reason it matters beyond one report is that the same moves are the foundation of a data warehouse, where “wide, pre-aggregated, human-readable” is the whole point.

If you remember three things 1. CASE plus an aggregate is the pivot, in both directions. 2. row_number() over (partition by …) is what lets a pivot produce many rows instead of one. 3. GROUPING() is how you tell a subtotal from real data — and GROUPING SETS lets you ask for exactly the totals you want instead of all of them.

Hierarchical Queries

Five recipes about data that points at itself: every employee’s MGR column holds another employee’s EMPNO, so the table is really a tree wearing a table’s clothes. The answer everywhere is a recursive query — walk up or down the tree one level per pass.

The short version

Chapter 13 in plain English

A hierarchy is stored as a self-reference: a row names another row in the same table as its parent. One level is an ordinary self-join. More than one level is where it gets interesting — you cannot know in advance how many joins to write, because the depth is data, not schema. That is exactly what CONNECT BY and recursive WITH are for.

👪

One level is a self-join

from emp a, emp b where a.mgr = b.empno — employee to manager, straight out of Chapter 3. It drops the top of the tree, because NULL = anything is never true.

🔁

Recursion is a UNION ALL

Anchor the starting row, then union all a query that joins the table to the result you already have. It repeats until nothing new comes back.

📏

LEVEL / DEPTH is the row’s height

Start at 0 (or 1 in Oracle) and add one per hop. It gives you indentation, filtering (“only the full path”) and the root/leaf tests.

🧵

Paths are strings you build

SYS_CONNECT_BY_PATH or x.tree || '-->' || e.ename glues the ancestors onto each row — the classic “KING - JONES - SCOTT” line.

🔭

Start at the top or the bottom

Recursive WITH can walk up from a leaf (MILLER → CLARK → KING) or down from the root (KING → everyone). CONNECT BY PRIOR just reverses direction.

🍃

Leaf, branch, root

Leaf = nobody works for them. Branch = a manager who has a manager. Root = no manager. Three COUNTs (or Oracle’s CONNECT_BY_ISLEAF) classify every row.

Recipe by recipe

13.1 – 13.6, explained simply

Five recipes and a summary.

13.1

Expressing a parent-child relationship

In plain English Print “FORD works for JONES” for every employee. The manager is not stored somewhere else — he is another row in the same table, and MGR holds his employee number. So join the table to itself and read the name from the second copy.

SQL · self-join, concatenate with || 
select a.ename || ' works for ' || b.ename as emps_and_mgrs
  from emp a, emp b
 where a.mgr = b.empno
SQL · concat() 
select concat(a.ename, ' works for ', b.ename) as emps_and_mgrs
  from emp a, emp b
 where a.mgr = b.empno
SQL · + for concatenation 
select a.ename + ' works for ' + b.ename as emps_and_mgrs
  from emp a, emp b
 where a.mgr = b.empno
The row that keeps disappearing: KING The self-join is an equi-join on a.mgr = b.empno, and KING’s MGR is NULL. NULL = anything is never true, so the root of the tree falls out and you get 13 rows instead of 14. A scalar subquery in the select list keeps him (it returns NULL instead of dropping the row). To keep him with a join, make it an outer join — left join in the ANSI syntax, or Oracle’s old (+) marker on the manager side.
13.2

Child, parent, grandparent

In plain English MILLER works for CLARK, and CLARK works for KING. You want the whole chain on one line: MILLER-->CLARK-->KING. Two self-joins could do it — but the point of the recipe is the general answer, one that still works when the chain is four deep or seven.

SQL · recursive WITH, walking up 
with x (tree, mgr, depth) as
(
select cast(ename as varchar(100)),
       mgr, 0
  from emp
 where ename = 'MILLER'
 union all
select cast(x.tree || '-->' || e.ename as varchar(100)),
       e.mgr, x.depth + 1
  from emp e, x
 where x.mgr = e.empno
)
select tree leaf___branch___root
  from x
 where depth = 2

SQL Server concatenates with + instead of ||; swap the operator and nothing else changes. The cast is needed because the two halves of a UNION ALL must agree on a type and a width.

SQL · the RECURSIVE keyword is required 
with recursive x (tree, mgr, depth) as
(
select cast(ename as char(100)),
       mgr, 0
  from emp
 where ename = 'MILLER'
 union all
select cast(concat(x.tree,'-->',e.ename) as char(100)),
       e.mgr, x.depth + 1
  from emp e, x
 where x.mgr = e.empno
)
select tree leaf___branch___root
  from x
 where depth = 2
SQL · CONNECT BY does it without a join 
select ltrim(
         sys_connect_by_path(ename,'-->'),
       '-->') leaf___branch___root
  from emp
 where level = 3
 start with ename = 'MILLER'
connect by prior mgr = empno
Read the recursion as two paragraphs The top half of the UNION ALL is the anchor: it runs once, and it decides where you start — here the leaf, MILLER, at depth 0. The bottom half is the step: it joins emp to the rows you already have and produces the next generation at depth + 1. The engine repeats the step, feeding each round its own output, until a round matches no rows. That is the entire mechanism, and every hierarchical query in this chapter is that pattern with the join flipped or the filter changed.
Oracle’s version is the same walk, backwards in the sentence start with ename = 'MILLER' is the anchor. connect by prior mgr = empno is the step: “take the MGR of the row I just produced and find the EMPNO equal to it”. PRIOR means “the previous row up the chain”, so think of connect by prior as the join condition written from the child’s point of view. LEVEL counts the hops, starting at 1 for the anchor — which is why the filter is level = 3 where the recursive version filters depth = 2.
13.3

A hierarchical view of a whole table

In plain English Not one chain — the entire org chart, every path from KING down to every leaf, written out as KING - JONES - SCOTT - ADAMS. Fourteen rows, one per employee, each showing the route from the top to that person.

SQL · walk downwards from the root 
with x (ename, empno) as
(
select cast(ename as varchar(100)), empno
  from emp
 where mgr is null
 union all
select cast(x.ename || ' - ' || e.ename as varchar(100)),
       e.empno
  from emp e, x
 where e.mgr = x.empno
)
select ename as emp_tree
  from x
 order by 1

SQL Server uses +; the anchor is where mgr is null, which finds the root without naming KING.

SQL · with recursive 
with recursive x (ename, empno) as
(
select cast(ename as char(100)), empno
  from emp
 where mgr is null
 union all
select cast(concat(x.ename,' - ',e.ename) as char(100)),
       e.empno
  from emp e, x
 where e.mgr = x.empno
)
select ename as emp_tree
  from x
 order by 1
SQL · START WITH + SYS_CONNECT_BY_PATH 
select ltrim(
         sys_connect_by_path(ename,' - '),
       ' - ') emp_tree
  from emp
 start with mgr is null
connect by prior empno = mgr
 order by 1
Anchor on the root, not on a name Recipe 13.2 hard-codes ename = 'MILLER'. Here the anchor is where mgr is null — “whoever has no boss” — so the query finds the root itself. Drop a new CEO into the table and it still works. (And if there were two roots, you would get two trees, which is usually what you want.)
The dots are 2 × LEVEL lpad('.', 2*level, '.') || ename is not part of any hierarchy feature — it is just padding computed from the depth, which is why the output steps inward by two dots per generation. It is the cheapest way to make a recursive result look like a tree, and it shows that LEVEL is available as a normal value you can do arithmetic on.
13.4

All child rows for a given parent

In plain English Everyone under JONES, directly or through someone else — JONES, SCOTT, ADAMS, FORD, SMITH — including JONES himself. No formatting, no paths: just the subtree as rows. This is the query behind “show me the whole team” on any org-chart screen.

SQL · anchor on JONES, then join children 
with x (ename, empno) as
(
select ename, empno
  from emp
 where ename = 'JONES'
 union all
select e.ename, e.empno
  from emp e, x
 where x.empno = e.mgr
)
select ename
  from x

MySQL needs with recursive. Note the join direction — x.empno = e.mgr — which is the mirror image of 13.2’s walk upwards.

SQL · START WITH makes JONES the root of this walk 
select ename
  from emp
 start with ename = 'JONES'
connect by prior empno = mgr
Which side of the equals you put PRIOR on decides the direction connect by prior empno = mgr walks down: take my employee number, find rows whose manager is that. connect by prior mgr = empno walks up: take my manager, find that person. Same clause, one identifier moved, opposite direction — and it is the single most common thing to get wrong when writing these by hand.
13.5

Leaf, branch or root

In plain English Label every node: a leaf has nobody working under them (SMITH, MILLER, and the other salesmen), a branch is a manager who also has a manager (JONES, BLAKE, SCOTT…), and the root is the one at the top with no manager (KING). Return 1 or 0 for each.

SQL · three correlated subqueries 
select e.ename,
       (select sign(count(*)) from emp d
         where 0 =
           (select count(*) from emp f
             where f.mgr = e.empno)) as is_leaf,
       (select sign(count(*)) from emp d
         where d.mgr = e.empno
           and e.mgr is not null) as is_branch,
       (select sign(count(*)) from emp d
         where d.empno = e.empno
           and d.mgr is null) as is_root
  from emp e
 order by 4 desc, 3 desc

SIGN(COUNT(*)) squeezes any count down to 0 or 1 — otherwise a busy manager would score 5 instead of “yes”.

SQL · CONNECT_BY_ISLEAF and CONNECT_BY_ROOT 
select ename,
       connect_by_isleaf is_leaf,
       (select count(*) from emp e
         where e.mgr = emp.empno
           and emp.mgr is not null
           and rownum = 1) is_branch,
       decode(ename,connect_by_root(ename),1,0) is_root
  from emp
 start with mgr is null
connect by prior empno = mgr
 order by 4 desc, 3 desc

CONNECT_BY_ROOT(ename) returns the name at the top of the current path; comparing it with the row’s own name flags the root. rownum = 1 does the job SIGN does in the other dialects.

Tree vs recursive modelling In EMP the root is marked with NULL. The alternative is a recursive hierarchy, where KING’s MGR would be KING’s own EMPNO and no row would be NULL. Much of the book’s advice — anchor on where mgr is null, test leaves and roots with NULL checks — assumes the tree model. If your data is the recursive kind, joining on empno = mgr never terminates by itself and you can get an endless loop; you have to add a depth limit or a path check.
Notice that the whole hierarchy is not needed All three flags are answered by counting rows in EMP — “does anyone point at me?” and “do I point at anyone?”. Only the Oracle recipe actually walks the tree, because its built-in functions require a CONNECT BY clause to exist. For a plain classification of node types, self-referencing subqueries are enough and they work everywhere.
13.6

Summing up

In plain English Recursive CTEs arriving in MySQL was the last domino: every major database can now express a hierarchy the same way, and long-standing Oracle-only tricks like CONNECT BY have a portable equivalent. That matters more than it sounds, because hierarchical data turns up in places nobody planned for — an approval chain, a folder tree, a parts list, a thread of replies.

The portable shape, one last time with x as (anchor union all step), where the anchor picks your starting rows and the step joins the table back to x. Direction is the join; depth is a counter you increment; the path is a string you concatenate. Then filter on the counter, sort by it, or indent with it.

14.1

Cross-tab reports with SQL Server’s PIVOT

In plain English You want the department counts across the top — 3, 5, 6, 0 — without writing a CASE for every column. SQL Server has a keyword that does recipe 12.1 for you: name the column to spread, list the values to spread it over, and say what to aggregate.

SQL · SQL Server — the pivot in one clause 
select [10] as dept_10,
       [20] as dept_20,
       [30] as dept_30,
       [40] as dept_40
  from (select deptno, empno from emp) driver
 pivot (
    count(driver.empno)
    for driver.deptno in ( [10],[20],[30],[40] )
 ) as empPivot

/* the same answer the portable way — compare the two */
select sum(case deptno when 10 then 1 else 0 end) as dept_10,
       sum(case deptno when 20 then 1 else 0 end) as dept_20,
       sum(case deptno when 30 then 1 else 0 end) as dept_30,
       sum(case deptno when 40 then 1 else 0 end) as dept_40
  from emp
SQL · pivot on a joined inline view, so the columns are names 
select [ACCOUNTING] as ACCOUNTING,
       [SALES]      as SALES,
       [RESEARCH]   as RESEARCH,
       [OPERATIONS] as OPERATIONS
  from (
          select d.dname, e.empno
            from emp e, dept d
           where e.deptno = d.deptno
        ) driver
  pivot (
    count(driver.empno)
    for driver.dname in ([ACCOUNTING],[SALES],[RESEARCH],[OPERATIONS])
  ) as empPivot
The bracketed list is the column list for driver.deptno in ([10],[20],[30],[40]) does two jobs: it says which values to aggregate, and it becomes the output column names (brackets stripped). If you do not alias them in the SELECT, the columns come out called 10, 20… which is why the book aliases them to DEPT_10.
The catch, and it is a real one Because the values live in the query text, the number of columns is fixed at parse time. Add department 50 tomorrow and the report silently ignores it — you must edit the SQL. The CASE version has exactly the same problem, so this is not a PIVOT flaw; it is the nature of cross-tabs in SQL.
14.2

Unpivoting with SQL Server’s UNPIVOT

In plain English Go back the other way: one wide row with four department columns becomes four narrow rows of DNAME and CNT. It is recipe 14.1’s output being taken apart again, using the mirror-image keyword.

SQL · something to unpivot, then UNPIVOT it 
select DNAME, CNT
  from (
    select [ACCOUNTING] as ACCOUNTING,
           [SALES]      as SALES,
           [RESEARCH]   as RESEARCH,
           [OPERATIONS] as OPERATIONS
      from (
              select d.dname, e.empno
                from emp e, dept d
               where e.deptno = d.deptno
           ) driver
     pivot (
       count(driver.empno)
       for driver.dname in ([ACCOUNTING],[SALES],[RESEARCH],[OPERATIONS])
     ) as empPivot
) new_driver
unpivot (cnt for dname in (ACCOUNTING,SALES,RESEARCH,OPERATIONS)
) as un_pivot
Read unpivot (cnt for dname in (…)) aloud “Take those four columns, produce one row per column, put the value in CNT and the column name in DNAME.” There is no aggregate anywhere — unpivoting is pure reshaping, so it cannot invent or merge rows.
Unpivot quietly drops NULLs A NULL in one of the four columns produces no row at all, not a row with a NULL count. (The book’s data has OPERATIONS = 0, not NULL, so all four rows survive.) If you need the NULL rows too, you want the portable answer instead: a UNION ALL of one SELECT per column, which keeps them.
14.3

Transposing with Oracle’s MODEL clause

In plain English MODEL lets you treat a result set as a spreadsheet: name some arrays, address their cells by an index value, and write rules that assign to those cells. Here the “cells” are three arrays — D10, D20, D30 — and the rule zeroes out everything that isn’t the matching department.

SQL · Oracle MODEL — arrays, an index, and three rules 
select max(d10) d10,
       max(d20) d20,
       max(d30) d30
  from (
select d10, d20, d30
  from ( select deptno, count(*) cnt from emp group by deptno )
 model
  dimension by (deptno d)
   measures (deptno, cnt d10, cnt d20, cnt d30)
   rules (
     d10[any] = case when deptno[cv()]=10 then d10[cv()] else 0 end,
     d20[any] = case when deptno[cv()]=20 then d20[cv()] else 0 end,
     d30[any] = case when deptno[cv()]=30 then d30[cv()] else 0 end
  )
       )
The three subclauses, in order measures (… d10, cnt d20, cnt d30) declares the arrays — all three are copies of CNT, which is why they start out identical. dimension by (deptno d) is the index: the arrays are keyed by DEPTNO, so d10[10] means “the D10 cell whose DEPTNO is 10” and evaluates to 3. rules (…) assigns to those cells: d10[any] means “for every row”, storing the count when the department matches and 0 when it doesn’t. cv() is “the current value of the dimension”.
The book says it plainly: this is a misuse The authors point out that MODEL was never meant for transposing result sets — it exists for forecasting, allocation and iterative calculations. The recipe is here to show the clause off, not because you should reach for it. CASE and PIVOT are the right tools; MODEL is the interesting wrong one.
14.4

Extracting string elements from unfixed locations

In plain English Log lines like xxxxxabc[867]xxx[-]xxxx[5309]xxxxx contain exactly three values wrapped in square brackets, and they are never in the same place twice. So don’t count characters — find the brackets and cut between them.

SQL · Oracle — INSTR finds, SUBSTR cuts 
select substr(msg,
         instr(msg,'[',1,1)+1,
         instr(msg,']',1,1)-instr(msg,'[',1,1)-1) first_val,
       substr(msg,
         instr(msg,'[',1,2)+1,
         instr(msg,']',1,2)-instr(msg,'[',1,2)-1) second_val,
       substr(msg,
         instr(msg,'[',-1,1)+1,
         instr(msg,']',-1,1)-instr(msg,'[',-1,1)-1) last_val
  from V
Anatomy of instr(string, char, start, occurrence) instr(msg,'[',1,2) = start at position 1, find the 2nd [. instr(msg,'[',-1,1) = start at the end and search backwards, so it finds the last [ — that is how “the third value, wherever it is” gets addressed without knowing how long the string is.
Why +1 and −1 substr starts at the position you give it, so starting at the bracket includes the bracket. Add 1 and you start just after it. And the length you pass is close − open, which still spans the closing bracket, so subtract 1. The page shows all three stages: both brackets present (no adjustment), opening bracket only (+1 alone), and with both adjustments the clean value.
14.5

Days in a year, the Oracle way

In plain English Chapter 9 found the number of days in a year by asking February how long it is. Oracle offers a shortcut: jump to 31 December and ask what day of the year that is — 365 or 366, by definition.

SQL · Oracle — truncate, add a year, step back one day 
select 'Days in 2021: '||
       to_char(add_months(trunc(sysdate,'y'),12)-1,'DDD') as report
  from dual
 union all
select 'Days in 2020: '||
       to_char(add_months(trunc(to_date('01-SEP-2020'),'y'),12)-1,'DDD')
  from dual

/* the three steps, separately */
select trunc(to_date('01-SEP-2020'),'y') first_of_year from dual

select add_months(trunc(to_date('01-SEP-2020'),'y'),12)   before_subtraction,
       add_months(trunc(to_date('01-SEP-2020'),'y'),12)-1 after_subtraction
  from dual

select to_char(add_months(trunc(to_date('01-SEP-2020'),'y'),12)-1,'DDD') num_days
  from dual
Four functions, one sentence trunc(d,'y') snaps to 1 January. add_months(…,12) jumps to 1 January of the next year. -1 steps back to 31 December of the year you started in. to_char(…,'DDD') prints the day-of-year number, which for 31 December is the length of the year. The leap-year test comes free with the calendar.
14.6

Finding mixed alphanumeric strings

In plain English Out of a list of strings, keep only the ones that contain both a letter and a digit: 1010 switch and findRow 55 yes; 333, threes and 3453430278 no. No regular expressions needed if your database has TRANSLATE.

SQL · Oracle (also DB2 and PostgreSQL) 
with v as (
select 'ClassSummary' strings from dual union
select '3453430278'           from dual union
select 'findRow 55'           from dual union
select '1010 switch'          from dual union
select '333'                  from dual union
select 'threes'               from dual
)
select strings, translated
  from (
select strings,
       translate(
         strings,
         'abcdefghijklmnopqrstuvwxyz0123456789',
         rpad('#',26,'#')||rpad('*',10,'*')) translated
  from v
       )
 where instr(translated,'#') > 0
   and instr(translated,'*') > 0
How translate differs from replace replace swaps one string for another. translate works character by character, using position: character 1 of the search string maps to character 1 of the replacement string, and so on. So the 26 letters map to 26 #s and the 10 digits to 10 *s — and rpad('#',26,'#') is just a lazy way to write 26 hashes. Anything not listed (space, punctuation) is left alone, which is why '1010 switch' comes out as **** ######.
14.7

Converting whole numbers to binary

In plain English Print each salary in base 2 — 800 becomes 1100100000. There is no to_binary function in Oracle, so the book builds a loop out of MODEL: take the remainder mod 2, prepend it, halve the number, repeat until nothing is left.

SQL · Oracle — a loop hidden in a scalar subquery 
select ename,
       sal,
       (
       select bin
         from dual
        model
        dimension by ( 0 attr )
        measures ( sal num,
                   cast(null as varchar2(30)) bin,
                  '0123456789ABCDEF' hex
                 )
        rules iterate (10000) until (num[0] <= 0) (
          bin[0] = substr(hex[cv()],mod(num[cv()],2)+1,1)||bin[cv()],
          num[0] = trunc(num[cv()]/2)
        )
       ) sal_binary
  from emp
The algorithm in two lines mod(num,2) gives the next bit; substr(hex, bit+1, 1) turns that bit into a character (hex is just '0123456789ABCDEF', so index 1 is 0, index 2 is 1). Prepending it to bin builds the answer right-to-left, and trunc(num/2) halves the number. The until (num[0] <= 0) stops the loop, and iterate (10000) is only a safety cap.
The book’s own verdict: use a function The authors say outright that a stored function would be more appropriate — this recipe is an adaptation of Tom Kyte’s TO_BASE. It is here to show that MODEL can run procedural logic while staying set-based, not because you should compute binary in SQL. Note also that hex being a 16-character string is what makes the same skeleton capable of base 16.
14.8

Pivoting a ranked result set

In plain English Three columns — the top three earners, the next three, and everyone else — with names and salaries lined up inside each column. It is recipe 12.2’s pivot, but the row number comes from a ranking instead of a name order.

SQL · rank, bucket, re-rank inside the bucket, pivot 
select max(case grp when 1 then rpad(ename,6) ||
                     ' ('|| sal ||')' end) top_3,
       max(case grp when 2 then rpad(ename,6) ||
                    ' ('|| sal ||')' end) next_3,
       max(case grp when 3 then rpad(ename,6) ||
                     ' ('|| sal ||')' end) rest
  from (
select ename,
       sal,
       rnk,
       case when rnk <= 3 then 1
            when rnk <= 6 then 2
            else                  3
       end grp,
       row_number()over (
         partition by case when rnk <= 3 then 1
                           when rnk <= 6 then 2
                           else                  3
                       end
             order by sal desc, ename
       ) grp_rnk
  from (
select ename,
       sal,
       dense_rank()over(order by sal desc) rnk
  from emp
       ) x
       ) y
 group by grp_rnk
Why two rankings DENSE_RANK() over (order by sal desc) is the global standing, so rnk <= 3 / <= 6 / else slices it into buckets. But a bucket cannot be pivoted until its rows are numbered within the bucket — that is the row_number() over (partition by …case… order by sal desc, ename). Group by grp_rnk and the first row of each bucket lines up, then the second, and so on. The ragged bottoms (4 rows in TOP_3 because of the 3000 tie, 7 in REST) are just MAX filling empty cells with NULL.
One pass through the table emp is read exactly once — everything after inline view X is arithmetic on values already in hand. The book makes this point explicitly: no self-joins, no temp tables, and for a report of this shape that is the whole performance story. rpad(ename,6) plus ' ('||sal||')' is pure cosmetics, to make the parentheses line up in a monospaced report.
14.9

A column header inside a double pivot

In plain English Two tables — one of researchers, one of app developers — stacked into a single report of two columns, where each department appears once as a heading and its people are indented underneath it. Two pivots in one query: rows to columns, and a running number to keep the two sides aligned.

SQL · Oracle — stack, number, pivot 
select max(decode(flag2,0,it_dept)) research,
       max(decode(flag2,1,it_dept)) apps
  from (
select sum(flag1)over(partition by flag2
                      order by flag1,rownum) flag,
       it_dept, flag2
  from (
select 1 flag1, 0 flag2,
       decode(rn,1,to_char(deptno),' '||ename) it_dept
  from (
select x.*, y.id,
       row_number()over(partition by x.deptno order by y.id) rn
  from (
select deptno,
       ename,
       count(*)over(partition by deptno) cnt
  from it_research
       ) x,
       (select level id from dual connect by level <= 2) y
       )
 where rn <= cnt+1
union all
select 1 flag1, 1 flag2,
       decode(rn,1,to_char(deptno),' '||ename) it_dept
  from (
select x.*, y.id,
       row_number()over(partition by x.deptno order by y.id) rn
  from (
select deptno,
       ename,
       count(*)over(partition by deptno) cnt
  from it_apps
       ) x,
       (select level id from dual connect by level <= 2) y
       )
 where rn <= cnt+1
       ) tmp1
       ) tmp2
 group by flag
The four moves, in order 1. union all stacks the two tables, tagging each side with flag2 (0 = research, 1 = apps). 2. Cross join to a two-row generator (connect by level <= 2) so every employee exists twice, and row_number() numbers them per department. 3. where rn <= cnt+1 keeps one extra row per department — that spare row is where the department number goes, with decode(rn,1,to_char(deptno),' '||ename) putting the number on the first row and an indented name on all the others. 4. sum(flag1) over (partition by flag2 order by …) numbers the rows 1..n per column, and the outer max(decode(flag2,…)) … group by flag lays those numbered rows out side by side.
Honest summary from the book “Stack ’n’ pivot with a Cartesian twist (on the rocks, with a little umbrella).” It works, it reads like a magic trick, and the running sum(flag1) is really just a row_number() written the long way because the row ordering needed rownum. If you ever need this, generate the report in code.

Turning a scalar subquery into a composite one

In plain English A subquery in the SELECT list may return only one value. So how do you pull three columns out of DEPT that way? You cheat honestly: define an object type with three attributes, return one object, and read its attributes out in an outer query.

SQL · Oracle — three fields packaged as one value 
create type generic_obj
    as object (
    val1 varchar2(10),
    val2 varchar2(10),
    val3 date
 );

select x.deptno,
       x.ename,
       x.multival.val1 dname,
       x.multival.val2 loc,
       x.multival.val3 today
  from (
select e.deptno,
       e.ename,
       e.sal,
       (select generic_obj(d.dname,d.loc,sysdate+1)
          from dept d
         where e.deptno=d.deptno) multival
  from emp e
       ) x
Nothing was actually broken The rule was never bypassed: the subquery still returns exactly one value — it just happens to be an object with parts. generic_obj(dname, loc, sysdate+1) is the type’s constructor, named after the type by default. To read the parts you must wrap the query in a named inline view, which is why this is one of the few places where Oracle insists on the alias.
The realistic version is a join As the book admits, joining emp to dept returns as many columns as you like and needs no object types at all. This recipe is about object-relational plumbing (Oracle’s answer to a struct or a tuple), not about reporting — a technique in search of a problem, but a real technique.
14.11

Parsing serialized data into rows

In plain English Strings like entry:stewiegriffin:lois:brian: hold up to three values between colons — and sometimes none. Parse each string into three columns, leaving gaps where the original had empty slots (entry:::flanders: means value 1 and 2 are missing, not that Flanders is first).

SQL · Oracle — count the delimiters, slice, pivot 
with cartesian as (
select level id
  from dual
 connect by level <= 100
)
select max(decode(id,1,substr(strings,p1+1,p2-1))) val1,
       max(decode(id,2,substr(strings,p1+1,p2-1))) val2,
       max(decode(id,3,substr(strings,p1+1,p2-1))) val3
  from (
select v.strings,
       c.id,
       instr(v.strings,':',1,c.id) p1,
       instr(v.strings,':',1,c.id+1)-instr(v.strings,':',1,c.id) p2
  from v, cartesian c
 where c.id <= (length(v.strings)-length(replace(v.strings,':')))-1
       )
 group by strings
 order by 1
How many values are in this string? length(s) - length(replace(s,':','')) is the count of colons. Seven colons means six fields, and dropping the leading entry and the trailing empty one leaves the number of values — that is the -1 in c.id <= … - 1. Generating numbers 1..n per string and joining is the “cartesian” step; it turns one row into as many rows as the string has values.
The two positions do all the slicing p1 is the position of the nth colon, p2 is the distance to the next one. substr(strings, p1+1, p2-1) then reads the field between them — and when two colons are adjacent, p2-1 is 0, so you get an empty string rather than an error, which is exactly the NULL you want. decode(id,1,…) drops each slice into its own column, and the MAX … group by strings collapses the three rows back to one.
14.12

Percent relative to total

In plain English What share of the total salary bill does each job represent? Clerks 14%, analysts 20%, managers 28%, salesmen 19%, and the single president 17%. Showing the headcount next to the percentage is what stops that 17% from looking like a rounding error.

SQL · Oracle — RATIO_TO_REPORT sums to 1 
select job, num_emps, sum(round(pct)) pct_of_all_salaries
  from (
select job,
       count(*)over(partition by job) num_emps,
       ratio_to_report(sal)over()*100 pct
  from emp
       )
 group by job,num_emps
 order by 2

/* everywhere else: divide by the windowed total */
select job,
       count(*) num_emps,
       round(100*sum(sal)/sum(sum(sal))over(),0) pct_of_all_salaries
  from emp
 group by job
Why the sum of rounds is used ratio_to_report(sal) over () gives each row’s share, so the inner query is one row per employee (14 of them). To get a figure per job you must sum those shares — sum(round(pct)). Rounding first and summing after is why the percentages add to 98 rather than a tidy 100: it is the book’s report, and this is the usual fate of rounded percentages.
The portable equivalent sal / sum(sal) over () is the same fraction without the Oracle function — and it composes with GROUP BY: sum(sal) / sum(sum(sal)) over () gives each job’s share in one step, no inner query. That is the version to remember, since RATIO_TO_REPORT is Oracle-only.
14.13

Testing for a value within a group

In plain English A student sits three exams per period. If they pass any one, the requirement is met for the whole period — so every row in that period should say +, not just the passing row. If they pass none, flag the latest exam as still in progress.

SQL · two window functions, then two DECODEs 
select student_id,
       test_id,
       grade_id,
       period_id,
       test_date,
       decode( grp_p_f,1,lpad('+',6),lpad('-',6) ) metreq,
       decode( grp_p_f,1,0,
               decode( test_date,last_test,1,0 ) ) in_progress
  from (
select V.*,
       max(pass_fail)over(partition by
                      student_id,grade_id,period_id) grp_p_f,
       max(test_date)over(partition by
                      student_id,grade_id,period_id) last_test
  from V
       ) x
Why max answers “did anyone?” pass_fail is only ever 1 or 0, so the maximum over a period is 1 exactly when at least one exam passed — and OVER pastes that verdict onto every row of the period. That is the difference between evaluating rows as individuals and as a group, which is the whole point of the recipe.
Two independent conditions, one row each in_progress needs the second window too: max(test_date) over (…) is the last exam date of the period, so decode(test_date, last_test, 1, 0) marks just that row — and only when the period was failed, because the decode(grp_p_f,1,0,…) short-circuits to 0 otherwise. lpad('+',6) is purely so the plus and minus signs sit under the column header.
14.14

Summing up

In plain English The book’s closing argument, and the whole reason this chapter exists: SQL is more capable than most people give it credit for. These recipes deliberately went looking for the edge cases — serialized strings, binary conversion, stacked pivots — to show how far standard features and a vendor’s extensions can be pushed.

Appendix A in plain English

Grouping (A.1–A.4), then windowing (A.5–A.13). The first half is set theory applied to GROUP BY; the second half is the machinery behind every OVER (…) you have seen in this guide.

A.1

Grouping

In plain English Grouping means “stop showing me rows, show me facts about sets of rows”. Look at department 10: three employees, one row per person. Group it and you get one row that describes all three — how many there are, the highest salary, the lowest.

SQL · three rows in, one row of summary out 
select deptno, ename
  from emp
 where deptno=10

select deptno,
       count(*) as cnt,
       max(sal) as hi_sal,
       min(sal) as lo_sal
  from emp
 where deptno=10
 group by deptno
Why bother With three rows you could read them yourself. With three million you cannot — and the question “how many, how high, how low” is the same question either way. That is the entire justification for GROUP BY: it gives you information about many rows without listing them.
A.2

What an SQL group actually is

In plain English The book defines a group as the result set of a GROUP BY query plus two rules: every row in that result is distinct and represents one or more rows of the table, and COUNT per group is never zero. Both rules are then proved with queries rather than argued.

SQL · proof 1: an empty table has no groups. Proof 2: groups are distinct 
create table fruits (name varchar(10))

/* all three return no rows — you cannot group nothing */
select name            from fruits group by name
select count(*) as cnt from fruits group by name
select name, count(*) as cnt from fruits group by name

insert into fruits values ('Oranges')
insert into fruits values ('Oranges')
insert into fruits values ('Oranges')
insert into fruits values ('Apple')
insert into fruits values ('Peach')

select name, count(*) as cnt
  from fruits
 group by name
The practical consequence Because the rows of a GROUP BY result are already distinct, adding DISTINCT to the select list is redundant — the book is careful to say that GROUP BY and DISTINCT are not the same concept, only that the grouped values come out unique. And because a group always has at least one member, count(*) in a grouped query can never be 0. Hold on to that second claim; A.3 is about to break it.
A.3

The NULL group paradox

In plain English Add five rows whose name is NULL and the rules contradict each other. GROUP BY lumps all the NULLs into one group — and that group has five members — yet count(name) for it returns 0, which A.2 said was impossible. Nothing is broken; the count is doing what it was told.

SQL · count(name) = 0 versus count(*) = 5 
insert into fruits values (null)
insert into fruits values (null)
insert into fruits values (null)
insert into fruits values (null)
insert into fruits values (null)

/* counts values — and there are no non-NULL names in the NULL group */
select coalesce(name,'NULL') as name,
       count(name) as cnt
  from fruits
 group by name

/* counts rows — five members are in that group */
select coalesce(name,'NULL') as name,
       count(*) as cnt
  from fruits
 group by name
The resolution: rows versus values Aggregates ignore NULLs, so count(column) counts values and count(*) counts rows. A group always has at least one row, so count(*) is never zero — the axiom holds for rows, and count(name) is simply answering a different question. Use count(*) when you mean “how many members”, and count(col) when you mean “how many of them have a value”.
Yes, the book really does go via Russell Pages 510–512 are a detour through Frege’s axiom of abstraction, the Barber puzzle and Russell’s paradox, to make the point that a definition can be locally self-contradictory without being useless. The lesson that survives is the previous callout: a paradox about NULL reveals how aggregates are implemented, not a flaw in what a group is.
A.4

The relationship between SELECT and GROUP BY

In plain English The familiar rule — “anything in the select list must be in the GROUP BY” — is slightly too strict. The real rule is: anything that could change the grouping or the aggregate must be listed. Constants, aggregates and scalar subqueries cannot, so they are allowed to sit there on their own.

SQL · what is legal, what is not, and why 
/* legal: a constant, a number and a scalar subquery change no group */
select 'hello' as msg,
       1 as num,
       deptno,
       (select count(*) from emp) as total,
       count(*) as cnt
  from emp
 group by deptno

/* legal: drop the ungrouped columns entirely */
select count(*)
  from emp
 group by deptno

/* illegal: JOB is a column from the table, so it changes the groups */
select deptno, job, count(*) as cnt
  from emp
 group by deptno

/* and the fix is to group by it too */
select deptno, job, count(*) as cnt
  from emp
 group by deptno, job
MySQL’s “feature” The book is unusually blunt here: MySQL historically let you put ungrouped table columns in the select list, and the authors call it “a bug waiting to happen” and suggest you ask them to remove it. The value returned for such a column is whatever row the engine happens to reach first — legal-looking SQL with a non-deterministic answer. Every other engine rejects the query outright, which is the kinder behaviour.
A.5

A simple example: COUNT(*) OVER ()

In plain English You want the total number of employees on every employee row — detail and summary side by side. A plain count(*) collapses the table to one row; add OVER () and the same count is pasted onto all fourteen.

SQL · the same function, two behaviours 
select count(*) as cnt
  from emp

select ename,
       deptno,
       count(*) over() as cnt
  from emp
 order by 2
OVER is the whole switch COUNT is an aggregate function; COUNT … OVER is a window function. Same name, same argument, and the single keyword OVER tells the engine “do not collapse the rows — give me one answer per row instead”. The empty parentheses mean “the window is the entire result set”, which is why 14 repeats.
A.6

Order of evaluation

In plain English Window functions run after WHERE and GROUP BY, and before the final ORDER BY. That single fact explains a dozen surprises elsewhere in this guide: filter the table and the window sees only what survived.

SQL · add one WHERE clause, the total changes 
select ename,
       deptno,
       count(*) over() as cnt
  from emp
 where deptno = 10
 order by 2
The rule to remember FROM → WHERE → GROUP BY → window functions → SELECT → ORDER BY → LIMIT. So you cannot filter on a window result in the same query — the value does not exist yet when WHERE runs. Wrap the query in an inline view and filter outside it, which is exactly what recipes 12.11 and 12.20 do.
A.7

Partitions

In plain English PARTITION BY is a “moving GROUP BY”: the aggregation restarts every time the partition value changes, but the rows are all still there. And you can partition by different columns in the same query.

SQL · one count per department, one per job, same rows 
select ename,
       deptno,
       count(*) over(partition by deptno) as dept_cnt,
       job,
       count(*) over(partition by job) as job_cnt
  from emp
 order by 2

/* what people wrote before window functions: a correlated subquery */
select e.ename,
       e.deptno,
       (select count(*) from emp d
         where e.deptno=d.deptno) as cnt
  from emp e
 order by 2
The two differences from GROUP BY 1. The rows survive: a partition is not distinct, so you get all fourteen employees and the per-department count. 2. Partitions are independent of each other and of the select list, so dept_cnt and job_cnt coexist without either one collapsing the query. The correlated subquery gives the same answer by re-reading the table once per row.
A.8

The effect of NULLs

In plain English PARTITION BY treats NULLs the way GROUP BY does: all of them fall into a single partition. So ten employees with no commission form one group — and then the choice of COUNT(*) or COUNT(comm) decides whether that group reports 10 or 0.

SQL · identical query, one asterisk different 
select coalesce(comm,-1) as comm,
       count(*)over(partition by comm) as cnt
  from emp

select coalesce(comm,-1) as comm,
       count(comm)over(partition by comm) as cnt
  from emp
Same paradox, windowed This is A.3 wearing different clothes. count(*) counts the rows in the partition — 10 for the NULL commission — and count(comm) counts non-NULL values, of which the NULL partition has none, hence 0. A window function ignores NULLs exactly like the aggregate it wraps; nothing about OVER changes that.
A.9

When order matters

In plain English Put an ORDER BY inside the OVER and something unexpected happens: a plain SUM stops being a total and becomes a running total. The order clause does two jobs at once — it sorts the rows and it decides how far the frame reaches.

SQL · total, total, running total 
select deptno,
       ename,
       hiredate,
       sal,
       sum(sal)over(partition by deptno) as total1,
       sum(sal)over() as total2,
       sum(sal)over(order by hiredate) as running_total
  from emp
 where deptno=10
Why TOTAL1 and TOTAL2 are identical WHERE deptno=10 has already reduced the table to three rows, so “the whole result set” and “department 10” are the same three rows. Both sums are 8750. This is A.6 again, and it is the reason the book nudges you to check which rows a window can actually see.
The hidden frame order by hiredate implicitly means range between unbounded preceding and current row — sum from the first row up to this one. CLARK 2450, then KING 2450+5000 = 7450, then MILLER 7450+1300 = 8750. The next section makes that default visible. (At the time of writing, SQL Server refused ORDER BY in OVER for aggregate functions, though it allowed it for ranking functions.)
A.10

The framing clause

In plain English The framing clause says exactly which rows inside the partition take part in the calculation. Four sums over the same three rows, four different answers — and once you can read these, you can read every window function in the book.

SQL · four frames, one partition 
select deptno,
       ename,
       sal,
       sum(sal)over(order by hiredate
                    range between unbounded preceding
                      and current row) as run_total1,
       sum(sal)over(order by hiredate
                     rows between 1 preceding
                     and current row) as run_total2,
       sum(sal)over(order by hiredate
                    range between current row
                     and unbounded following) as run_total3,
       sum(sal)over(order by hiredate
                     rows between current row
                     and 1 following) as run_total4
  from emp
 where deptno=10
Read each clause as a sentence unbounded preceding and current row — everything from the start of the partition up to me (the running total). 1 preceding and current row — me and the row before (CLARK has no previous row, so 2450). current row and unbounded following — me to the end (a reverse running total). current row and 1 following — me and the next row.
ROWS versus RANGE ROWS counts physical rows; RANGE works in values of the ordering column. With one row per hire date in a three-row partition the two mostly agree — which is why RUN_TOTAL1 and RUN_TOTAL2 match for CLARK and KING — but they diverge as soon as two rows share a value. That distinction is the whole reason recipe 12.19 gets the same answer for two employees hired on the same day.
A.11

A framing finale: eight columns from one table

In plain English One query, eight MIN/MAX columns, each with a different frame — a tour of every possibility at once. The surprise is MAX1: ordered by SAL ascending with the default frame, the running maximum is always the current row.

SQL · no frame, whole partition, current row only, and 3 either side 
select ename,
       sal,
       min(sal)over(order by sal) min1,
       max(sal)over(order by sal) max1,
       min(sal)over(order by sal
                    range between unbounded preceding
                      and unbounded following) min2,
       max(sal)over(order by sal
                    range between unbounded preceding
                      and unbounded following) max2,
       min(sal)over(order by sal
                    range between current row
                      and current row) min3,
       max(sal)over(order by sal
                    range between current row
                      and current row) max3,
       max(sal)over(order by sal
                     rows between 3 preceding
                      and 3 following) max4
  from emp
Column by column MIN1 = 800 everywhere: ordered ascending, the smallest salary comes first and stays the smallest. MAX1 = the row’s own salary: the running maximum of an ascending list is always the newest, largest item. MIN2/MAX2 = 800/5000, because unbounded preceding and unbounded following is the whole table. MIN3/MAX3 = SAL, since current row and current row is a frame of one. MAX4 looks three rows back and three forward: for MARTIN that is WARD 1250, ADAMS 1100, JAMES 950, MARTIN 1250, MILLER 1300, TURNER 1500, ALLEN 1600 — the highest is ALLEN’s 1600.
A.12

Readability + performance = power

In plain English Three questions about the same table — how many employees per department, how many per department and job, and how many in total — answered by one short query, versus a version that answers them with scalar subqueries. Identical output; very different futures.

SQL · three partitions, then the same thing with subqueries 
select deptno,
       job,
       count(*) over (partition by deptno)     as emp_cnt,
       count(job) over (partition by deptno,job) as job_cnt,
       count(*) over ()                        as total
  from emp

select a.deptno, a.job,
       (select count(*) from emp b
         where b.deptno = a.deptno) as emp_cnt,
       (select count(*) from emp b
         where b.deptno = a.deptno and b.job = a.job) as job_cnt,
       (select count(*) from emp) as total
  from emp a
 order by 1,2
Why the window version wins Both read the table; the difference is how many times. A correlated subquery is evaluated per outer row, so the subquery version re-scans emp roughly three times per employee. On fourteen rows nobody notices — the book’s own words are “try these queries with a 1,000- or 10,000-row table”. The window version is one pass, and it reads better because the three questions are three lines.

       sal,

Appendix B in plain English

B.1

Subqueries as derived tables

In plain English You want the job with the most employees — but that needs max(count(*)), and SQL does not allow an aggregate inside an aggregate. So compute the counts first in a subquery, and ask the outer query for the maximum of that.

SQL · a double aggregate, via a derived table 
select max(HeadCount) as HighestJobHeadCount
  from (
select job,
       count(empno) as HeadCount
  from emp
 group by job
       ) head_count_tab
Some engines insist on the alias The trailing head_count_tab is not decoration: MySQL, PostgreSQL and SQL Server all require a name for an inline view, while Oracle does not. Write it every time — it also makes the query self-documenting, and it is mandatory the moment you want to reference the derived table more than once.
Why “derived table” is the right phrase The inner query is not a table that exists anywhere; it is a table-shaped result produced for the length of one statement. Which is also exactly what a CTE is — the difference is spelling.
B.2

Common table expressions

In plain English A CTE names the derived table before the query that uses it, so the query reads top to bottom: here is the table I am building, here is what I do with it. Same double aggregate, same answer, better order.

SQL · WITH names the table first; then the recursion CTEs exist for 
with head_count_tab (job,HeadCount) as
(
select job, count(empno)
  from emp
 group by job
)
select max(HeadCount) as HighestJobHeadCount
  from head_count_tab

/* the first 20 Fibonacci numbers, recursively */
with recursive workingTable (fibNum, NextNumber, index1) as
(
select 0, 1, 1
 union all
select fibNum+nextNumber, fibNum, index1+1
  from workingTable
 where index1 < 20
)
select fibNum from workingTable
Three syntax facts worth memorising 1. The column list comes first, in the parentheses after the CTE name — the reverse of aliasing a normal table. 2. Multiple CTEs are just commas between them, each with its own name and query. 3. RECURSIVE is required in MySQL, Oracle and PostgreSQL, and not in SQL Server or DB2.
The WHERE clause is the loop condition Without where index1 < 20 the recursion never stops — and because the numbers grow, most engines would first die of a numeric overflow. Better still, the CTE keeps the current and previous number in two columns, which is a hand-rolled LAG: fibNum + NextNumber is the classic “add the last two” step. (The book’s printed listing says from anchor and fibNUm; both are typos — the table is workingTable.)
When a CTE is genuinely better than a subquery For one derived table, there is little in it. The case strengthens with depth: five nested subqueries push the meaning of each alias into five different indentation levels, while a CTE lists each element vertically, in the order you would explain it to someone. That is also why every recursive query in Chapter 13 is written as a CTE — recursion has no readable subquery form.
