1Why start here? The big idea

When an application feels slow, people tend to blame the query. But the query is only one small piece of a much bigger machine. The database sits inside a chain: application → SQL Server instance → virtual or physical hardware → disks → network. Any one of those links can be the real culprit.

That is the whole point of Chapter 1. Before you start tuning queries, you check whether the server was ever set up correctly in the first place. A surprising number of "mystery" performance problems turn out to be a bad setting somebody chose five years ago and never revisited.

In plain terms

Don't start by staring at a slow query. Start by asking: is this server built and configured sensibly? This chapter is the checklist for answering that question.

2Hardware & operating system

The author deliberately avoids naming specific vendors or part numbers — hardware goes stale fast. Instead he gives rules that stay true.

CPUBuy the fastest CPU you can afford

SQL Server licensing usually costs more than the hardware itself. You could build a decent server for less than the retail price of four Enterprise Edition cores. So don't cheap out on the CPU — especially on Standard Edition, which caps how many cores you may use anyway.

  • Newer generation beats same-speed older generation — typically 10–15% free performance just from generation.
  • Fewer fast cores vs. many slow cores? OLTP (and especially In-Memory OLTP) likes fast single cores. Data warehouse / analytical workloads like more cores and parallelism.

Memory"How much does SQL Server need?" → "More."

More memory means more data cached, which means less disk I/O. Adding RAM is often the cheapest, fastest fix available.

  • Adding memory only hides bad queries — it doesn't fix them, and eventually the data outgrows the cache. Treat it as a temporary bandage, not a cure.
  • Edition limits matter: Standard Edition (2014+) caps the buffer pool at 128 GB, In-Memory OLTP at 32 GB per database, and columnstore segments at 32 GB. Web Edition gets half of that.
  • Don't forget memory for other components: plan cache, lock manager.

DiskLow latency is the whole game

SQL Server reads and writes constantly, so a fast disk subsystem is essential. The author's targets for critical tier-1 systems:

File typeTarget latencyWhy
Data file reads/writes3–5 msRandom I/O is constant; queues build fast
Transaction log writes1–2 msLog writes are synchronous — every commit waits
  • Measure latency inside SQL Server, not on the storage array. SQL Server's numbers are routinely higher than storage KPIs because of queueing.
  • Priority order if you have performance tiers: tempdb first, then transaction log, then data files.
  • Putting several log and/or data files on one drive turns sequential writes into random I/O — avoid it.
  • Split data and log onto separate physical drives for maintainability and recovery — but check the storage config first, since splitting LUNs on an array without enough spindles can make things worse.
  • The author does not split clustered and nonclustered indexes across filegroups onto different drives — it rarely helps I/O and it badly complicates disaster recovery.

NetworkYour throughput equals your slowest hop

A 10 Gbps server uplink is meaningless if there's a 1 Gbps switch in the path. When troubleshooting network performance, map the whole topology. This matters most for network-based storage — keep the I/O path to disks as direct as possible.

On clusters: a dedicated heartbeat network for AlwaysOn Failover Clusters / Availability Groups is good practice on simple single-subnet setups. In complex multi-subnet or virtual environments, extra networks can create routing problems instead of solving them.

OS & appsKeep it clean and current

  • Use the most recent OS version that supports your SQL Server, and patch both on a regular schedule.
  • On SQL Server versions before 2016, use the 64-bit build — it scales better.
  • Since SQL Server 2017, Linux is a first-class option; performance is similar to Windows, but HA strategy differs (e.g. Pacemaker instead of Windows Server Failover Cluster).
  • Use a dedicated database host. App servers are cheap and easy to scale; database hosts are not.
  • Don't run SSMS on the server in an RDP session — work remotely instead.
  • If antivirus is mandatory, exclude database folders from scanning.

Virtualization & cloudFine — but watch the host

Virtualize unless you genuinely need every last ounce of bare-metal performance. You gain vMotion / Live Migration as an extra HA layer, easier hardware upgrades, and simpler management. Overhead grows on very large many-core servers, but is usually acceptable.

The catch

The guest VM's own metrics can look perfectly healthy while the host is over-provisioned. Work with your infrastructure engineers, check physical vs. allocated vCPU and RAM on the host, and reserve resources for mission-critical SQL Server VMs. Once you're past this layer, troubleshooting a VM is the same as troubleshooting physical hardware — and the cloud is just someone else's datacenter.

3Configuring the SQL Server instance

The default setup is "relatively decent" for light and moderate workloads, but several things need validating.

First command to runVersion and patch level

First statement in any health checkT-SQL
SELECT @@VERSION;

Why bother? Two reasons: it reveals the patching discipline of the environment, and it tells you which known bugs may already be fixed in a service pack or cumulative update you haven't applied. The author has repeatedly been called in to fix problems that were already solved by a patch.

Upgrading is often the highest-value "tuning" you can do. Moving from SQL Server 2012 to 2016 or later commonly gives 20–40% performance improvement with no other changes. Since 2016 SP1, many former Enterprise-only features (like data compression) also work in lower editions. Always test before upgrading — risk is small for minor patches, higher for major upgrades.

Setting #1Instant File Initialization (IFI)

Normally, when SQL Server grows a file it fills the new space with zeros first. That blocks every session writing to that file and spikes I/O. For transaction logs this is unavoidable. For data files you can skip it.

Enable IFI by granting SA_MANAGE_VOLUME_NAME (the "Perform Volume Maintenance Task" privilege) to the SQL Server startup account via secpol.msc, then restart the service. From SQL Server 2016 onward you can grant it right in the setup wizard.

Check it on SQL Server 2012 SP4 / 2016 SP1 or later:

Quick check via DMVT-SQL
SELECT instant_file_initialization_enabled, *
FROM sys.dm_server_services;

On older versions, use the trace-flag trick from the book — create a dummy database and read what the error log says about zeroing:

Listing 1-1 — Checking IFI in older SQL Server versionsT-SQL
DBCC TRACEON(3004,3605,-1);
GO
CREATE DATABASE Dummy;
GO
EXEC sp_readerrorlog 0,1,N'Dummy';
GO
DROP DATABASE Dummy;
GO
DBCC TRACEOFF(3004,3605,-1);
GO

If IFI is off, the log shows zeroing of both the .mdf and the .ldf. If it's on, only the .ldf is zeroed.

The trade-off

IFI has a small security implication: a DBA could potentially read remnants of previously deleted files through newly allocated data pages. Most systems accept that risk — if yours does, turn IFI on.

Setting #2tempdb

tempdb stores temporary objects for users and for SQL Server itself. It is extremely busy and a classic contention point.

  • Put it on the fastest drive. It doesn't need redundancy or persistence (it's recreated at startup), so local SSD or cloud ephemeral storage is ideal — but remember SQL Server goes down if tempdb disappears.
  • On non-Enterprise editions, if the server has more RAM than SQL Server can consume, tempdb can live on a RAM drive. Never do this on Enterprise — that memory is better spent on the buffer pool. Pre-allocate the files to the RAM drive's full size and add small on-disk files as overflow.
  • Always use multiple data files. Rule of thumb:
CPU corestempdb data files
8 or fewerOne per core
More than 88, or ¼ of the cores — whichever is greater, rounded up in batches of 4
Example: 24 cores8 files
Example: 40 cores12 files

Give every tempdb file the same initial size and auto-growth set in MB, never percent — that's what lets SQL Server balance usage evenly.

Setting #3Trace flags

Trace flags toggle hidden product behaviors. Check which ones are already on with DBCC TRACESTATUS; enable new ones in SQL Server Configuration Manager or via the -T startup parameter.

FlagWhat it doesVerdict
T1118Stops mixed-extent allocations, reducing tempdb catalog contentionEnable on 2014 and earlier. Unnecessary on 2016+ (default behavior).
T1117Auto-grows every file in a filegroup when one fills up, balancing I/OOptional on 2014 and earlier for tempdb. Check for unevenly sized filegroups first.
T2371Makes the statistics-update threshold dynamic instead of the fixed 20%-of-rows rule, so big tables get updated statsEnable unless every database is compatibility level 130+.
T3226Stops logging successful backups to the error logHandy for keeping logs small and readable.
T1222Writes deadlock graphs to the error logRemove it — redundant with the system_health xEvents session, and it makes logs harder to read.
T4199Enables Query Optimizer hotfixes from service packs / CUsGenerally avoid in production — raises plan-regression risk after patching unless you can regression-test thoroughly.
T7412Lightweight query profiling (2016/2017)Cheap execution-plan and metrics collection; covered further in Chapter 5.
Short version

On SQL Server 2014 and earlier: enable T1118, T2371, and maybe T1117. On 2016+: enable T2371 unless all databases sit at compatibility level 130 or above. Then audit every other flag — third-party tools quietly install some, and they can hurt performance.

Server optionOptimize for Ad-hoc Workloads

By default SQL Server caches the full execution plan of every ad-hoc (unparameterized) query. Most ad-hoc queries never run a second time, so that's wasted plan-cache memory. Turn this setting on and SQL Server caches only a tiny plan stub (a few hundred bytes) on first execution, promoting it to a full plan only if the query comes back.

Recommendation

Enable it on every system. Costs nothing but the occasional extra compile of a genuinely repeated query. It doesn't affect parameterized queries or stored procedures. On SQL Server 2019 / Azure SQL Database you can also set it per-database with OPTIMIZE_FOR_AD_HOC_WORKLOADS.

Server optionMax Server Memory

Controls how much memory SQL Server may use. There's endless debate about the "right" formula, and it's true that a wrong value is worse than the default. But the author's experience says the most common problem is severe under-provisioning: someone upgraded the hardware and forgot to raise the limit, or calculated it wrongly on a shared server. Raising it (or temporarily resetting to default) can produce instant wins. Chapter 7 covers the details.

Server optionAffinity mask & NUMA

On multi-NUMA hardware (usually one NUMA node per physical CPU), if you restrict SQL Server to fewer cores than the machine has, spread those cores evenly across NUMA nodes. Limiting 24 cores on two 18-core Xeons: take 12 + 12, not 18 + 6.

Listing 1-2 — Checking scheduler (CPU) distribution across NUMA nodesT-SQL
SELECT
  parent_node_id
  ,COUNT(*) as [Schedulers]
  ,SUM(current_tasks_count) as [Current]
  ,SUM(runnable_tasks_count) as [Runnable]
FROM sys.dm_os_schedulers
WHERE status = 'VISIBLE ONLINE'
GROUP BY parent_node_id;

Compare the Schedulers count per parent_node_id — an even split across nodes is what you want.

Server optionParallelism (MAXDOP & cost threshold)

The defaults (MAXDOP = 0, cost threshold 5) are relics and don't suit modern servers. Rules of thumb:

  • MAXDOP = ¼ of available CPUs on OLTP, ½ on data warehouse. Very large OLTP servers: keep it at 16 or below. Never exceed the number of schedulers in a single NUMA node.
  • Cost Threshold for Parallelism = 50.
  • SQL Server 2016+ / Azure SQL: set MAXDOP per database with ALTER DATABASE SCOPED CONFIGURATION SET MAXDOP when one instance hosts mixed workloads.

AuditWhich server settings were changed?

SQL Server won't tell you the defaults, so you have to hardcode them and compare against sys.configurations. Here's the book's approach (the published script lists a few settings; the full version is in the companion materials):

Listing 1-3 — Detecting changes in server configuration settingsT-SQL
DECLARE
    @defaults TABLE
    (
        name SYSNAME NOT NULL PRIMARY KEY,
        def_value SQL_VARIANT NOT NULL
    )
INSERT INTO @defaults(name,def_value)
VALUES('backup compression default',0);
INSERT INTO @defaults(name,def_value)
VALUES('cost threshold for parallelism',5);
INSERT INTO @defaults(name,def_value)
VALUES('max degree of parallelism',0);
INSERT INTO @defaults(name,def_value)
VALUES('max server memory (MB)',2147483647);
INSERT INTO @defaults(name,def_value)
VALUES('optimize for ad hoc workloads',0);
/* Other settings are omitted in the book */

SELECT
    c.name, c.description, c.value_in_use, c.value
    ,d.def_value, c.is_dynamic, c.is_advanced
FROM
    sys.configurations c JOIN @defaults d ON
        c.name = d.name
WHERE
    c.value_in_use <> d.def_value OR
    c.value <> d.def_value
ORDER BY
    c.name;

4Configuring your databases

Turn this offAuto Shrink

Auto Shrink periodically shrinks the database and hands free space back to the OS. Sounds tidy; isn't. The shrink works at the physical level — it finds empty space near the front of the file and moves allocated extents from the end into it, ignoring extent ownership. The result: heavy load and serious index fragmentation. And usually for nothing, because the files just grow again as data arrives.

Recommendation

Disable Auto Shrink and manage file space yourself. Same for transaction log files — never auto-shrink them.

Also turn offAuto Close

With Auto Close on, SQL Server throws away the database's buffer-pool pages and cached plans when the last connection closes. The next session pays for re-caching and recompiling. Disable it, with few exceptions (perhaps an instance hosting hundreds of rarely used databases).

Check theseOther database settings

SettingWhat you wantWhy
Page VerifyCHECKSUMDetects consistency errors far more effectively; helps resolve corruption cases
Recovery modelNot SIMPLE for critical DBsIn SIMPLE you cannot recover beyond the last full backup — a real data-loss risk. Raise it with stakeholders immediately.
Compatibility levelNewest level matching your SQL Server versionOlder levels block new features. But test first — going from 110 to 120+ switches on the new cardinality estimator and can change plans dramatically.

To de-risk a compatibility-level upgrade, keep the old cardinality estimator for a while: set LEGACY_CARDINALITY_ESTIMATION = ON (2016+) or enable trace flag T9481 (2014). That lets you change one thing at a time. Chapter 5 goes deeper.

Transaction logFewer, better-sized VLFs

SQL Server uses write-ahead logging and writes the log serially, "merry-go-round" style. It divides the log into Virtual Log Files (VLFs) and manages them as whole units — it cannot truncate a VLF that holds even one active record.

  • One log file is almost always enough. Multiple log files complicate admin and rarely help performance.
  • Too few huge VLFs → slow, awkward log management and truncation. Too many tiny VLFs → degraded log performance. Aim for no more than a few hundred VLFs in production.
  • Growth of 64 MB–1 GB creates ~8 VLFs; over 1 GB creates ~16. Percent-based growth is the enemy — it produces wildly uneven VLFs. The author grows in 1,024 MB chunks (yielding 128 MB VLFs) unless the log needs to be huge.
  • Count VLFs with sys.dm_db_log_info (2016+) or DBCC LOGINFO (older). If it's bad, rebuild the log: shrink to minimum, then grow in 1,024–4,096 MB chunks.
  • Don't cap the maximum size or disable auto-growth — you want emergency growth to work.
Counting VLFs (SQL Server 2016+)T-SQL
-- How many VLFs does this log have?
SELECT COUNT(*) AS [VLF_Count]
FROM sys.dm_db_log_info(DB_ID());

Data filesFilegroups and Proportional Fill

By default a new database gets one data file in PRIMARY and one log file. That's suboptimal for performance, management, and HA.

  • SQL Server tracks space through allocation maps. On volatile data these become contention points because access is serialized. Multiple files in the filegroup give you multiple sets of allocation pages and reduce that contention.
  • Proportional Fill writes mostly to the file with the most free space. Identically sized files with identical MB-based growth keep writes balanced.
  • Consider AUTOGROW_ALL_FILES (2016+) so every file in the filegroup grows together. On older versions trace flag T1117 does this — but server-wide.

When laying out (or re-laying out) filegroups, the author's guidance:

  1. Multiple data files in volatile-data filegroups — start with four, add more if latching issues appear. Same size, same MB growth, AUTOGROW_ALL_FILES on. Read-only filegroups need only one file.
  2. Don't spread clustered indexes, nonclustered indexes, or LOB data across filegroups — little gain, real pain during corruption recovery.
  3. Keep related tables together (e.g. Orders and OrderLineItems) — simpler management and disaster recovery.
  4. Keep PRIMARY empty if possible.

5Reading the error log

The SQL Server error log is another early stop in troubleshooting. Errors 823 and 824 in particular can point to disk subsystem problems or database corruption. The problem is noise: the log is full of informational messages that bury the real signal.

You can read it in SSMS, or programmatically with xp_readerrorlog. The book's script filters out the noise and, optionally, shows you the log lines around each error so you get context.

VariableControls
@StartDate / @EndDateThe time window to analyze
@NumErrorLogsHow many rolled-over log files to read
@ExcludeLogonErrorsDrops logon-auditing messages
@ShowSurroundingEventsAlso returns informational messages around each error
@SurroundingEventsBeforeSecond / ...AfterSecondThe context window, in seconds
@ErrorsToIgnorePatterns for known-harmless "error" lines

It produces two result sets: the cleaned-up list of errors, then (optionally) the surrounding context for each one.

Listing 1-4 — Analyzing the SQL Server error logT-SQL
IF OBJECT_ID('tempdb..#Logs',N'U') IS NOT NULL DROP TABLE #Logs;
IF OBJECT_ID('tempdb..#Errors',N'U') IS NOT NULL DROP TABLE #Errors;
GO
CREATE TABLE #Errors
(
  LogNum INT NULL,
  LogDate DATETIME NULL,
  ID INT NOT NULL IDENTITY(1,1),
  ProcessInfo VARCHAR(50) NULL,
  [Text] NVARCHAR(MAX) NULL,
  PRIMARY KEY(ID)
);
CREATE TABLE #Logs
(
  [LogDate] DATETIME NULL,
  ProcessInfo VARCHAR(50) NULL,
  [Text] NVARCHAR(MAX) NULL
);
DECLARE
  @StartDate DATETIME = DATEADD(DAY,-7,GETDATE())
  ,@EndDate DATETIME = GETDATE()
  ,@NumErrorLogs INT = 1
  ,@ExcludeLogonErrors BIT = 1
  ,@ShowSurroundingEvents BIT = 1
  ,@ExcludeLogonSurroundingEvents BIT = 1
  ,@SurroundingEventsBeforeSecond INT = 5
  ,@SurroundingEventsAfterSecond INT = 5
  ,@LogNum INT = 0;
DECLARE
  @ErrorsToIgnore TABLE
  (
    ErrorText NVARCHAR(1024) NOT NULL
  );
INSERT INTO @ErrorsToIgnore(ErrorText)
VALUES
  (N'Registry startup parameters:%'),
  (N'Logging SQL Server messages in file%'),
  (N'CHECKDB for database%finished without errors%');

WHILE (@LogNum <= @NumErrorLogs)
BEGIN
  INSERT INTO #Errors(LogDate,ProcessInfo,Text)
    EXEC [master].[dbo].[xp_readerrorlog]
      @LogNum, 1, N'error', NULL, @StartDate, @EndDate, N'desc';
  IF @@ROWCOUNT > 0
    UPDATE #Errors SET LogNum = @LogNum WHERE LogNum IS NULL;
  SET @LogNum += 1;
END;

IF @ExcludeLogonErrors = 1
  DELETE FROM #Errors WHERE ProcessInfo = 'Logon';

DELETE FROM e
FROM #Errors e
WHERE EXISTS
(
  SELECT *
  FROM @ErrorsToIgnore i
  WHERE e.Text LIKE i.ErrorText
);

-- Errors only
SELECT * FROM #Errors ORDER BY LogDate DESC;

IF @@ROWCOUNT > 0 AND @ShowSurroundingEvents = 1
BEGIN
  DECLARE
    @LogDate DATETIME
    ,@ID INT = 0

  WHILE 1 = 1
  BEGIN
    SELECT TOP 1 @LogNum = LogNum, @LogDate = LogDate, @ID = ID
    FROM #Errors
    WHERE ID > @ID
    ORDER BY ID;

    IF @@ROWCOUNT = 0
      BREAK;

    SELECT
      @StartDate = DATEADD(SECOND, -@SurroundingEventsBeforeSecond, @LogDate)
      ,@EndDate = DATEADD(SECOND, @SurroundingEventsAfterSecond, @LogDate);

    INSERT INTO #Logs(LogDate,ProcessInfo,Text)
      EXEC [master].[dbo].[xp_readerrorlog]
        @LogNum, 1, NULL, NULL, @StartDate, @EndDate;
  END;

  IF @ExcludeLogonSurroundingEvents = 1
    DELETE FROM #Logs WHERE ProcessInfo = 'Logon';

  DELETE FROM e
  FROM #Logs e
  WHERE EXISTS
  (
    SELECT *
    FROM @ErrorsToIgnore i
    WHERE e.Text LIKE i.ErrorText
  );

  SELECT * FROM #Logs ORDER BY LogDate DESC;
END

What you're looking for is system-specific, so the book doesn't enumerate every possible error. The rule is: investigate anything suspicious and understand its possible impact. Finally, if it isn't already done, set up SQL Server Agent alerts for high-severity errors.

6Putting too much on one server

Consolidation cuts hardware and licensing cost, but it isn't free. There's no universal strategy — weigh data volume, load, hardware, business and security requirements. A few firm rules:

  • Don't mix OLTP and data warehouse/reporting databases on one heavily loaded server. Warehouse queries churn through huge amounts of data, hammer I/O, and flush the buffer pool — hurting every other database on the instance. If they're already combined, consider splitting them.
  • Watch security features. Audit runs at the server level and adds overhead to everything. TDE is database-level, but if any database on the instance has it enabled, tempdb gets encrypted too — overhead for all.
  • As a general rule, don't keep databases with different security requirements on the same instance. Watch metric trends and split databases when needed.
Better approach

Instead of piling many independent active databases onto one SQL Server instance, virtualize — run several VMs on one or a few hosts. You get far better flexibility, manageability, and isolation, and resource consumption is much easier to control.

7The observer effect

Every serious production system needs monitoring — it makes you proactive and shortens incident detection and recovery. But monitoring costs you something, and sometimes the cost is large.

Two real examples from the author's consulting work:

  • A tool that called sys.dm_db_index_physical_stats in DETAILED mode for every index in the database every four hours. Result: enormous I/O spikes, a wiped buffer pool, and a visible performance hit.
  • A tool that constantly polled DMVs, adding significant CPU load.

Monitoring built from T-SQL is at least visible — you can find the queries and measure them. Extended Events monitoring is much harder to spot, and some events are genuinely heavy. The session below captures every query in the system, which is exactly the kind of thing that looks harmless on a slide and hurts on a busy box:

Listing 1-5 — Creating an xEvents session to capture queries in the systemT-SQL
CREATE EVENT SESSION CaptureQueries ON SERVER
ADD EVENT sqlserver.rpc_completed
(
  SET collect_statement=(1)
  ACTION
  (
    sqlos.task_time
    ,sqlserver.client_app_name
    ,sqlserver.client_hostname
    ,sqlserver.database_name
    ,sqlserver.nt_username
    ,sqlserver.sql_text
  )
),
ADD EVENT sqlserver.sql_batch_completed
(
  ACTION
  (
    sqlos.task_time
    ,sqlserver.client_app_name
    ,sqlserver.client_hostname
    ,sqlserver.database_name
    ,sqlserver.nt_username
    ,sqlserver.sql_text
  )
),
ADD EVENT sqlserver.sql_statement_completed
ADD TARGET package0.event_file
(SET FILENAME=N'C:\PerfLogs\LongSql.xel',MAX_FILE_SIZE=(200))
WITH
(
  MAX_MEMORY =4096 KB
  ,EVENT_RETENTION_MODE=ALLOW_SINGLE_EVENT_LOSS
  ,MAX_DISPATCH_LATENCY=5 SECONDS
);

Deployed on a heavily loaded server with lots of concurrent requests, the effect is measurable. The author tested throughput with and without the session — and found enabling it cut throughput by about 20%:

The lesson

Evaluate your monitoring strategy and estimate its overhead as part of the analysis — especially on servers hosting multiple databases. xEvents operates at the server level: filtering on database_id happens after the event fires, so it affects every database on the instance. Check for unnecessary monitoring and data-collection tools during every investigation.
