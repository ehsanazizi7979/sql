Chapter 8

Examining Index Usage

Why the optimizer picks the index it picks — and the three things that break that choice: bad statistics, stale statistics, and parameter sniffing. Then the two index types that look different in a plan: columnstore and memory-optimized.

1 The optimizer's shopping list

An index is only used if it's selective — and "selective" is a number the optimizer pulls out of statistics, not a quality you can see by looking at your query.

The chapter opens with a warning worth taking literally: you cannot fix every slow query by adding an index, and you can absolutely have too many indexes. Every index you add is maintained on every INSERT, UPDATE, DELETE and MERGE. The goal is the minimal set that helps the optimizer resolve the most important, expensive and frequent queries in your workload as cheaply as possible.

Clustered indexReplaces the heap. Stores all the table data, ordered by the clustering key, so ranges of keys are physically adjacent.
Nonclustered indexStores only the key values plus a pointer back to the row (the clustered key, or the RID on a heap). INCLUDE pads it with extra leaf-level columns.

To experiment, the book builds a heap-free copy of Sales.SalesOrderDetail with a clustered primary key and two nonclustered indexes — one on ProductID, one on OrderQty:

Note what already happened there. The index isn't covering — the query asks for LineTotal, which the index doesn't have — yet the optimizer still preferred seek-plus-46-lookups over one big scan. It had a reason, and the reason is statistics.

2 Statistics: density, histogram, tipping point

The optimizer's "data about the data". Three result sets, and every index decision in the chapter comes out of them.

Listing 8-3 · look at the statistics
DBCC SHOW_STATISTICS('dbo.NewOrders',
                     'IX_NewOrders_OrderQty');

It returns three result sets — header, density graph, histogram — in that order.

The header

Why 40 steps for 41 distinct values? A histogram holds at most 200 steps. It's built in a single pass that only keeps the most "interesting" data points, so it can miss one. Don't read the step count as a distinct count.

The density graph

Density is the optimizer's uniqueness estimate: lower density means more distinct values, which means a more selective index. A unique column in a 10,000-row table has density 1/10000 = 0.0001, and an equality predicate on it has the same selectivity as a number — they're computed identically.

Density has a second job: estimating rows after an aggregate. A Color column with 5 distinct values in 10,000 rows has density 1/5 = 0.2, so GROUP BY Color is estimated at 1/0.2 = 5 rows. That's the same mechanism that gives every GROUP BY its estimate in Chapter 5.

The two formulas the whole chapter runs on Unknown value (can't sniff): estimated rows = density × row count — 0.02439024 × 121317 ≈ 2958.95.
Unknown value with an inequality (>, <): the density is ignored and the optimizer uses a hard-coded 30% estimate instead.

The histogram

When the value is known — hard-coded, or sniffed — the optimizer switches from the density graph to the histogram. An exact match on RANGE_HI_KEY means it reads EQ_ROWS directly: 46 rows. No match means it looks at the range the value falls into and uses AVG_RANGE_ROWS, which is just RANGE_ROWS / DISTINCT_RANGE_ROWS. Ask for OrderQty = 35 and there's no 35 row; 35 falls in the range topped by 36, so the estimate becomes that row's AVG_RANGE_ROWS — 2 rows.

The tipping point

With 46 rows estimated, the optimizer prices one seek + 46 lookups against its only real alternative, one clustered index scan, and the seek wins. But lookups scale linearly while a scan doesn't, so there is a crossover. In this table it's around 400 rows:

  • WHERE OrderQty = 11 → 392 estimated rows → still seek + lookups.
  • WHERE OrderQty = 12 → 466 estimated rows → it tips, and you get a scan.

The local-variable trap

Listing 8-4 · the same query with a variable
DECLARE @OrderQuantity SMALLINT
SET @OrderQuantity = 20
SELECT OrderQty,
       SalesOrderID,
       SalesOrderDetailID,
       LineTotal
FROM dbo.NewOrders
WHERE OrderQty = @OrderQuantity;

Semantically identical to Listing 8-2, yet this one gets the scan — even though the actual row count is way below the tipping point. The optimizer cannot sniff a local variable, so it falls back to the density graph and estimates 2,958.95 rows, which is far above the crossover.

Change even less and the estimate gets worse Write WHERE OrderQty > @OrderQuantity and there's no density to fall back on at all: the optimizer applies its hard-coded 30% and estimates 36,395.1 rows when only 164 are returned. You will always get the scan. Variables are the single easiest way to accidentally throw away a good index.

Covering indexes

All of the above is a fight over the lookup. When rows are few, a lookup is cheap; when there are many, the lookups are the whole cost. Covering the index — either by putting the columns in the key, or by INCLUDE-ing them at the leaf — removes the fight entirely. But pay for it once, in writes: each added index or INCLUDE'd column is reordered, inserted and deleted with the data. Weigh the query's importance and frequency against that permanent tax.

When the optimizer ignores a perfectly good index Usually it's one of these, and only the last is a statistics problem: implicit conversion because a parameter's data type doesn't match the column's; a function wrapped around the column in the predicate; a complex or inequality predicate; or an index that is genuinely cheaper elsewhere in the plan because it delivers data pre-sorted for a Merge Join, a Stream Aggregate, or an ORDER BY.

3 When statistics go stale

Same query, same plan, wildly different cost. One script, three measurements — and one number that should make you sit up.

Four things can produce a bad plan out of the statistics themselves: missing statistics (e.g. AUTO_CREATE_STATISTICS OFF), stale statistics, reuse of a cached plan that no longer matches the data, and skewed distributions that defeat averaging.

Five percent of the table's rows, all with ProductID = 897 — enough to skew the data, not enough to trip the automatic statistics update threshold. SET STATISTICS XML in separate batches is what keeps the INSERT's own plan out of the captures.
The numbers that make the lesson 52 logical reads before the insert → 19,385 logical reads after it. Same query. Same plan. Same second of wall clock, different data.
What to do about it Leave AUTO_UPDATE_STATISTICS on, always. For large tables consider a scheduled UPDATE STATISTICS job, because the automatic threshold is proportional and big tables can go a long time without a refresh. If a specific skew hurts a specific important query, look at filtered statistics.

4 Parameter sniffing, both faces

The feature that saves you one day charges you 239,186 logical reads the next. It's the same plan, and it's doing exactly what it was told.

When a batch calls a procedure, SQL Server compiles the batch first — setting variables and evaluating expressions — then checks the plan cache, and only compiles the procedure if there's no plan. At that moment the optimizer can peek at the value being passed and use the histogram row for it instead of an average. That's parameter sniffing.

Sniffing is your friendA million-row table, filtered to the last week by an inequality. Without sniffing you get a 30% (300,000-row) plan for a query returning hundreds.
Sniffing is irrelevantPredicates on the primary key, or on keys with an even distribution, where every value costs the same. Every plan is fine.
Listing 8-6 · the query as a procedure, with an optional parameter
CREATE OR ALTER PROCEDURE dbo.OrdersByQty
    @OrderQty SMALLINT = NULL
AS
SELECT SalesOrderID,
       SalesOrderDetailID,
       OrderQty,
       LineTotal
FROM dbo.NewOrders
WHERE
      (
          OrderQty = @OrderQty
          OR @OrderQty IS NULL
      );
GO
Why scan the index instead of seeking it? Because of the optional parameter. Peek at the Index Scan's Predicate and you'll see OrderQty = @OrderQty OR @OrderQty IS NULL, not a Seek Predicate. A plan has to be safe for reuse: if a plan with a seek predicate on OrderQty = @OrderQty were reused with no value supplied, the seek would compare against NULL and return nothing — when the intent was to return everything. The optimizer trades a little speed for correctness. Any OR … IS NULL "optional parameter" pattern costs you seeks.

The dark side

Listing 8-7 · same procedure, very different value
EXEC dbo.OrdersByQty @OrderQty = 1;
GO

The cached plan is reused — it was compiled for 46 rows, and now 74,954 rows match. So the Key Lookup executes 74,954 times. Logical reads go from 424 to 239,186; runtime from about 10 ms to about 1,400 ms.

Listing 8-8 · flush one plan, not the whole cache
DECLARE @PlanHandle VARBINARY(64);
SELECT  @PlanHandle = deps.plan_handle
FROM    sys.dm_exec_procedure_stats AS deps
WHERE   deps.object_id = OBJECT_ID('dbo.OrdersByQty');
IF @PlanHandle IS NOT NULL
    BEGIN
        DBCC FREEPROCCACHE(@PlanHandle);
    END
GO

Re-run Listing 8-7 and the optimizer compiles fresh, reads the histogram, estimates 74,954 rows (spot on), and chooses the clustered index scan: 1,512 logical reads instead of 239,186. Same result set.

The four ways out

FixWhat it doesWhat it costs
OPTION (RECOMPILE)Recompiles that one statement for the actual value every timeCompilation on every execution. Put it on only the affected statement, not the whole procedure.
OPTION (OPTIMIZE FOR @p = 20)Forces the plan to be built for a value you chooseYou must know the best value — and it may stop being the best as data changes.
OPTION (OPTIMIZE FOR (@p UNKNOWN))Generic plan from the density graph (2,958.95 rows here)Deliberately imprecise: fine for most values, poor for the extremes.
Plan forcing (Chapter 9)Pin a known-good planThe data may move out from under the pinned plan.

A useful side effect of RECOMPILE: because the plan will never be reused, the optimizer no longer has to play safe with the optional parameter, so the Index Seek comes back instead of the Index Scan.

5 Columnstore indexes

Different storage, different rules: no seeks at all, aggregation that happens inside the scan, and estimated rows that mean the opposite of what you expect.

A columnstore index stores data by column rather than by row — all the values for one column packed into their own pages and compressed. A clustered columnstore replaces the heap with a column-wise copy of the whole table; a nonclustered columnstore can sit alongside your normal rowstore indexes.

Built forData warehouse and reporting: very large tables (millions to billions of rows), queries that touch all rows or large selections, aggregations.
Terrible forSingle-row or small-subset lookups — the engine has to read a page per column to reconstruct one row. Below ~100,000 rows per partition you also lose most of the compression benefit.
Listing 8-9 · baseline aggregation query
SELECT p.Name,
       COUNT(th.ProductID) AS CountProductID,
       SUM(th.Quantity) AS SumQuantity,
       AVG(th.ActualCost) AS AvgActualCost
FROM Production.TransactionHistory AS th
    JOIN Production.Product AS p
        ON p.ProductID = th.ProductID
GROUP BY th.ProductID,
         p.Name;

That plan returns 441 rows in an average 127 ms, with 803 logical reads. Now add a nonclustered columnstore index over just the columns the query needs:

Listing 8-10 · add a nonclustered columnstore index
CREATE NONCLUSTERED COLUMNSTORE INDEX ix_csTest
ON Production.TransactionHistory
(
    ProductID,
    Quantity,
    ActualCost,
    ReferenceOrderID,
    ReferenceOrderLineID,
    ModifiedDate
);

Same query, same 441 rows: 55 ms and 84 logical reads. The structure lets the engine read only the requested columns and skip the rest of the table entirely.

Aggregate pushdown

That looks like a contradiction until you know about aggregate pushdown (SQL Server 2016+). Because the data is stored pivoted by column, the scan itself can do some or all of the aggregation and inject the results straight into the aggregating operator. The arrow out of the operator only carries rows that couldn't be aggregated locally — here, none. That's why the Hash Match (Aggregate) appears to thicken the arrow: rows arrive out of band, not through it.

No seek, but predicates get pushed down

Listing 8-11 · add a filter
SELECT p.Name,
       COUNT(th.ProductID) AS CountProductID,
       SUM(th.Quantity) AS SumQuantity,
       AVG(th.ActualCost) AS AvgActualCost
FROM Production.TransactionHistory AS th
    JOIN Production.Product AS p
        ON p.ProductID = th.ProductID
WHERE th.TransactionID > 150000
GROUP BY th.ProductID,
         p.Name;

The plan keeps the same shape and the same operators — still a Columnstore Index Scan. There is no Seek operator for a columnstore index, ever: the data isn't sorted, so there's no structure to navigate to a value. Filtering is done by pushing the predicate into the scan.

Pushdown matters far more here than on a rowstore index, because a pushed predicate enables rowgroup elimination (older documentation calls it segment elimination). Each partition is split into rowgroups of up to about a million rows, compressed together; with min/max metadata per rowgroup, whole rowgroups can be skipped without being read. You see it in SET STATISTICS IO as "segment skipped":

Note the two things a columnstore changes about STATISTICS IO: rowstore reads are near zero (the data comes through LOB reads), and there's a new segment reads / segment skipped line. On this 113K-row table everything is in one rowgroup, so nothing is skipped — on a 60-million-row table that count is where your win shows up.
Compare actual to estimated execution mode On a columnstore scan, both should read Batch (Figure 8-15). If actual says Row while estimated says Batch, you have a batch-mode plan that fell back to row mode mid-execution — catastrophic for performance. Per the book this is only an issue on SQL Server 2012, where a batch-mode plan falls back when a hash operation spills to tempdb.

6 Memory-optimized indexes

Two new index structures, and plans that look almost reassuringly normal — with two sharp edges: a hash index can't do ranges, and natively-compiled plans report every cost as zero.

Hash indexAn array of hash buckets; each bucket points at a row in memory. Point lookups only — it's the fastest thing in the book for WHERE key = value.
Range indexA Bw-tree, the memory-optimized cousin of the B-tree. Used for ranges and ordering. This is what you need when the hash index can't help.

These exist for the very-high-throughput OLTP case where you'd otherwise be bottlenecked on page latches. Their other common use is making table variables faster (Chapter 7's 100-row estimate relies on the same machinery).

Where the hash index falls over

Listing 8-15 · change the point lookup into a range
SELECT a.AddressLine1,
       a.City,
       sp.StateProvinceName,
       cr.CountryRegionName
FROM dbo.Address AS a
    JOIN dbo.StateProvince AS sp
        ON sp.StateProvinceID = a.StateProvinceID
    JOIN dbo.CountryRegion AS cr
        ON cr.CountryRegionCode = sp.CountryRegionCode
WHERE a.AddressID BETWEEN 42
                  AND     52;

The fix would be a memory-optimized nonclustered (range) index on AddressID. This is the general lesson: a hash index is a point-lookup machine, and the plan tells you immediately when you've asked it for something else.

Natively-compiled procedures: costs of zero

Listing 8-16 · natively-compiled version of the range query
CREATE OR ALTER PROC dbo.AddressDetails @AddressIDMin INT, @AddressIDMax INT
WITH NATIVE_COMPILATION, SCHEMABINDING, EXECUTE AS OWNER AS
BEGIN ATOMIC WITH (TRANSACTION ISOLATION LEVEL = SNAPSHOT, LANGUAGE = N'us_english')
 SELECT a.AddressLine1,
       a.City,
       sp.StateProvinceName,
       cr.CountryRegionName
FROM dbo.Address AS a
    JOIN dbo.StateProvince AS sp
        ON sp.StateProvinceID = a.StateProvinceID
    JOIN dbo.CountryRegion AS cr
        ON cr.CountryRegionCode = sp.CountryRegionCode
WHERE a.AddressID BETWEEN @AddressIDMin
                  AND     @AddressIDMax;
END
GO
EXECUTE dbo.AddressDetails @AddressIDMin = 42, -- int
                           @AddressIDMax = 52;  -- int
You cannot get an actual plan for a natively-compiled procedure That's a real limitation. Estimated plans only.

The costs are zero because these procedures are costed in a new way that isn't exposed externally; the plans aren't even in the plan cache. You lose costs and row counts, which weakens your ability to make decisions — but you still see which operators ran and in what order, which is often enough to explain why a query is slow. And if you add a range index later, the plan won't visibly change: the engine picks the index at runtime.

  • The optimizer doesn't judge your index — it prices it. Every decision in this chapter is estimated rows × estimated cost.
  • Seek vs. scan is an estimate fight, not a data fight. Listing 8-4 returns 46 rows and gets a scan; Listing 8-2 returns the same 46 and gets a seek.
  • Variables kill estimates. Density (2,958.95 rows) for equality, a blanket 30% for inequality.
  • Reused plans are reused decisions. A plan compiled for 46 rows run against 6,068 rows costs 19,385 reads.
  • Compiled value ≠ runtime value is the one property that diagnoses parameter sniffing in seconds.
  • Columnstore: pushdown and pushdown. Predicate pushdown → rowgroup elimination; aggregate pushdown → locally aggregated rows that never travel the arrow.
  • Memory-optimized: hash for points, Bw-tree for ranges. Estimated costs are lower because they assume memory — don't compare them to rowstore plan costs.
  • Zero costs still have a shape. Natively-compiled plans omit the numbers but keep the operator order, which explains the slowness even when it can't measure it.
The chapter's summary, condensed Indexes and their statistics decide plan quality. You can't fix every query by adding an index, and too many indexes is its own problem. Be selective with predicates, judicious with columns, and certain that statistics reflect the data. Hard-coded values give exact estimates but no plan reuse; sniffing gives exact estimates and reuse — until the next parameter value is wildly different from the one the plan was built for. Everything here is a trade-off, and there is not always a single correct answer.
