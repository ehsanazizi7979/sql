Chapter 14

Plans for Special Data Types and Cursors

XML, JSON, HIERARCHYID, geography and cursors all bend the optimizer into shapes you haven't seen yet: a single Remote Scan that swallows a whole OPENXML statement, fixed 10,000- and 50-row estimates, and operators that hide rather than show the work. This chapter is a field guide to spotting them.

1 Special types only show up when you process them

Storing an XML document or a geography point in a column is invisible to the plan. What shows up is the moment you ask SQL Server to convert between that type and ordinary rows.

That's the key idea, and it's why this chapter is really about four conversions plus one programming style. The plan-level triggers are:

Converting

  • Relational → XML: the FOR XML clause. New operator: XML SELECT, or UDX.
  • XML → relational: the OPENXML rowset provider. New operator: Remote Scan (all work hidden).
  • Querying XML: XQuery methods. New operators: Table-Valued Function (XML Reader) and UDX.
  • JSON: no JSON type at all — FOR JSON and OPENJSON still leave fingerprints.

Behaving differently

  • HIERARCHYID: a CLR type over varbinary. Plans look ordinary — the curiosity is in the Seek Predicate.
  • Spatial: geometry/geography, with a very complex index and even more complex plans.
  • Cursors: not a data type, a row-by-row behaviour. Represented by placeholder icons in estimated plans, and by floods of separate plans in actual ones.
The cost that isn't in the operator Manipulating XML uses the XML parser, which consumes memory and CPU that you'd otherwise have for T-SQL. The book's advice is blunt: be judicious about how much XML you push through SQL Server, and don't assume the operator cost you see is the whole story.

2 Relational → XML: FOR XML

Three of the four FOR XML modes produce the same plan. The fourth makes you rewrite the query, and that rewrite — not the XML — is what doubles the cost.

Start with a plain relational query, so you have a baseline to compare against.

Listing 14-1 · the baseline
SELECT s.Name AS StoreName,
       bec.PersonID,
       bec.ContactTypeID
FROM Sales.Store AS s
    JOIN Person.BusinessEntityContact AS bec
        ON s.BusinessEntityID = bec.BusinessEntityID
ORDER BY s.Name;

Now add one clause. AUTO, RAW and PATH all behave identically at the plan level.

Listing 14-2 · same query, XML output
SELECT s.Name AS StoreName,
       bec.PersonID,
       bec.ContactTypeID
FROM Sales.Store AS s
    JOIN Person.BusinessEntityContact AS bec
        ON s.BusinessEntityID = bec.BusinessEntityID
ORDER BY s.Name
FOR XML AUTO;

Which is the first genuinely useful fact in the chapter: choosing between AUTO, RAW and PATH costs nothing at runtime. Pick the shape of XML you want; the optimizer doesn't care. The output really is different, though, for the same first row:

The same row, three modes
-- AUTO:
<s StoreName="A Bicycle Association">
  <bec PersonID="2050" ContactTypeID="11" />
</s>
-- RAW:
<row StoreName="A Bicycle Association" PersonID="2050"
     ContactTypeID="11" />
-- PATH
<row>
  <StoreName>A Bicycle Association</StoreName>
  <PersonID>2050</PersonID>
  <ContactTypeID>11</ContactTypeID>
</row>

The TYPE directive, and the 10× cost

Without TYPE, that output is just a string that looks like XML. With TYPE it's a real xml value — which matters mostly when you nest FOR XML inside a subquery.

Listing 14-3 · a nested FOR XML with TYPE
SELECT s.Name AS StoreName,
       (   SELECT bec.BusinessEntityID,
                  bec.ContactTypeID
           FROM Person.BusinessEntityContact AS bec
           WHERE bec.BusinessEntityID = s.BusinessEntityID
           FOR XML AUTO, TYPE, ELEMENTS) AS contact
FROM Sales.Store AS s
ORDER BY s.Name
FOR XML AUTO;

That plan costs 1515 logical reads — about ten times Listing 14-2. Not because of the XML type, but because the subquery forces a Nested Loops join: the outer input returns 701 rows (BusinessEntityID + Name, sorted by Name), each of those IDs is pushed into the inner input, and the seek runs 701 times. That's the real bill.

Reading a UDX operator It's a generic "user-defined extension" box. The only useful property is Name — FOR XML, FOR JSON, or an XQuery transform. It appears constantly in this chapter, and that one property is how you tell the cases apart. The Compute Scalar after it (renaming Expr1002 to Expr1004) does nothing you need to understand.

EXPLICIT: you pay for the rewrite

EXPLICIT gives total control over the XML shape, but the rowset you feed it must obey strict formatting rules. Try Listing 14-2 with it and you get Msg 6803: FOR XML EXPLICIT requires the first column to hold positive integers that represent XML tag IDs. So you hand-build the hierarchy with UNION ALL:

Listing 14-4 · EXPLICIT mode, hand-built hierarchy
SELECT  1 AS Tag,
        NULL AS Parent,
        s.Name AS [Store!1!StoreName],
        NULL AS [BECContact!2!PersonID],
        NULL AS [BECContact!2!ContactTypeID]
FROM    Sales.Store s
JOIN    Person.BusinessEntityContact AS bec
        ON s.BusinessEntityID = bec.BusinessEntityID
UNION ALL
SELECT  2 AS Tag,
        1 AS Parent,
        s.Name AS StoreName,
        bec.PersonID,
        bec.ContactTypeID
FROM    Sales.Store s
JOIN    Person.BusinessEntityContact AS bec
        ON s.BusinessEntityID = bec.BusinessEntityID
ORDER BY [Store!1!StoreName],
        [BECContact!2!PersonID]
FOR     XML EXPLICIT;
Blame the UNION ALL, not EXPLICIT The doubling is an indirect result of the option's requirements — it made you write the same query twice. You get precise control over the XML and pay for it in duplicated work. And as always: drop the FOR XML EXPLICIT clause and the plan changes only by XML Select → Select.

3 XML → relational: OPENXML and the Remote Scan

A whole statement's worth of XML parsing collapses into one operator, because it happens outside the query engine. What's left in the plan is a fixed 10,000-row guess.

OPENXML turns an XML document held in nvarchar into a rowset you can treat as a table — usable anywhere a table is, including the FROM of INSERTs, but never as the target of one. You need a document first:

Listing 14-5 · the document (elements wrapped to fit)
<ROOT>
  <Currency CurrencyCode="UTE"
     CurrencyName="Universal Transactional Exchange">
    <CurrencyRate FromCurrencyCode="USD" ToCurrencyCode="UTE"
                   CurrencyRateDate="2007/1/1" AverageRate=".553"
                   EndOfDateRate=".558" />
    <CurrencyRate FromCurrencyCode="USD" ToCurrencyCode="UTE"
                   CurrencyRateDate="2017/6/1" AverageRate=".928"
                   EndOfDateRate="1.057" />
  </Currency>
</ROOT>

Then shred it into two tables — the whole lifecycle, preparedocument to removedocument:

Listing 14-6 · insert from XML in a batch
BEGIN TRAN;
DECLARE @iDoc AS INT;
DECLARE @Xml AS NVARCHAR(MAX);

SET @Xml = '<ROOT>
<Currency CurrencyCode="UTE" CurrencyName="Universal
  Transactional Exchange">
   <CurrencyRate FromCurrencyCode="USD" ToCurrencyCode="UTE"
     CurrencyRateDate="2007/1/1" AverageRate=".553"
     EndOfDayRate=".558" />
   <CurrencyRate FromCurrencyCode="USD" ToCurrencyCode="UTE"
     CurrencyRateDate="2007/6/1" AverageRate=".928"
     EndOfDayRate="1.057" />
</Currency>
</ROOT>';

EXEC sys.sp_xml_preparedocument
    @iDoc OUTPUT,
    @Xml;

INSERT  INTO Sales.Currency
        (CurrencyCode, Name, ModifiedDate)
SELECT  CurrencyCode,
        CurrencyName,
        GETDATE()
FROM    OPENXML (@iDoc, 'ROOT/Currency', 1)
           WITH (CurrencyCode NCHAR(3), CurrencyName NVARCHAR(50));

INSERT  INTO Sales.CurrencyRate
        (CurrencyRateDate, FromCurrencyCode, ToCurrencyCode,
         AverageRate, EndOfDayRate, ModifiedDate)
SELECT  CurrencyRateDate,
        FromCurrencyCode,
        ToCurrencyCode,
        AverageRate,
        EndOfDayRate,
        GETDATE()
FROM    OPENXML (@iDoc, 'ROOT/Currency/CurrencyRate', 2)
          WITH (CurrencyRateDate DATETIME  '@CurrencyRateDate',
                FromCurrencyCode NCHAR(3)  '@FromCurrencyCode',
                ToCurrencyCode   NCHAR(3)  '@ToCurrencyCode',
                AverageRate      MONEY     '@AverageRate',
                EndOfDayRate     MONEY     '@EndOfDayRate');

EXEC sys.sp_xml_removedocument
    @iDoc;
ROLLBACK TRAN;

Two INSERTs, so two actual plans. The first is startlingly small:

Remote Scan means "an object outside the query engine is producing these rows" — a DLL or a CLR object, in this case the MSXML parser. Because it isn't part of the engine, the optimizer draws it as a single opaque box. The only XML evidence is in its Output List:

Everything after it is ordinary: sorted once for the clustered index, sorted again for the nonclustered index. And exactly one row is inserted. So why the Sort at all? Because the optimizer assumes 10,000 rows will come back from a Remote Scan. That's a hard-coded estimate, and it drives every downstream choice.

Read the arrow widths In the actual plan the arrow into Compute Scalar is thin (1 row actual) and the arrow out is fat (10,000 estimated) — a Compute Scalar never does real work, so it only ever reports estimates. Mismatched arrow sizes around a Compute Scalar are a shortcut to finding a bad estimate.
What to do about it You cannot fix the 10,000. If it's hurting you, load the XML into a temporary table first so the optimizer gets real statistics and plans the rest of the work properly. Separately: parsing XML is memory-hungry, so get in, shred, and sp_xml_removedocument as fast as you can.

4 Querying XML with XQuery

Five methods, two new operators. The surprise is how much of a FLWOR expression the optimizer evaluates as ordinary relational work.

The five methods on the xml type, and the two operators the optimizer reaches for:

MethodReturnsWhat it's for
.query()xmlReturn some or all of the XML you're querying.
.value()a scalarExtract one typed value out of the XML.
.nodes()a rowsetShred XML into rows — the pivot you saw in Chapter 13.
.exist()bitDoes the XPath match anything? Like EXISTS.
.modify()—Insert, update or delete XML fragments in place.

Implemented with Table-Valued Function (XML Reader), with or without an XPath filter, plus UDX, in varying combinations. Two examples follow — one filter, one transform.

.exist(): filter on the document

Listing 14-7 · was this person ever a sales manager?
SELECT p.LastName, p.FirstName, e.HireDate, e.JobTitle
  FROM Person.Person AS p
    INNER JOIN HumanResources.Employee AS e
      ON p.BusinessEntityID = e.BusinessEntityID
    INNER JOIN HumanResources.JobCandidate AS jc
      ON e.BusinessEntityID = jc.BusinessEntityID
     AND jc.Resume.exist(
           'declare namespace
        res="http://schemas.microsoft.com/sqlserver/2004/07/
adventure-works/Resume";
        /res:Resume/res:Employment/res:Emp.JobTitle[contains
             (.,"Sales Manager")]') = 1;

The TVF hands its rows — two columns, value and lvalue — to a Filter, which checks that the XPath result equals 1 and is not null (the null check is redundant, but present). One row survives. The rest of the plan is textbook.

The TVF has no plan of its own Unlike a multi-statement TVF, the internal ones XQuery uses can't be found in the plan cache, the Query Store, or an estimated plan. Its execution is purely internal — the operator's properties are all you get. Like Remote Scan, it plays the role of "shredded rows appear here", but unlike Remote Scan it is part of the engine and gets its own icon.

.query(): filter and rebuild the XML

This one uses FLWOR (For, Let, Where, Order, Return) and is the most instructive plan in the chapter, because it visibly splits into three jobs.

Listing 14-8 · stores over 20,000 sq ft for one salesperson
SELECT s.Name,
  s.Demographics.query
('
   declare namespace ss="http://schemas.microsoft.com/
sqlserver/2004/07/adventure-works/StoreSurvey";
   for $s in /ss:StoreSurvey
   where ss:StoreSurvey/ss:SquareFeet > 20000
   return $s
') AS Demographics
  FROM Sales.Store AS s
  WHERE s.SalesPersonID = 279;

Three responsibilities, in order:

Part 1 · relational access
-- Clustered Index Scan on Sales.Store
--   Filter: SalesPersonID = 279
--     -> top input of Nested Loops (Left Outer Join)
--     -> pushes BusinessEntityID + Demographics
--        into the lower input via Outer References

And then the tell-tale: the Filter in that subtree is the FLWOR where clause. Its predicate tests the extracted column value against 20000. In other words, the engine pulled the value out of the XML, made it relational, and compared it with an ordinary Filter operator. Not all FLWOR logic is pushed into an XML-specific operator — and this is how you can tell which part wasn't.

Part 3 · back to XML
-- Compute Scalar: prep work for the UDX
-- UDX:     rowset -> XML again
-- Filter:  Startup Expression Predicate
--          = skip this whole subtree when
--            Demographics IS NULL
The mental model, restated XQuery against an XML column is: relational access → extract to a rowset → ordinary operators (filters, joins) → convert back to XML. Once you see that, the odd-looking operators are just the two conversion boundaries.

When to use it: XQuery can replace FOR XML (expect some performance degradation) and it can replace OPENXML (with more capability, and a genuine plan rather than a black box). Test both before committing.

5 JSON: no type, still fingerprints

JSON arrived in SQL Server 2016 but never got a data type — it lives in nvarchar. So there are no methods and no XML indexes; just conversions with a couple of revealing properties.

AdventureWorks has no JSON, so build some. Note the twin fixed estimates coming up.

Listing 14-9 · build a JSON column with FOR JSON PATH
SELECT p.BusinessEntityID,
       p.Title,
       p.FirstName,
       p.LastName,
       (   SELECT p2.FirstName AS "person.name",
                  p2.LastName AS "person.surname",
                  p2.Title,
                  p2.BusinessEntityID
           FROM Person.Person AS p2
           WHERE p.BusinessEntityID = p2.BusinessEntityID
           FOR JSON PATH) AS JsonData
INTO dbo.PersonJson
FROM Person.Person AS p;

Only two things in that plan are worth naming:

  • An Index Spool exists so the Clustered Index Scan isn't re-run per row. Check the Execution Count: both Clustered Index Scans show 1, while the spool shows 19,972 — once per row.
  • A UDX does the JSON conversion, and its Name = FOR JSON is the only clue you'll get.

Reading it back with OPENJSON

Listing 14-10 · shred the JSON with OPENJSON
SELECT oj.FirstName,
       oj.LastName,
       oj.Title
FROM dbo.PersonJson AS pj
    CROSS APPLY
    OPENJSON(pj.JsonData, N'$')
    WITH (FirstName VARCHAR(50) N'$.person.name',
          LastName  VARCHAR(50) N'$.person.surname',
          Title     VARCHAR(8)  N'$.Title',
          BusinessEntityID INT N'$.BusinessEntityID') AS oj
WHERE oj.BusinessEntityID = 42;

The Nested Loops looks crazy: ~19,972 rows scanned means ~19,972 executions of a fairly expensive TVF. But CROSS APPLY gives the inner input a different row for each outer row, and Nested Loops is the only way the optimizer can currently implement that — it has no choice. Then note the estimate: a fixed 50 rows per execution, when in fact it returns one.

The shredding-then-filtering problem The Filter sits after the TVF, so SQL Server shreds the JSON in every row and only then discards all but BusinessEntityID 42. What you want is the predicate pushed down so only the needed rows get shredded — and it doesn't happen. The book's remedy: put the commonly-filtered JSON values in a persisted computed column and index that.

That's the end of the JSON evidence. There is no further insight into how conversion happens — these hints, plus the two fixed estimates, are the whole story.

6 HIERARCHYID: boring plans, interesting predicate

A CLR type from SQL Server 2008 that stores a path as varbinary. Plans for it look almost suspiciously clean — the machinery is all inside the Seek Predicate.

Listing 14-11 · everyone under one manager
DECLARE @ManagerID HIERARCHYID;
SELECT @ManagerID = e.OrganizationNode
  FROM HumanResources.Employee AS e
  WHERE e.JobTitle = 'Vice President of Engineering';

SELECT e.BusinessEntityID, p.LastName
  FROM HumanResources.Employee AS e
    JOIN Person.Person AS p
      ON e.BusinessEntityID = p.BusinessEntityID
  WHERE e.OrganizationNode.IsDescendantOf(@ManagerID) = 1;

The predicate IsDescendantOf(...) = 1 became a genuine Index Seek, not a scan-plus-filter. Look at the Seek Predicate and you see why the type exists:

Add a column, lose the seek Include JobTitle and the index stops being covering: you get either a Clustered Index Scan, or a Seek plus Key Lookup, depending on the cost estimates. Your "clean" plan is one column away from a different shape.

7 Spatial: a simple query, a very complicated plan

Spatial indexes work with some functions but not all, and they tessellate the globe. The plan reflects every bit of that — while still using operators you already know.

Listing 14-12 · addresses within a kilometre of a point
DECLARE @MyLocation GEOGRAPHY = geography::STPointFromText(
    'POINT(-122.33383 47.610870)', 4326);

SELECT a.AddressLine1,
       a.City,
       a.PostalCode,
       a.SpatialLocation
FROM Person.Address AS a
WHERE @MyLocation.STDistance(a.SpatialLocation) < 1000;

No spatial index yet, so there's nothing clever to do:

Listing 14-13 · add a spatial index
CREATE SPATIAL INDEX TestSpatial
ON Person.Address (SpatialLocation)
USING GEOGRAPHY_GRID
WITH (GRIDS = (LEVEL_1 = MEDIUM, LEVEL_2 = MEDIUM,
                LEVEL_3 = MEDIUM, LEVEL_4 = MEDIUM),
      CELLS_PER_OBJECT = 16,
      PAD_INDEX = OFF,
      SORT_IN_TEMPDB = OFF,
      DROP_EXISTING = OFF,
      ALLOW_ROW_LOCKS = ON,
      ALLOW_PAGE_LOCKS = ON)
ON [PRIMARY];
GO

Rerun Listing 14-12 and the cost drops from 19.9 to 0.67 — for a plan with far more operators in it.

Tessellation is the trick: rather than a range of values, the engine computes which grid cells cover your 1,000-metre radius and looks those up.

And the seek itself doesn't look like any seek you've met:

Listing 14-14 · clean up
DROP INDEX TestSpatial ON Person.Address;
Same tools, harder puzzle There are no new operators to learn here — the difficulty is entirely in the configuration. That is exactly why spatial plans are hard to troubleshoot: nothing is unfamiliar, there's just a great deal of it.

8 Cursors: Population Query and Fetch Query

Not a data type — a processing behaviour, one row at a time. A cursor's plan is really two queries wearing one icon, and the difference between cursor types is what those two queries do.

The mental model to hold on to:

Population QueryHow the result set is collected. Runs once, at OPEN.
Fetch QueryHow each row is retrieved. Runs once per FETCH.
Catch-allOne placeholder Cursor icon each for OPEN, FETCH, CLOSE, DEALLOCATE. Estimated plans only, properties mostly useless.

Static cursor: snapshot into a temp table

Listing 14-15 · STATIC cursor, deliberately doing nothing
DECLARE CurrencyList CURSOR STATIC FOR
SELECT c.CurrencyCode, cr.Name
  FROM Sales.Currency AS c
    JOIN Sales.CountryRegionCurrency AS crc
      ON crc.CurrencyCode = c.CurrencyCode
    JOIN Person.CountryRegion AS cr
      ON cr.CountryRegionCode = crc.CountryRegionCode
  WHERE c.Name LIKE '%Dollar%';

OPEN CurrencyList;
FETCH NEXT FROM CurrencyList;

WHILE @@Fetch_Status = 0
  BEGIN
    -- Normally there would be operations here using cursor data
    FETCH NEXT FROM CurrencyList;
  END

CLOSE CurrencyList;
DEALLOCATE CurrencyList;
GO

Now the behaviour. A static cursor must not see later changes, so OPEN simply runs the query into a temporary table and FETCH reads from that table. Two plans, and the second one is a tempdb lookup:

That row number is an artificial primary key on the cursor's result set. All of it lands in a temporary clustered index called CWT_PrimaryKey — and it's in tempdb:

Don't capture actual plans for cursors It's expensive and produces a wall of near-identical plans. Use Extended Events for a single execution, or SET STATISTICS XML ON around one statement.

Keyset cursor: store the keys, re-read the rows

A keyset cursor shouldn't show new rows, but should show changed data in existing ones. So the Population Query stores key values, and the Fetch Query uses them to go back and get current values. Same query, different declaration:

Listing 14-16 · KEYSET cursor
DECLARE CurrencyList CURSOR KEYSET
FOR
SELECT c.CurrencyCode,
       cr.Name
FROM Sales.Currency AS c
    JOIN Sales.CountryRegionCurrency AS crc
        ON crc.CurrencyCode = c.CurrencyCode
    JOIN Person.CountryRegion AS cr
        ON cr.CountryRegionCode = crc.CountryRegionCode
WHERE c.Name LIKE '%Dollar%';

OPEN CurrencyList;
FETCH NEXT FROM CurrencyList;

WHILE @@FETCH_STATUS = 0
    BEGIN
 -- Normally there would be operations here using data from cursor
        FETCH NEXT FROM CurrencyList;
    END

CLOSE CurrencyList;
DEALLOCATE CurrencyList;
GO

Dynamic cursor: no population query at all

Listing 14-17 · the only change
DECLARE CurrencyList CURSOR DYNAMIC

A Compute Scalar adds an ID, the results go into a temporary clustered index (so you can move backwards as well as forwards), and the data is retrieved repeatedly. That's why dynamic is the least efficient cursor type. Capturing actual plans just shows the same plan over and over.

One honest gap in the book There are apparently internal checks that stop the engine re-running the query every single time — the author says the details aren't known. Planning advice: assume it does re-run it.

9 Cheat sheet

If you remember nothing else from this chapter, remember which operator to look for, and which fixed estimate to distrust.

FeatureWhat appears in the planThe catch
FOR XML AUTO / RAW / PATHXML SELECT instead of SELECTIdentical plan in all three; only the XML shape differs. Free choice.
FOR XML ... , TYPEUDX (Name = FOR XML)Nested subquery ⇒ Nested Loops ⇒ one seek per outer row (1515 reads vs ~150).
FOR XML EXPLICITTwo nearly identical branches~2× cost, caused by the UNION ALL the mode forces you to write.
OPENXMLOne Remote ScanEverything hidden; fixed estimate of 10,000 rows ⇒ pointless Sorts and Merge Joins. Arrow widths around Compute Scalar expose it.
.exist()TVF (XML Reader with XPath filter) + FilterTVF has no plan of its own; outputs value/lvalue; Filter tests = 1.
.query()3 parts: relational access → XML index seeks + Filter → Compute Scalar + UDXFLWOR where is evaluated relationally; Startup Expression Predicate skips the subtree for NULLs.
FOR JSON PATHUDX (Name = FOR JSON) + Index SpoolSpool at 19,972 executions; nothing else is visible about the JSON.
OPENJSONTVF (OPENJSON_EXPLICIT) under Nested LoopsFixed estimate of 50 rows per execution. Shreds every row before the Filter — use a persisted computed column.
HIERARCHYIDOrdinary Index SeekRead the Seek Predicate: Start/End from DescendantLimit. Adding a column can kill the seek.
SpatialVery wide plan, TVF (tessellation), Clustered Index Seek (Spatial)Same operators, far more of them. Cost 19.9 → 0.67 with the index.
CursorCursor-type operator + Population Query + Fetch QueryStatic = temp table; Keyset = keys + Key Lookups + Left Outer joins; Dynamic = Fetch only, re-runs. Actual plans = one per row.

The three fixed estimates, and what they wreck

  • 10,000 rows — OPENXML / Remote Scan. Produces unnecessary Sorts and Merge Joins. Fix: stage into a temp table for real statistics.
  • 50 rows — OPENJSON TVF. Contributes to a badly-sized Nested Loops over every row in the table.
  • 1 row — not a fixed estimate, but the fact that the OPENJSON TVF actually returns one row per execution while estimating 50 makes the shape look reasonable when it isn't.
  • Storing a special type costs nothing; processing it does. Look for the conversion boundary.
  • UDX and Remote Scan are black boxes. Name is the only clue on a UDX; a Remote Scan tells you nothing at all.
  • The TVF (XML Reader) is part of the engine but has no cacheable plan — don't go hunting in the plan cache for it.
  • Much XQuery runs as normal relational operators. A Filter on an extracted value column is your FLWOR where.
  • Cursor plans are two queries. Judge the Population Query and the Fetch Query separately.
  • None of this changes how you read a plan. Same operators, extra values — drill into the properties and walk the data flow.
The chapter's summary, condensed XML, hierarchical, spatial and JSON expand what you can store, and each leaves its own fingerprint on the plan; cursors add row-by-row behaviour on top. But the operators and the method don't change: follow the rows, open the properties, and read the estimates — especially the ones that were hard-coded before your query was ever seen.
