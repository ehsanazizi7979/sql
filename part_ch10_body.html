Chapter 10

Controlling Execution Plans with Hints

The chapter where the book stops being a tutorial and becomes an intervention. Eleven hints, measured one by one — and most of them make the query worse. Hints are commandments, not suggestions, and this chapter is the evidence.

! The ground rules

If you take one thing from this chapter, take the warning. The demos are the proof.

The optimizer gets it right most of the time. The cases where it doesn't are well understood by now: jagged data distributions that statistics can't describe accurately, complex predicates that are hard to estimate, and predicates that force a hard-coded selectivity guess (Chapters 8 and 9). In those cases you may want to force the optimizer's hand with hints about how to access tables, which join strategy to use, or how to optimize an entire query. But:

Hints are not suggestions. They are commandments. The optimizer must obey them — even when obeying is impossible or absurd, in which case it raises an error rather than quietly doing something sensible (you'll see that with the INDEX() hint). A hint that is right for one query can radically slow another, cause severe blocking and timeouts, and it removes the optimizer's ability to pick a better plan later when the data changes, or when you patch or upgrade SQL Server.

The book's rule of thumb is a good one: if you're putting hints on most of your queries, you're doing something wrong. Apply one only after copious testing, document why it's there, and schedule re-testing as the system changes. This chapter deliberately shows as many hints hurting as helping, "as this simply reflects reality. Hints more often hurt performance than they help it."

Query hintsApply to the whole query via the OPTION clause — every operator, every join, every aggregate. Cannot be used on INSERT (except in its associated SELECT) and cannot be used in subqueries.
Join hintsApply to one specific join, written in the JOIN clause. A join hint overrides the matching query hint.
Table hintsApply to one table: which index, seek or scan, expand an indexed view or not. Worse than the others — some also change locking and can affect data integrity.
NoteTable hints go in WITH ( … ). Always use WITH and always comma-separate: safe, consistent and future-proof.

1 Aggregation and UNION hints

Two hints that each add an operator the optimizer had deliberately avoided. Both times, the plan gets more expensive.

Listing 10-1 · the OPTION clause
  SELECT ...
  OPTION (<hint>,<hint>...);

HASH GROUP / ORDER GROUP

Listing 10-2 · the aggregation query
SELECT p.Suffix,
       COUNT(*) AS SuffixUsageCount
FROM Person.Person AS p
GROUP BY p.Suffix;
Listing 10-3 · forcing a Stream Aggregate
SELECT p.Suffix,
       COUNT(p.Suffix) AS SuffixUsageCount
FROM Person.Person AS p
GROUP BY p.Suffix
OPTION (ORDER GROUP);
The cost of disobeying the optimizer's judgement Estimated cost up 39% (2.99727 → 4.17893), and runtime 9.7 ms → 18 ms — a 100% increase. Note the COUNT(*) becoming COUNT(p.Suffix) in the book's listing; the point stands either way. And the deeper problem: the hint freezes this shape forever, regardless of new indexes or changed data. If you want stream aggregation, the fix is a nonclustered index the optimizer can use to deliver the order — not a hint.

MERGE / HASH / CONCAT UNION

Listing 10-4 · a UNION that's too slow
SELECT pm1.Name,
       pm1.ModifiedDate
FROM Production.ProductModel AS pm1
UNION
SELECT p.Name,
       p.ModifiedDate
FROM Production.Product AS p;

So: can a join operator do the de-duplication and lose that Sort?

Listing 10-6 · HASH UNION

Works here only because the probe (bottom) input is guaranteed duplicate-free. Note HASH UNION can never apply to UNION ALL, which the optimizer implements as Concatenation by definition.
The exception to remember If the bottom input had contained duplicates, the optimizer would have had to add a Distinct Sort or similar anyway — so the win evaporates. Try it by dropping the Name column from Listing 10-6. A hint doesn't make a plan cheap; it changes what the optimizer is allowed to consider.

2 LOOP / MERGE / HASH JOIN — four plans, one query

The most instructive comparison in the book: the same four-table query, four join hints, and a different definition of "better" every time.

These set the method for all joins in the query, including the semi-joins behind EXISTS and IN. A join hint on a specific join overrides them.

Listing 10-7 · the test query
SELECT pm.Name,
       pm.CatalogDescription,
       p.Name AS ProductName,
       i.Diagram
FROM Production.ProductModel AS pm
    LEFT JOIN Production.Product AS p
        ON pm.ProductModelID = p.ProductModelID
    LEFT JOIN Production.ProductModelIllustration AS pmi
        ON p.ProductModelID = pmi.ProductModelID
    LEFT JOIN Production.Illustration AS i
        ON pmi.IllustrationID = i.IllustrationID
WHERE pm.Name LIKE '%Mountain%'
ORDER BY pm.Name;

The LIKE '%Mountain%' is non-SARGable — it can never be an index seek, so the Clustered Index Scan on ProductModel is inevitable. The two small tables get scanned rather than seeked simply because they're so small that scanning costs nothing measurable.

Listing 10-8 · LOOP JOIN
...OPTION ( LOOP JOIN );
But I/O went up, not down 485 → 1,250 logical reads (73 ms, essentially unchanged), because the Product table is now scanned 37 times — once per row out of the Sort. The one genuine gain is the MemoryGrantInfo on the SELECT operator: a significantly smaller memory grant. That matters if the query runs constantly; it isn't the I/O reduction we were after.
Listing 10-9 · MERGE JOIN
OPTION  ( MERGE JOIN );
Fewest reads, worst of both worlds 116 logical reads — best so far — yet performance didn't improve (~83 ms). Two reasons: the extra Sort overhead nearly doubles the memory grant, and the rightmost Merge Join is a many-to-many join, which needs a worktable in tempdb (Chapter 4) and is far less efficient. Fewer reads ≠ faster.
Listing 10-10 · HASH JOIN
OPTION  ( HASH JOIN );

97 logical reads — the best — at roughly the original runtime, but with a memory grant up to about 6,080 KB from hashing every table. So: if you have severe I/O contention, this could be a win; under additional load, you'd have to test to know.

The verdict the chapter wants you to draw Four hints, four plans, minimal reward — and every one of them ignored the actual problem: the non-SARGable LIKE '%Mountain%'. The right fix is to change the database structure (or the search pattern) so that wildcard scans aren't necessary. Hints are what you reach for when the code and schema are out of your control.

3 FAST n — optimise for the first screenful

A hint that optimises for what the user perceives rather than what the query costs. It works — spectacularly — and the bill arrives at the storage layer.

Listing 10-11 · the full result set, ordered
SELECT soh.SalesOrderNumber,
       soh.OrderDate,
       soh.DueDate,
       sod.CarrierTrackingNumber,
       sod.OrderQty
FROM Sales.SalesOrderDetail AS sod
    JOIN Sales.SalesOrderHeader AS soh
        ON sod.SalesOrderID = soh.SalesOrderID
ORDER BY soh.DueDate DESC;
The warning is a false alarm The SELECT operator carries a warning: Type conversion in expression (CONVERT(nvarchar(23),[soh].[SalesOrderID],0)) may affect "CardinalityEstimate". It comes from a calculated column on SalesOrderHeader that this query never filters on — so it has no effect. Warnings are worth reading, not automatically obeying.
Listing 10-12 · FAST 10
OPTION  ( FAST 10 );
The mechanism, and the price Internally the optimizer treats the query as if it had TOP (10) — same plan choices, minus the operators that implement TOP. Estimated cost drops from 11.3573 to 2.72567, but that's the cost of the first ten rows. Hence the nonsense estimates: the Sort is estimated at 2.6 rows when it actually returns 31,465. And the reads: 1,935 → 106,505. On a busy server that trade-off can hurt everyone else.

4 FORCE ORDER and MAXDOP

One hint takes away the optimizer's join-order search. The other takes away its parallelism. Both are for the edges of the problem, not the middle.

FORCE ORDER

Listing 10-13 · ten tables, ten joins
SELECT pc.Name AS ProductCategoryName,
       ps.Name AS ProductSubCategoryName,
       p.Name AS ProductName,
       pdr.Description,
       pm.Name AS ProductModelName,
       c.Name AS CultureName,
       d.FileName,
       pri.Quantity,
       pr.Rating,
       pr.Comments
FROM Production.Product AS p
    LEFT JOIN Production.ProductModel AS pm
        ON p.ProductModelID = pm.ProductModelID
    LEFT JOIN Production.ProductSubcategory AS ps
        ON p.ProductSubcategoryID = ps.ProductSubcategoryID
    LEFT JOIN Production.ProductInventory AS pri
        ON p.ProductID = pri.ProductID
    LEFT JOIN Production.ProductReview AS pr
        ON p.ProductID = pr.ProductID
    LEFT JOIN Production.ProductDocument AS pd
        ON p.ProductID = pd.ProductID
    LEFT JOIN Production.Document AS d
        ON pd.DocumentNode = d.DocumentNode
    LEFT JOIN Production.ProductCategory AS pc
        ON ps.ProductCategoryID = pc.ProductCategoryID
    LEFT JOIN Production.ProductModelProductDescriptionCulture AS pmpdc
        ON pm.ProductModelID = pmpdc.ProductModelID
    LEFT JOIN Production.ProductDescription AS pdr
        ON pmpdc.ProductDescriptionID = pdr.ProductDescriptionID
    LEFT JOIN Production.Culture AS c
        ON c.CultureID = pmpdc.CultureID;
Listing 10-14 · FORCE ORDER
OPTION (FORCE ORDER);

So it does exactly what it says — and 149 ms → 166 ms because of all the extra Sorts. Worth knowing for three situations, though: you're certain your join order beats the optimizer's; you see optimizer timeouts on huge queries; or you see excessive compiles/recompiles from one query and need the plan to stabilise.

MAXDOP

The scenario is the nastiest one in practice: a query that's usually fine and occasionally terrible. Extended Events or Query Store eventually show you two plans.

The honest first question is why did it recompile, and why are the costs different? For a parameterized query, parameter sniffing is the prime suspect (Chapter 8). Here it's a simple query and the book chooses the "easy" fix. Note the advice around it: tune cost threshold for parallelism properly (don't leave it at 5), set MAXDOP at the database level rather than server level, and don't simply switch parallelism off — a well-configured system benefits from it.

Listing 10-15 · contrive a parallel plan, then reset
--enable advanced options
EXEC sys.sp_configure 'show advanced options', 1
GO
RECONFIGURE WITH OVERRIDE
GO
--change the cost threshold to 1
EXEC sp_configure 'cost threshold for parallelism', 1;
GO
RECONFIGURE WITH OVERRIDE;
GO
--Execute the query which will go parallel
SELECT wo.DueDate,
       MIN(wo.OrderQty) AS MinOrderQty,
       MIN(wo.StockedQty) AS MinStockedQty,
       MIN(wo.ScrappedQty) AS MinScrappedQty,
       MAX(wo.OrderQty) AS MaxOrderQty,
       MAX(wo.StockedQty) AS MaxStockedQty,
       MAX(wo.ScrappedQty) AS MaxScrappedQty
FROM Production.WorkOrder AS wo
GROUP BY wo.DueDate
ORDER BY wo.DueDate;
GO
--reset the cost threshold to the default value
--if your cost threshold is set to a different value, change the 5
EXEC sys.sp_configure 'cost threshold for parallelism', 5;
GO
RECONFIGURE WITH OVERRIDE;
GO
--disable advanced options
EXEC sys.sp_configure 'show advanced options', 0
GO
RECONFIGURE WITH OVERRIDE
GO
Listing 10-16 · MAXDOP 1
OPTION  ( MAXDOP 1 );

Add it and the plan becomes Figure 10-17 — serial, no parallelism at all. More commonly you'd use a value between 1 and the processor count, so a single long query can't take the whole box.

5 OPTIMIZE FOR and RECOMPILE

Two fixes for parameter sniffing, and the recursive irony: a hint that stops the optimizer guessing, and a hint that makes it guess again — every time.

OPTIMIZE FOR

Listing 10-17 · two values, two plans
SELECT  AddressID,
        AddressLine1,
        AddressLine2,
        City,
        StateProvinceID,
        PostalCode,
        SpatialLocation,
        rowguid,
        ModifiedDate
FROM    Person.Address
WHERE   City = 'Mentor';
SELECT  AddressID,
        AddressLine1,
        AddressLine2,
        City,
        StateProvinceID,
        PostalCode,
        SpatialLocation,
        rowguid,
        ModifiedDate
FROM    Person.Address
WHERE   City = 'London';
Put this in a procedure and the second value inherits the first value's plan Execute with Mentor first, then with London, and the cached plan does thousands of Key Lookups for a query that should scan. That's Chapters 8 and 9 in one sentence. Adding OPTIMIZE FOR (@City = 'London') "fixes" it — until the data changes and London stops being the common case. The book's honest view: OPTIMIZE FOR UNKNOWN is generally more stable than optimizing for any particular value.
Listing 10-18 · local variables get one generic plan
DECLARE @City NVARCHAR(30)
SET @City = 'Mentor'
SELECT  AddressID,
        AddressLine1,
        AddressLine2,
        City,
        StateProvinceID,
        PostalCode,
        SpatialLocation,
        rowguid,
        ModifiedDate
FROM    Person.Address
WHERE   City = @City;
SET @City = 'London'
SELECT  AddressID,
        AddressLine1,
        AddressLine2,
        City,
        StateProvinceID,
        PostalCode,
        SpatialLocation,
        rowguid,
        ModifiedDate
FROM    Person.Address
WHERE   City = @City;
Listing 10-19 · OPTIMIZE FOR UNKNOWN in a procedure
CREATE OR ALTER PROCEDURE dbo.AddressByCity @City NVARCHAR(30)
AS
SELECT  AddressID,
        AddressLine1,
        AddressLine2,
        City,
        StateProvinceID,
        PostalCode,
        SpatialLocation,
        rowguid,
        ModifiedDate
FROM    Person.Address
WHERE   City = @City
OPTION (OPTIMIZE FOR UNKNOWN);
GO
EXEC dbo.AddressByCity @City = N'Mentor';
Listing 10-20 · optimizing for more than one value
CREATE OR ALTER PROCEDURE dbo.AddressDetails
    @City NVARCHAR(30),
    @PostalCode NVARCHAR(15),
    @AddressLine2 NVARCHAR(60) NULL
AS
SELECT a.AddressLine1,
       a.AddressLine2,
       a.SpatialLocation
FROM Person.Address AS a
WHERE a.City = @City
      AND a.PostalCode = @PostalCode
      AND (   a.AddressLine2 = @AddressLine2
              OR @AddressLine2 IS NULL)
OPTION (OPTIMIZE FOR (@City = 'London', @PostalCode = 'W1Y 3RA'));
One hint clause, as many parameter values as you need. Note this listing also contains the OR … IS NULL optional-parameter pattern — the one that costs you seeks (Chapter 8).

This is one of the few hints the author uses regularly, "though still not often" — and always with the caveat that using it requires intimate knowledge of the data. The wrong value doesn't just fail to help; it actively hurts.

RECOMPILE

Listing 10-21 · the tipping point again
SELECT  soh.SalesOrderNumber ,
        soh.OrderDate ,
        soh.SubTotal ,
        soh.TotalDue
FROM    Sales.SalesOrderHeader soh
WHERE   soh.SalesPersonID = 279;
GO
SELECT  soh.SalesOrderNumber ,
        soh.OrderDate ,
        soh.SubTotal ,
        soh.TotalDue
FROM    Sales.SalesOrderHeader soh
WHERE   soh.SalesPersonID = 280;
Listing 10-22 · the same query as a prepared statement
DECLARE @IDValue INT;
DECLARE @MaxID INT = 280;
DECLARE @PreparedStatement INT;
SELECT @IDValue = 279;
EXEC sp_prepare @PreparedStatement OUTPUT,
                N'@SalesPersonID INT',
                N'SELECT  soh.SalesPersonID, soh.SalesOrderNumber,
        soh.OrderDate,
        soh.SubTotal,
        soh.TotalDue
FROM    Sales.SalesOrderHeader soh
WHERE   soh.SalesPersonID =  @SalesPersonID';
WHILE @IDValue <= @MaxID
BEGIN
    EXEC sp_execute @PreparedStatement, @IDValue;
    SELECT @IDValue = @IDValue + 1;
END
EXEC sp_unprepare @PreparedStatement;

Because sp_prepare compiles before any value exists, there's no sniffing: you get one clustered index scan plan, used for both values, in either execution order. Stable — and wrong for the selective value.

Listing 10-23 · adding RECOMPILE to the prepared statement
…
EXEC sp_prepare @PreparedStatement OUTPUT,
                N'@SalesPersonID INT',
                N'SELECT  soh.SalesPersonID, soh.SalesOrderNumber,
        soh.OrderDate,
        soh.SubTotal,
        soh.TotalDue
FROM    Sales.SalesOrderHeader soh
WHERE   soh.SalesPersonID =  @SalesPersonID
OPTION (RECOMPILE)';
…
Both plans, neither cached With RECOMPILE you see the two different plans in SSMS again — and in the plan cache, neither. For code modules, every statement stays cached but the hinted statement recompiles every execution; for ad hoc queries the plan isn't stored at all. You swap cache pressure for compile CPU, deliberately.

6 EXPAND VIEWS and the columnstore ignore hint

Two hints that say "don't use the clever structure I built" — and the measurements that explain why you usually shouldn't say it.

Listing 10-24 · a query against an indexed view
SELECT vspcr.StateProvinceCode,
       vspcr.StateProvinceName,
       vspcr.CountryRegionName
FROM Person.vStateProvinceCountryRegion AS vspcr;

OPTION (EXPAND VIEWS) replaces any referenced indexed view with its definition during compilation and then skips view matching — so the optimizer never gets the chance to use the materialised copy.

The fine print Indexed-view matching is Enterprise only, so on Standard this hint does nothing at all. You can override the hint per view with WITH (NOEXPAND). And in most cases (not all) the indexed view is the better plan — test before you expand.

IGNORE_NONCLUSTERED_COLUMNSTORE_INDEX does what it says for the whole query: any nonclustered columnstore index is ignored. It does not affect a clustered columnstore index. Useful when a columnstore that's great for aggregations is being chosen for a point lookup it's bad at (Chapter 8).

7 Join hints and table hints

Now the surgical ones: a single join, a single index, a single operator type. More precision, more ways to hurt yourself.

Join hints

LOOP, HASH or MERGE, written into the JOIN clause. Two consequences worth knowing: a join hint also forces the join order — effectively the same as OPTION (FORCE ORDER) — and you cannot force an Adaptive Join (Chapter 4) with any hint. A fourth kind, REMOTE, pushes the join to a remote server and doesn't change the visible plan.

Listing 10-25 · the reference query again
SELECT pm.Name,
       pm.CatalogDescription,
       p.Name AS ProductName,
       i.Diagram
FROM Production.ProductModel AS pm
    LEFT JOIN Production.Product AS p
        ON pm.ProductModelID = p.ProductModelID
    LEFT JOIN Production.ProductModelIllustration AS pmi
        ON p.ProductModelID = pmi.ProductModelID
    LEFT JOIN Production.Illustration AS i
        ON pmi.IllustrationID = i.IllustrationID
WHERE pm.Name LIKE '%Mountain%'
ORDER BY pm.Name;
Listing 10-26 · HASH on one join only
SELECT pm.Name,
       pm.CatalogDescription,
       p.Name AS ProductName,
       i.Diagram
FROM Production.ProductModel AS pm
    LEFT JOIN Production.Product AS p
        ON pm.ProductModelID = p.ProductModelID
    LEFT JOIN Production.ProductModelIllustration AS pmi
        ON pm.ProductModelID = pmi.ProductModelID
    LEFT HASH JOIN Production.Illustration AS i
        ON pmi.IllustrationID = i.IllustrationID
WHERE pm.Name LIKE '%Mountain%'
ORDER BY pm.Name;
Note where the hint goes: LEFT HASH JOIN, not LEFT JOIN … OPTION(HASH JOIN). That's the whole difference between one join and every join.
Note on Figure 10-27 In my copy of the book, the image embedded for Figure 10-27 is pixel-for-pixel the same plan as Figure 10-26 — the optimizer's original, un-hinted plan. The text says the Illustration join should now be a Hash Match with the other joins changed to Merge Joins and a Sort added on Product. Read the caption as the intended plan, and treat the image as a printing fault rather than as evidence that the hint did nothing. The numbers in the prose (34 reads) are what you're meant to take away.
The best result in the chapter 485 reads → 34, and runtime down marginally (77 → 74 ms). Eliminating the 455 repeated scans is a real, substantial I/O saving. The time barely moved, so whether it's "better" depends entirely on whether your bottleneck is I/O contention — which needs testing on a loaded system to establish.

Table hints and NOEXPAND

Table hints can change locking behaviour and therefore data integrity, so they deserve even more caution than the others. The syntax is always the same:

Listing 10-27 · table hint syntax
FROM TableName WITH (hint, hint,…)
WITH and commas aren't mandatory for every hint, but they're allowed for all of them — use both and stop guessing.
Listing 10-28 · NOEXPAND
SELECT a.City,
       v.StateProvinceName,
       v.CountryRegionName
FROM Person.Address AS a
    JOIN Person.vStateProvinceCountryRegion AS v WITH (NOEXPAND)
        ON a.StateProvinceID = v.StateProvinceID
WHERE a.AddressID = 22701;
Why NOEXPAND matters most on Standard Edition Enterprise and Developer will use an indexed view's indexes when the optimizer judges it best — that's indexed view matching, and it needs a specific session state: ANSI_NULLS, ANSI_WARNINGS, CONCAT_NULL_YIELDS_NULL, ANSI_PADDING, ARITHABORT and QUOTED_IDENTIFIER all ON, and NUMERIC_ROUNDABORT OFF. On Standard, matching doesn't happen at all — so NOEXPAND is how you get the indexed view used.

INDEX()

Listings 10-29 to 10-31 · three ways to name an index
-- by number (from sys.indexes) — not recommended, numbering can change
…FROM dbo.TableName WITH (INDEX(2))…

-- by name — the book's recommendation
…FROM dbo.TableName WITH (INDEX (IndexName))…

-- several indexes in ONE hint = force an index intersection
…FROM TableName WITH (INDEX (IndexName1,IndexName2))…
Two special numbers: 0 forces a scan of the clustered index or heap; 1 forces a scan or seek on a clustered index and errors on a heap. And note what the multi-index form does — it doesn't let the optimizer pick among those indexes, it forces all of them, in the listed order.
Listing 10-32 · index intersection in action
CREATE TABLE dbo.IndexSample (ID INT NOT NULL IDENTITY(1, 1),
                              ColumnA INT,
                              ColumnB INT,
                              ColumnC INT,
                              CONSTRAINT IndexSamplePK
                                  PRIMARY KEY (ID));

CREATE INDEX FirstIndex ON dbo.IndexSample (ColumnA);
CREATE INDEX SecondIndex ON dbo.IndexSample (ColumnB);
CREATE INDEX ThirdIndex ON dbo.IndexSample (ColumnC);

SELECT isa.ID,
       isa.ColumnA,
       isa.ColumnB,
       isa.ColumnC
FROM dbo.IndexSample AS isa WITH (INDEX(FirstIndex, SecondIndex, ThirdIndex));

DROP TABLE dbo.IndexSample;
Listings 10-33 and 10-34 · a realistic use, and a warning
-- the unhinted query
SELECT de.Name,
       e.JobTitle,
       p.LastName + ', ' + p.FirstName
FROM HumanResources.Department AS de
    JOIN HumanResources.EmployeeDepartmentHistory AS edh
        ON de.DepartmentID = edh.DepartmentID
    JOIN HumanResources.Employee AS e
        ON edh.BusinessEntityID = e.BusinessEntityID
    JOIN Person.Person AS p
        ON e.BusinessEntityID = p.BusinessEntityID
WHERE de.Name LIKE 'P%';

-- the same query, forcing the Department clustered index
SELECT de.Name,
       e.JobTitle,
       p.LastName + ', ' + p.FirstName
FROM HumanResources.Department AS de WITH (INDEX(PK_Department_DepartmentID))
    JOIN HumanResources.EmployeeDepartmentHistory AS edh
        ON de.DepartmentID = edh.DepartmentID
    JOIN HumanResources.Employee AS e
        ON edh.BusinessEntityID = e.BusinessEntityID
    JOIN Person.Person AS p
        ON e.BusinessEntityID = p.BusinessEntityID
WHERE de.Name LIKE 'P%';

Twice the speed here, identical reads. Which is exactly why the "just make it seek" instinct is unreliable — as the next pair of hints proves.

FORCESEEK / FORCESCAN

The mirror image of INDEX(): force the operator and let the optimizer choose the index.

Listing 10-35 · no WHERE clause, so: scans
SELECT p.Name AS ComponentName,
       p2.Name AS AssemblyName,
       bom.StartDate,
       bom.EndDate
FROM Production.BillOfMaterials AS bom
    JOIN Production.Product AS p
        ON p.ProductID = bom.ComponentID
    JOIN Production.Product AS p2
        ON p2.ProductID = bom.ProductAssemblyID;
Listing 10-36 · FORCESEEK
SELECT p.Name AS ComponentName,
       p2.Name AS AssemblyName,
       bom.StartDate,
       bom.EndDate
FROM Production.BillOfMaterials AS bom WITH (FORCESEEK)
    JOIN Production.Product AS p
        ON p.ProductID = bom.ComponentID
    JOIN Production.Product AS p2
        ON p2.ProductID = bom.ProductAssemblyID;
The numbers that end the argument 145 ms → 290 ms. 34 reads → 1,160. Taking the scan away forced a plan that re-reads the same data thousands of times. "Seeks are always better than scans" is one of the most expensive myths in T-SQL, and this is the chapter's best demolition of it.

  • Hints are commands. The optimizer will obey, or fail with an error — it will not quietly do the sensible thing.
  • A hint removes the optimizer's ability to improve later. Data changes, patches land, upgrades happen; the hint doesn't.
  • Most hints in this chapter made things worse. That's not a coincidence of the book's examples; it's the base rate.
  • Fewer reads ≠ faster, and faster ≠ cheaper. Compare reads, elapsed time, and memory grant — then choose which one you actually need.
  • Always ask what the real problem is. Every join-hint experiment above still had a non-SARGable LIKE '%Mountain%' at its centre.
  • Document and re-test. A hint without a note explaining why is a landmine with a timer on it.
The chapter's summary, condensed The optimizer is usually right and sometimes wrong. When it's wrong and you can't change the code, query, join and table hints can take control — but the data is always changing, so anything you force today can become tomorrow's problem. Test before you apply, document why, re-test after every upgrade, and treat hints as a last resort rather than standard practice.
