Chapter 16

The Query Store

The plan cache forgets. The Query Store is the first tool in this book that remembers — per query, per plan, with runtime metrics, persisted inside the database. That last part is what enables plan forcing, and plan forcing is what turns "the plan regressed" from a fire into a setting.

1 What it is, and how it stays out of the way

Query Store arrived in Azure SQL Database in 2015 and in the boxed product with SQL Server 2016. It records query metrics and keeps every version of every plan, per database.

The design goal is to record everything without disturbing normal operations, and that goal explains almost every behaviour in this chapter:

Capture is asynchronousInfo lands in memory first, and a background process flushes it to disk — asynchronously, again.
It doesn't touch optimisationOnce the optimizer has produced a plan, Query Store grabs it as it's written to cache. It never interferes with compilation.
It catches plans that never cacheAn ad hoc query with RECOMPILE produces a plan that isn't cached — but by default Query Store captures it anyway, at the moment it would have been.
Metrics are aggregatedAfter execution, another async process records how long it ran, how much memory it used, and so on.

Everything lives in system tables in each database where the feature is enabled. You can turn it on and off, but you cannot choose where the data goes — always the PRIMARY filegroup. Off by default in SQL Server 2016; on by default in Azure SQL Database.

The organizing principle is the query Not the stored procedure, not the batch — the individual query, with one or more plans beneath it. That's the "query" in Query Store, and it's why the catalog views look the way they do.

Why plans are stored as text, not XML

query_plan is NVARCHAR(MAX) even though the content is XML. The reason is unglamorous: SQL Server has a limit on XML nesting depth, and deep plans would break it. To view a plan graphically you must either CAST(qsp.query_plan AS XML) — fine as long as you're under the nesting limit — or export it to a .showplan file.

Change them with ALTER DATABASE, not the GUI — the GUI can't reach all of them.

Retention and clean-up: 367 days by default — a leap year plus a day — with automatic clean-up once data passes the limit. Adjust, or turn the clean-up off, depending on how much history you actually need. And since the data is in system tables, you can't relocate it; only control its volume.

4 Getting plans with T-SQL

Four catalog views do almost all the work. Everything else is wrapping them in the right order and getting past one annoying quirk.

Catalog viewHolds
sys.query_store_planThe plan itself, plus query_plan_hash, compatibility level, whether it's trivial (Figure 16-1).
sys.query_store_queryIdentifies a query — last compile time, parameterization type, query hash. Not the text (stored separately).
sys.query_context_settingsANSI settings, replication flag, language — the context a query ran under.
sys.query_store_query_textThe query text.

Three other Query Store views exist; they're about performance metrics, not plans, so they're out of scope here.

Listing 16-3 · all four views, one query
SELECT qsq.query_id,
       qsqt.query_sql_text,
       CAST(qsp.query_plan AS XML),
       qcs.set_options
FROM sys.query_store_query AS qsq
    JOIN sys.query_store_query_text AS qsqt
        ON qsqt.query_text_id = qsq.query_text_id
    JOIN sys.query_store_plan AS qsp
        ON qsp.query_id = qsq.query_id
    JOIN sys.query_context_settings AS qcs
          ON qcs.context_settings_id = qsq.context_settings_id
WHERE qsq.object_id = OBJECT_ID('dbo.AddressByCity');

The CAST(... AS XML) is what makes the column clickable in SSMS. The query_context_settings join is there because a query executed under different SET options shows up more than once.

The parameterization quirk

Listing 16-4 · the text Query Store actually stored
(@City nvarchar(30))SELECT a.AddressID  ,a.AddressLine1
,a.AddressLine2  ,a.City  ,sp.[Name] AS StateProvinceName
,a.PostalCode  FROM Person.Address AS a  JOIN Person.StateProvince
AS sp  ON a.StateProvinceID = sp.StateProvinceID  WHERE a.City = @City
Listing 16-5 · what you wrote
CREATE OR ALTER PROC dbo.AddressByCity @City NVARCHAR(30)
AS
SELECT a.AddressID, a.AddressLine1, a.AddressLine2,
       a.City, sp.Name AS StateProvinceName,
       a.PostalCode
FROM Person.Address AS a
    JOIN Person.StateProvince AS sp
        ON a.StateProvinceID = sp.StateProvinceID
WHERE a.City = @City;
Query Store prepends the parameter definition That (@City nvarchar(30)) prefix is not in your procedure. It's injected into the stored text, which means you cannot find your query by searching for the text you wrote. This "vagary" is the single biggest source of wasted time when querying the catalog views directly.

It gets worse for ad hoc queries and better at the same time:

Listing 16-6 · a simple ad hoc query
SELECT bom.BillOfMaterialsID,
       bom.StartDate,
       bom.EndDate
FROM Production.BillOfMaterials AS bom
WHERE bom.BillOfMaterialsID = 2363;

Simple parameterization kicks in: 2363 becomes @1 inside the stored plan. So this returns nothing at all:

Listing 16-7 · the empty result you'll hit once and remember
SELECT qsqt.query_text_id
FROM sys.query_store_query_text AS qsqt
WHERE qsqt.query_sql_text = 'SELECT bom.BillOfMaterialsID,
       bom.StartDate,
       bom.EndDate
FROM Production.BillOfMaterials AS bom
WHERE bom.BillOfMaterialsID = 2363;';

The original T-SQL was never stored — only the parameterized version. The rescue is sys.fn_stmt_sql_handle_from_sql_stmt, which maps the text you wrote to the statement handle Query Store knows about. It needs two things: your SQL, and the parameterization type (which you get from sys.query_store_query).

Listing 16-8 · finding it anyway
SELECT qsqt.query_text_id
FROM sys.query_store_query_text AS qsqt
    JOIN sys.query_store_query AS qsq
        ON qsq.query_text_id = qsqt.query_text_id
    CROSS APPLY sys.fn_stmt_sql_handle_from_sql_stmt(
                    'SELECT bom.BillOfMaterialsID,
       bom.StartDate,
       bom.EndDate
FROM Production.BillOfMaterials AS bom
WHERE bom.BillOfMaterialsID = 2363;',
                    qsq.query_parameterization_type) AS fsshfss
WHERE fsshfss.statement_sql_handle = qsqt.statement_sql_handle;
Which tool for which query Ad hoc or simple/forced parameterized → fn_stmt_sql_handle_from_sql_stmt. Stored procedure → that function doesn't work; use object_id (and deal with the multiple statements inside the proc) or LIKE.

5 Plan forcing

The most important thing Query Store does for plans — and the one deliberate exception to "everything here is asynchronous".

Forcing is synchronous by design. Once a plan is forced, it survives cache flushes, recompiles, server reboots, even a backup and restore of the database, because the fact that it's forced is written into the Query Store system tables and travels with the database. The only conditions: the plan must still be valid for the query as currently defined (an index change can invalidate it), and there's a rare case where a "morally equivalent" plan — identical in all the core essentials — gets used instead.

Forcing beats plan guides If you're on SQL Server 2016+ or Azure SQL Database and need to pin a plan, use Query Store forcing rather than a plan guide (Chapter 9). If both exist, Query Store forcing wins.

Two situations where it's the right answer:

  • Parameter sniffing gone wrong — the classic from Chapter 10, where one plan is consistently better across the range of parameters than the plan the optimizer keeps choosing.
  • Plan regression — something changed and the new plan is worse. Common causes: upgrading past SQL Server 2012 (new cardinality estimator), or a CU/hotfix that changes optimizer behaviour. Run Query Store data before changing compatibility level or applying the CU, and you can prove the regression and undo it.
Double-edged sword Forcing is not set-and-forget. The author's advice is extremely judicious use plus a review schedule — because statistics and data change, and the perfect plan to force today may not be the perfect plan tomorrow.

A demonstration: London, then Mentor

Listing 16-9 · the big-city execution
EXEC dbo.AddressByCity @City = N'London';
Listing 16-10 · evict that plan
DECLARE @PlanHandle VARBINARY(64);

SELECT @PlanHandle = deqs.plan_handle
FROM sys.dm_exec_query_stats AS deqs
    CROSS APPLY sys.dm_exec_sql_text(deqs.sql_handle) AS dest
WHERE dest.objectid = OBJECT_ID('dbo.AddressByCity');

IF @PlanHandle IS NOT NULL
BEGIN;
    DBCC FREEPROCCACHE(@PlanHandle);
END;
GO
Listing 16-11 · the small-town execution
EXEC dbo.AddressByCity @City = N'Mentor';

To force one, you need two numbers: query_id and plan_id.

Listing 16-12 · find the IDs
SELECT qsq.query_id,
       qsp.plan_id,
       CAST(qsp.query_plan AS XML)
FROM sys.query_store_query AS qsq
    JOIN sys.query_store_plan AS qsp
        ON qsp.query_id = qsq.query_id
WHERE qsq.object_id = OBJECT_ID('dbo.AddressByCity');

Look at both plans, decide which is the more predictable one, then:

Listing 16-13 · force it
EXEC sys.sp_query_store_force_plan 214, 248;

Now flush the cache again and pass any city you like — you get plan 248 every time. And the forced plan carries a marker that says so:

Listing forced plans, and undoing it:

Listing 16-14 · everything currently forced

6 Automatic tuning: forcing without a human

SQL Server 2017 and the foundation of Azure SQL Database's automatic tuning. It is only plan forcing, chosen by the engine — no statistics updates, no indexes, no code changes.

Listing 16-16 · enable FORCE_LAST_GOOD_PLAN
ALTER DATABASE CURRENT SET AUTOMATIC_TUNING(
    FORCE_LAST_GOOD_PLAN = ON);

Off by default. Once Query Store is enabled and collecting, here's the loop:

1 · DetectA plan change clearly causes a regression.
2 · ForceThe engine enables the last good plan — not necessarily optimal, just better than what's running now.
3 · VerifyIt keeps measuring. If performance got worse, forcing is revoked and the query recompiles on its next call.

You don't have to enable anything to see the opportunities. A DMV lists them, and its interesting columns — type, reason, state, details — are partly JSON, so you have to pull them apart (which is the Chapter 14 material coming back around).

Listing 16-17 · pulling the JSON apart
SELECT ddtr.reason,
       ddtr.score,
       pfd.query_id,
       JSON_VALUE(ddtr.state,
                  '$.currentValue') AS CurrentState
FROM sys.dm_db_tuning_recommendations AS ddtr
    CROSS APPLY
    OPENJSON(ddtr.details,
             '$.planForceDetails')
    WITH (query_id INT '$.queryId') AS pfd;

Useful on its own. To actually act on it, join the DMV to the Query Store catalog views — this is the query that gives you the recommendation and both plans and the script that implements it:

Listing 16-18 · recommendations joined to Query Store
WITH DbTuneRec
AS (SELECT ddtr.reason,
           ddtr.score,
           pfd.query_id,
           pfd.regressedPlanId,
           pfd.recommendedPlanId,
           JSON_VALUE(ddtr.state,
                      '$.currentValue') AS CurrentState,
           JSON_VALUE(ddtr.state,
                      '$.reason') AS CurrentStateReason,
           JSON_VALUE(ddtr.details,
                      '$.implementationDetails.script') AS
                      ImplementationScript
    FROM sys.dm_db_tuning_recommendations AS ddtr
        CROSS APPLY
        OPENJSON(ddtr.details,
                 '$.planForceDetails')
        WITH (query_id INT '$.queryId',
              regressedPlanId INT '$.regressedPlanId',
              recommendedPlanId INT '$.recommendedPlanId') AS pfd)

SELECT qsq.query_id,
       dtr.reason,
       dtr.score,
       dtr.CurrentState,
       dtr.CurrentStateReason,
       qsqt.query_sql_text,
       CAST(rp.query_plan AS XML) AS RegressedPlan,
       CAST(sp.query_plan AS XML) AS SuggestedPlan,
       dtr.ImplementationScript
FROM DbTuneRec AS dtr
    JOIN sys.query_store_plan AS rp
        ON rp.query_id = dtr.query_id
           AND rp.plan_id = dtr.regressedPlanId
    JOIN sys.query_store_plan AS sp
        ON sp.query_id = dtr.query_id
           AND sp.plan_id = dtr.recommendedPlanId
    JOIN sys.query_store_query AS qsq
        ON qsq.query_id = rp.query_id
    JOIN sys.query_store_query_text AS qsqt
        ON qsqt.query_text_id = qsq.query_text_id;

score is an estimated impact, 0–100. Run this whether or not automatic tuning is on: without it you get candidates to force by hand, with it you mostly get plans the engine has already forced.

Watching it happen

The demo procedure generates five different plans when run across the full range of ReferenceID values; one is far slower than the rest, so eventually the engine forces the good one.

Listing 16-19 · the victim
CREATE OR ALTER PROC dbo.ProductTransactionHistoryByReference
    (@ReferenceOrderID INT)
AS
BEGIN
    SELECT p.Name,
           p.ProductNumber,
           th.ReferenceOrderID
    FROM Production.Product AS p
        JOIN Production.TransactionHistory AS th
            ON th.ProductID = p.ProductID
    WHERE th.ReferenceOrderID = @ReferenceOrderID;
END

Confirm who did it:

Listing 16-20 · who forced it, and when
SELECT ddtr.reason,
       ddtr.valid_since,
       ddtr.last_refresh,
       ddtr.execute_action_initiated_by
FROM sys.dm_db_tuning_recommendations AS ddtr;
The revert path, and whose decision wins If the engine later measures that forcing hurt performance, forcing is removed and the Revert_* columns in sys.dm_db_tuning_recommendations fill in. The record of what was forced — and why — stays until you remove the data from Query Store. If you unforce it manually, execute_action_initiated_by shows User, and that query won't be automatically forced again regardless of behaviour. Your override beats the automation — right up until you clear the Query Store data, at which point your override is forgotten too.

7 Removing plans — and the privacy problem

Three levels of delete, then the part that matters if you ever hand a database to someone else.

Listing 16-21 · everything
ALTER DATABASE AdventureWorks2014 SET QUERY_STORE CLEAR;
Listing 16-22 · one query, all its plans and stats
EXEC sys.sp_query_store_remove_query
    @query_id = 214;
Listing 16-23 · one plan only
EXEC sys.sp_query_store_remove_plan @plan_id = 248;
CommandRemovesSide effect
SET QUERY_STORE CLEAREvery bit of Query Store information.Heavy handed. Appropriate before handing a restored production database to development.
sp_query_store_remove_queryThe query, all captured plans, all runtime stats.Forcing stops, because the information is no longer stored.
sp_query_store_remove_planThat one plan.Query and other plans survive; forcing on that plan stops.
Disabling Query StoreNothing.All data stays in place.
Query Store data travels with the database It's in system tables, so it's in the backup — and in any restore. That includes query text with filter criteria and compile-time parameter values baked in. If you're sanitising healthcare or similarly restricted data before handing a database to someone unauthorised, Query Store is a place your sensitive values are hiding. Use the removal commands above deliberately.

8 Cheat sheet

What the Query Store gives you that nothing earlier in the book could.

QuestionAnswer
How does it affect query performance?It doesn't, by design: capture is asynchronous and happens after optimisation, at cache-write time. The exception is plan forcing, which is synchronous.
Where is the plan stored?sys.query_store_plan.query_plan as NVARCHAR(MAX) — text, to dodge XML nesting limits. CAST it to XML to make it clickable.
Why can't I find my query text?Parameterization. Query Store stores the parameterized text, prefixed with definitions like (@City nvarchar(30)). Use fn_stmt_sql_handle_from_sql_stmt for ad hoc queries; object_id for procs.
How do I force a plan?sp_query_store_force_plan query_id, plan_id — or the button in the report. Undo with sp_query_store_unforce_plan.
How do I know a plan is forced?Use plan = True on the first operator; is_forced_plan = 1 in sys.query_store_plan; a check mark in the reports.
Does forcing survive a reboot/restore?Yes — it's stored with the database. It does not survive the plan becoming invalid (e.g. an index change).
Automatic tuning?2017+. AUTOMATIC_TUNING(FORCE_LAST_GOOD_PLAN = ON). It's only ever plan forcing, and it reverts itself if the forced plan measures worse.
Where do recommendations live?sys.dm_db_tuning_recommendations — state and details are JSON; score is 0–100 impact.
Who forced the plan?execute_action_initiated_by = System or User. A user override suppresses further automation.
  • Organised by query, not by procedure or batch. That's the mental model for every catalog view.
  • Default retention is 367 days — a leap year plus one — with automatic clean-up.
  • QUERY_CAPTURE_MODE: ALL / AUTO / NONE. Choose AUTO if Optimize For Ad Hoc Workloads is on.
  • Regressed Queries is the report to start with, and Top Resource Consuming Queries the one you'll live in.
  • Two plans selected → Compare Execution Plans. The most useful thing in the report toolbar.
  • Review every forced plan on a schedule. Today's perfect plan is tomorrow's regression.
  • Sanitise before you hand over a database. Query Store keeps query text and compile-time parameters.
The chapter's summary, condensed Query Store persists plans and runtime metrics inside the database, which lets you troubleshoot offline from production and — crucially — force a plan and have that decision survive everything short of the plan becoming invalid. That solves a whole class of plan regressions. But data and statistics keep moving, so the plan worth forcing today needs revisiting tomorrow.
